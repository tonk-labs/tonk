# July 5th

## A space that just sat there never pulled

Sync is meant to ride ordinary request traffic: every fetch through the service worker's `on_fetch` schedules a debounced drain that pushes dirty repos and pulls every open one, so a viewer picks up a remote edit without ever committing. That holds only as long as the tab keeps making requests. Once a `/space` finishes booting it settles into a steady state where the only open connection is the SSE subscription, and a subscription is one long-lived request, not a stream of new ones. No new fetch means no new drain, so a second client's edits just never arrive at the tab you are watching. The plan had flagged this idle case and left it open, assuming some low-frequency traffic would keep the pump primed, but on the space route there was none.

The fix is an idle-time poll from the top-page `<tonk-host>`. A `requestIdleCallback` loop fetches `POST /api/sync` roughly every second while the tab is open, and immediately on `visibilitychange` back to visible and on `online`, so a refocus reconciles at once. The endpoint itself does nothing: it returns 200 and that is all. The point is not the handler, it is that reaching it is a fetch, so `on_fetch` schedules the normal debounced drain like any other request. The poll rides the existing machinery instead of forcing a sync, which matters because a forced drain in the handler would stack a second, un-debounced one on top of the scheduled one. Hidden tabs throttle `requestIdleCallback` to about once every ten seconds on their own, so there is no visibility gate to write; Safari, which lacks the API, falls back to a timer.

## The debounce could defer forever

Chasing the idle case surfaced the opposite failure. The drain uses a trailing-edge debounce with a generation ticket: every request bumps the generation and schedules a drain, and when that wakes it only runs if its ticket is still the latest. A burst collapses into one drain, the last request wins. But a tab making requests faster than the debounce window keeps bumping the generation, so no ticket is ever the latest when it wakes, and the drain starves indefinitely. Busy is exactly when you want it to run, and it was the one case that never did.

Added a max-wait cap. The scheduler now stamps when the current un-drained burst began and clears it on each drain. A woken ticket runs if it is the latest, as before, or if the burst has been pending past the cap, regardless of newer requests. So continuous traffic still coalesces, but the drain fires at least every few seconds no matter what. Dropped the debounce from two seconds to five hundred milliseconds while I was in there, since it is now the real rate limiter, and collapsed the background-sync tag to a bare `sync` because the handler drains the whole queue regardless of which repo the tag named.

Unit tests over the scheduler cover the coalescing, the cap firing under continuous traffic, the cap clock resetting after a drain, and the no-overlap guard. tonk PR on `fix/sync-idle-poll`, BUG-36.

## The launcher was unusable in dark mode

Dark mode was effectively ignored: white surfaces, black text on a black chrome, a Hub launcher you could not read. The cause was not the theming plumbing, which was fine, but colors that bypassed it. The launcher view carried its own light-only palette (`--ink`, `--paper`, `--accent`, `--lime`), and the app shell that gets injected into every sealed space view hard-coded a `#f0f0f0` body background. Those constants never adapt, so no matter what color scheme the OS asked for, the page stayed light.

The fix was to stop inlining colors and adopt Web Awesome's design tokens everywhere instead. Every surface, border, and ink now reads from a `--wa-color-*` semantic token, which redefines itself per mode, so the launcher, its create-spot wizard, and the app background become color-mode agnostic and pick up dark or light for free. The interaction states followed the same rule: the card hover lift and the selected-template ring derive their color from `--wa-color-text-normal` mixed to a low alpha rather than a fixed rgb, so a drop-shadow that was invisible on the dark surface now mirrors correctly in both modes. The brand accent moved to `#DEFF1A` across the app as one token change.

## The wordmark font never reached the sealed guest

The launcher's Gestalte display type rendered as plain sans-serif because it could not load inside the sealed iframe. The guest cannot fetch fonts across its null origin, so the host inlines them as data URLs, but that inliner only handled `.woff2` and Gestalte ships as `.otf`. Worse, the "tonk" wordmark uses a separate cut, GestalteName, that was not in the repo at all. Taught the inliner to embed any file under `/fonts/` regardless of extension, pulled the GestalteName face out of the design source and self-hosted it, and made the wordmark live text rather than a black logo image so it takes the theme ink instead of going black-on-black.

Verified the whole flow in the browser against both the wireframe and the deployed launcher. The awkward part was that the launcher view seeds into the profile branch once at service-worker boot and page reloads do not restart the worker, so edits look stale until the worker is torn down and reseeded. tonk PR #559 on `fix/dark-mode`.
