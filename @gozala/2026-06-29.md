# June 29th

## The `{subject}` database mystery

Spent the day chasing two symptoms on the Hub that turned out to be one cause plus a latent dialog bug. The Hub rendered no spaces even though the profile had two, and an IndexedDB database literally named `{subject}` kept appearing.

Walked it back with chrome devtools. The profile had two real spaces, both with `subject`/`kind`/`status` facts, and a hand-run query returned both rows. But `<tonk-display model=space>` sat at `data-state=empty` with an empty `<!--tonk-repeat-->`. The directory builds its instances query as an all-required join over every descriptor field, so the empty list meant a field in the descriptor had no matching fact on the records.

It did. The stored `tonk:space` descriptor had four fields, not three: a `name` (`xyz.tonk.replica/name`) that the current `profile.yaml` source no longer declares and the replica writer never stamps. So the join required a `name` fact that does not exist, dropped every nameless replica, and the directory folded to zero rows. Profile concept descriptors are lowered once and never reconciled, so my old profile DB still carried the four-field version from a branch where `name` was a thing. That is the recurrence I kept seeing: a field added-then-dropped strands every existing profile.

The empty directory still renders its repeat scaffold once, unbound, so `<tonk-repository name={subject}>` and the sync badge ran with the literal placeholder. That fired `GET /api/repository/{subject}/branch/main/sync/status`, which 404'd, but the database was already created by then.

## load should not create

The 404 was a red herring for where the DB came from. The reactor's `acquire` already calls `.load()`, which is documented "load existing, fail if not found" and did fail (hence the 404). The leak is one layer down in dialog: `storage::Load`'s handler calls `S::open(location)` before checking the credential, and IndexedDB's `open` brings the database into being. Native FS never had this because its `open` is lazy, a path is created only on first write. So load was leaking an empty DB on every miss, and it is still that way on dialog master.

Fixed it upstream rather than guarding against names in tonk, which is the wrong layer. Split the contract: `Resource::open` stays open-or-create, new `Resource::load` is open-existing-only and must materialize nothing. The default `load` delegates to `open` (correct for the lazy backends), and IndexedDb overrides it to probe `indexedDB.databases()` first and error when absent, creating nothing. `Space` forwards `load` to its four fields, and the loader's `storage::Load` calls `load`.

Wrote the failing test first, in both suites. The native one passed immediately, which is what told me the leak is IndexedDB-only. The web one failed for the exact right reason: load of a missing space created the `{name}.profile` database. Passes after the fix. dialog PR [#365](https://github.com/dialog-db/dialog-db/pull/365) against `feat/dialog-remote-fs`.

> [!note]
> Self-healing (delete the empty DB after open) was the obvious shortcut and it is wrong. An empty DB is not proof we created it. You do not delete something on the assumption you made it.

On the tonk side I made `name` optional (`maybe:`) in the `&space` concept so a missing `name` fact stops emptying the Hub for new profiles. Existing profiles still need a reseed or a startup re-lowering, which is the real recurrence fix and still open.

## A bug that vanished from its own concept

A bug created in the UI (BUG-27) was missing from the board. It still answered a loose `squash.bug:` domain query but not the strict `bug:` concept query, so something matched on type, not just attribute.

It was the ordering. The UI sets `ordering: maxOrd+1`, a JS number, and JSON has no integer type, so it deserializes to a float. The concept declares `ordering` as `SignedInteger`. The view's query and the concept query match by attribute id and value type, and a float fact never binds a `SignedInteger` slot, so the entity dropped out of its own concept with no error. Same shape as the `age as: text` bug from earlier, except on the JSON transact path, which had no type gate at all.

`/transact` was emitting one EAV per parameter verbatim. The descriptor was right there at the emit site, carrying each field's declared `as:`, and we read it only for the attribute id and cardinality, never to check or coerce the value.

Fix is in the type. `SourceApplication` is the raw wire form; `PredicateApplication` is the validated one with private fields, reachable only through `TryFrom<SourceApplication>`. The conversion casts each value to its declared type, lossless only: an integral float narrows to int, a string parses into an entity or symbol, an entity widens to text. A real mismatch is an error and becomes a 4xx. Holding a `PredicateApplication` is now proof the values conform, so the emitter cannot receive a bad one. dialog's own `scalar_to_value` stays stricter on the int/float axis because notation has a real integer literal and the wire does not. tonk PR [#546](https://github.com/tonk-labs/tonk/pull/546).

> [!caution]
> My first cut also required a construction to carry every declared field. The wasm `it_dispatches_the_invite_command` test caught it: `tonk:invite` declares `prevent-default` in its `with:` but the command never sends it. A `with:` map is the concept's shape, not the fields a given call provides. Commands and updates bind a subset. Missing field is not an error.

Then the data. Flipped `bug-ordering` to `Float`, rebound the concept, rewrote all 37 orderings to float. Retract-then-assert, not a plain re-assert: a different value type does not replace the old fact, it coexists, so I had to drop the int fact explicitly first. The view is its own surprise: it carries an inline descriptor inside the artifact's portal content HTML, `ordering as: SignedInteger`, independent of the `bug` name. So migrating the data to float made the view match zero until I edited that string too.

> [!note]
> `assignee` is the same bug waiting. Stored as an `entity` (a person did), declared `as: Text`. Seven assigned bugs are hidden from the full concept query for exactly this reason. Filed as BUG-29's sibling, still open.
