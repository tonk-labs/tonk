# May 17

## Weekend Journey into Effects

Over the weekend I had some time to think more about effects, and I've updated last week's code snippet. Copying here is roughly my current thinking on the matter. You define a concept for the thing that causes an effect, I'm considering calling these [abilities (like Unison)](https://www.unison-lang.org/docs/language-reference/abilities-and-ability-handlers/), Elm called them [commands](https://package.elm-lang.org/packages/elm/core/latest/Platform.Cmd), JS-land seems to call them [actions](https://redux.js.org/faq/actions).

```yaml
# Defines increment ability that MUST be asserted
# on the special `effect:system` entity.
concept!: &increment
	description: Command to increment
	with:
  	subject:
  		the: tonk.xzy.command/subject
  		as: entity
```

Regardless of the name, the general idea is that it's like a message on `stdin` or a request to your HTTP route that causes the system to react to it.

> [!important]
>
> The entity for these concepts is the special `effect:system`. Because every ability targets the same entity, only one event at a time can be in flight, which is also the reason this is a static entity and not, say, a static attribute (an attribute would let any number of events coexist).

When an ability is submitted to a transaction via commit, the system executes the relevant effects, which assert concepts that translate into facts added to the transaction being committed. Those new facts may cause more effects to execute, which the system does until a [fixed point](https://en.wikipedia.org/wiki/Fixed_point_(mathematics)) is reached. Then the whole transaction is committed, which causes all the views to update through existing subscription pipelines.

```yaml

# defines behavior of counter caused by increment action
effect!:
  description: Effect increments counter on increment command
	# asserts counter concept
  assert!: counter
	when:
	  # Counter exists
    - assert: counter
    	where:
        this: ?this
        count: ?last-count
        
    - assert: increment
    	where:
    		this: effect:system
    		subject: ?this

    # Derive count by incrementing last count by 1
    - assert: +
    		of: ?last-count
        with: 1
        is: ?count
```

The rule above basically says it will assert `counter` when the listed premises hold. Concretely, when there is a counter with `?last-count` and an `increment` where the `?this` counter is the `subject`, and where `?count = ?last-count + 1`, the effect asserts `counter: { this: ?this, count: ?count }`. The notation could be improved (these are sketches I'm considering, not the form we'd ship):

```yaml
effect!:
  description: Effect increments counter on increment command
	# asserts counter concept
  assert!: counter
	when:
	  # Counter count is one less than new count
    - assert: counter
    	where:
        this: ?this
        count: ?count - 1

    - assert: increment
    	where:
    		this: effect:system
    		subject: ?this
```

Or perhaps something like this

```yaml
effect!:
  description: Effect increments counter on increment command
	# asserts counter concept
  assert!: counter
	when:
	  # Counter count is one less than new count
    - assert: counter
    	where:
        this: ?this
        count: ?count

    - assert: increment
    	where:
    		this: effect:system
    		subject: ?this
  then:
  	this: ?this
  	count: ?count + 1
```

Either form would still expand into the current notation; both are sugar that we could add later, once the system itself is working.

With this sketch you'll be able to cause that effect by asserting increment

```yaml
# invoke increment on counter
increment!:
	this: effect:system
	subject: ?counter
```



> [!note]
>
> The reason we have this special `effect:system` entity is that anything you assert on it doesn't stick around, it doesn't even make it into storage. You can imagine a built-in effect that retracts anything asserted on that entity. In other words it's like an event: ephemeral, available for a single cycle.



### Rules

Effects are a constrained variant of [inductive rules as per the Dedalus paper](https://www.neilconway.org/docs/dedalus_dl2.pdf). Over the weekend I ended up writing a patch to add [an `InductiveRule` variant to dialog](https://github.com/dialog-db/dialog-db/pull/339/changes). Before I go into the difference between effects and inductive rules, let me try to build up a mental model of what rules are, and what the difference is between deductive and inductive rules in dialog.

#### Deductive

I think it helps to think of dialog concepts as tables in a relational database. It's not a perfect analogy: in a relational database tables are the lowest-level primitive, you don't have table columns as a separate thing, and if you did that would probably be roughly what a fact is in dialog. I'm digressing, but another primitive of a relational database is a view, which lets you project a subset of a table, map the data, or even join across tables into a **derived** table-like thing you can query but not insert into, because the mapping can be lossy. That is basically what deductive rules are in dialog: they describe how a concept can be realized from facts.

> [!note]
>
> Actually concepts are themselves more like live views in a relational database, where facts are more like tables (but you only get three columns). A concept is like a view that selects over a union, and when you define a deductive rule you alter that view by adding a member to the union.

```yaml
concept!: &person
  description: A person
  with:
    first-name:
      description: First name
      the: xyz.tonk.person/first-name
      as: text
    last-name:
      description: Last name
      the: xyz.tonk.person/last-name
      as: text

concept!: &full-name
  description: Entity that has a full name
  with:
    full-name:
      description: Full name
      the: xyz.tonk.person/full-name
      as: text

rule!:
  description: Derives a person's full name
  assert: full-name
  when:
    # Person we're deriving the full name for
    - assert: person
      where:
        this: ?this
        first-name: ?first-name
        last-name: ?last-name

    # ?spaced = ?first-name + " "
    - assert: text/concatenate
      where:
        first: ?first-name
        second: " "
        is: ?spaced

    # ?full-name = ?spaced + ?last-name
    - assert: text/concatenate
      where:
        first: ?spaced
        second: ?last-name
        is: ?full-name
```

> [!important]
>
> Deductive rules run at query time and derived concepts are just deductions returned as query results, nothing is mutated or stored.

#### Inductive

Inductive rules are more like triggers in a relational database, which insert or delete rows in tables and, importantly, run as part of a transaction. Unlike triggers, however, inductive rules are defined just the same as deductive rules. Here is the rule above redefined as an inductive one:

```yaml
rule!:
  description: Derives a person's full name
  assert!: full-name # 👈 Exclamation mark is the only difference
  when:
    - assert: person
      where:
        this: ?this
        first-name: ?first-name
        last-name: ?last-name

    - assert: text/concatenate
      where:
        first: ?first-name
        second: " "
        is: ?spaced

    - assert: text/concatenate
      where:
        first: ?spaced
        second: ?last-name
        is: ?full-name
```

So the only difference is you write `assert!: full-name` instead of `assert: full-name`, where the `!` suffix indicates that mutation takes place, mirroring how queries and assertions in our notation already work. Behaviorally, deductive rules run at query time and the deduced concepts are returned as query results without ever touching storage. Inductive rules run at transaction time and the deduced concepts are added to the transaction and persisted alongside whatever else was committed.

> [!important]
> Inductive rules are run by the transactor on commit and incorporate derived concepts into the transaction, which means they cause a state change.

### Effects

Ok, so we're almost ready to talk about how effects differ from inductive rules. Inductive rules are a very elegant idea, however the logical model implies executing every single inductive rule in the system on every change, which can be suboptimal. To avoid running every inductive rule we can keep a reverse index of the premises each rule has, so for every fact we can figure out which rules will be affected and only run those. Because we store rules also as facts, and because in dialog you can query in either direction, we already have everything we need for this; we just run only the rules that are relevant.

However there is still a complication. When we pull changes from a remote, we splice our local tree onto the remote and defer replicating subtrees that don't overlap with our local one. This means we can't just iterate over every fact that has changed and run the effects that have them in premises, because we never see most of those facts. So either we give up on partial on-demand replication, or we end up in a system that isn't deterministic.

Consider a social media follow graph and a `follow-suggestion` derived from it: if you follow someone who follows someone else, suggest that other person as someone you might want to follow.

```yaml
concept!: &follow
  description: A person you follow
  with:
    follow:
      description: The person being followed
      the: xyz.tonk.connection/follow
      as: entity

concept!: &follow-suggestion
  description: A person the system suggests you might want to follow
  with:
    suggestion:
      description: The suggested person
      the: xyz.tonk.connection/suggestion
      as: entity

rule!:
  description: Suggest follows-of-follows
  assert!: follow-suggestion
  when:
    - assert: follow
      where:
        this: ?this
        follow: ?bridge

    - assert: follow
      where:
        this: ?bridge
        follow: ?suggestion
```

Now consider two scenarios. In the first, Alice asserts on her replica

```yaml
follow!:
  this: did:key:zAlice
  follow: did:key:zBob
```

and Bob, concurrently on his replica, asserts

```yaml
follow!:
  this: did:key:zBob
  follow: did:key:zCarol
```

When Alice and Bob later pull from each other, the rule sees both edges arriving as part of an integrated upstream tree, neither was asserted locally during the pull, so the rule has no commit to react to and no `follow-suggestion` is derived on either side.

In the second scenario, Bob first pulls from Alice and *then* asserts his edge locally. Now Bob's commit triggers the rule, both edges are visible at commit time, and `did:key:zCarol` shows up as a suggestion for Alice. Same data, different ordering, different derived state. That's the determinism problem in concrete terms.

> [!note]
>
> One way out of this would be to use the local-only diff as a trigger after every pull. We already splice local changes on top of the pulled tree, so we can walk just those facts (no upstream subtrees we didn't replicate), feed them to the inductive-rule evaluator as the dirty set, and commit anything it derives as a follow-up change on top. Both peers would converge on the same suggestions regardless of who pulled first. We're not doing this in V1, but it's worth noting as an option for later: it preserves partial replication and keeps the recovery story local-only.

However we can constrain things so that no matter what you pulled, no inductive rule will be affected, which sidesteps the problem. That's precisely what effects are, and why we have this `effect:system` entity. As I already mentioned, any assertions on `effect:system` get retracted in the same transaction, and all effects must have a premise that checks for an ability on `effect:system`. Therefore effects can only be triggered on the site they originate at, and when we pull we know there will be nothing upstream that can trigger an effect _(because the premise with an ability will produce no match)_.

While I really wish we had complete inductive-rule support, I do think going with effects is a very practical solution. It covers something like 80% of cases in general, and effectively 100% of the UI cases, since UI events always originate and get handled locally.

### Actor Model

I've often speculated that you should be able to express the actor model with dialog and inductive rules. Only now did I realize that the effects described above, as a contained version of inductive rules, can be slightly generalized in that direction while still maintaining partial on-demand replication of the system.

The shift is fairly minimal: instead of the special `effect:system` entity, you address a recipient's inbox directly with a `message` concept. The recipient's entity URI is the constant in the rule's premises, and the same property that makes effects cheap on pull (a known entity URI ⇒ bounded key-range scan) carries over: we only have to look at facts targeting known recipient entities, not everything that arrived in the upstream tree.

```yaml
concept!: &message
  description: A message sent to a recipient
  with:
    sender:
      description: Entity of the sender's inbox
      the: xyz.tonk.message/sender
      as: entity
    payload:
      description: Message payload
      the: xyz.tonk.message/payload
      as: text

rule!: &echo
  description: Receives a message and responds back to the sender
  assert!: message
  when:
    # Incoming message addressed to us; the sender's URI is the
    # `this` of the message we're going to produce in response.
    - assert: message
      where:
        this: did:key:zRecipientInbox
        sender: ?this
        payload: ?incoming

    # Build the reply payload by prefixing the incoming one with
    # "echo ".
    - assert: text/concatenate
      where:
        first: "echo "
        second: ?incoming
        is: ?payload

    # Our inbox is the sender of the reply.
    - assert: ==
      where:
        of: ?sender
        is: did:key:zRecipientInbox
```

Ok, so what's going on up there? We define a `message` concept and an inductive rule that produces a response message whenever an incoming message targets our recipient entity.

The generalization here is that we don't need a special `effect:system` entity, we just need a constant entity in the premises, which lets us narrow down affected rules significantly. This is something we can easily analyze at rule compilation, and even enforce.

> [!note]
>
> Unlike effects, which didn't require running inductive rules on pull at all, here we do need to. Although this becomes a much more bounded problem: it's just a query like
>
> ```yaml
> message:
>   this: did:key:zRecipientInbox
> ```
>
> And if there are any (new) messages, we fire the rules that have a corresponding premise.

> [!caution]
>
> It also needs to be flagged that we'd need a way to retract, or somehow mark, messages that have already been processed. This isn't particularly difficult, we just need to figure out a nice interface for doing so.

There's something interesting here that I want to call out, though I'll try not to oversell it. The conventional actor model is shared-nothing: each actor owns its state, and messages are the only way to interact, which means every cross-actor read has to be encoded as a request/response message exchange. That's the price of isolation. What's described above is closer to stored message-passing over a shared database: the message is just a fact, the handler is a rule, and the handler can join across the message and any other facts in the same query. You keep the addressable-mailbox affordance but skip the marshaling tax. I don't think this is "actors but better"; it's a different point in the design space that happens to share some surface features. The actor comparison is more useful as a lens than as a claim.

It's also interesting to imagine extending the concept of mailboxes so that agents react to messages in them. Cron jobs fit the same model too: the scheduler just lands a message into a mailbox on schedule, and the effects on the receiving side take care of the rest. No special "cron rule" type, the cron is just whatever is dropping the message.

> [!note]
>
> Another thing that falls out of this naturally is authorization. A rule can require, alongside the message premise, an additional premise that the message is signed by an actor the recipient has authorized. An unauthorized sender can still drop a message, but the effect simply doesn't fire until the authorization premise is also satisfied. The neat part is that the order doesn't matter: authorization can be asserted before or after the message lands, things happen the moment all the conditions are met. That's the beauty of the declarative model: you don't have to think about "did the message arrive before or after authorization?", the rule just describes what has to hold for it to fire.
