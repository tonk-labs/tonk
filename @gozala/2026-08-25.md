# Finding an account by email address

Inviting someone by email needs the `did:key` behind the address, and nothing exposed that direction. The mapping was already sitting there as `customer.email → customer.did` in the access service's control db, written at `/customer/enroll`, unindexed and unreachable. [#767](https://github.com/tonk-labs/tonk/pull/767).

Two databases hold an email-to-DID mapping and the choice between them is not arbitrary. The account service has `accounts.email → accounts.root_did`, the passkey registry. The access service has the customer row, and the two DIDs are the same value. The access service wins on two counts: it is already the `did:web` host, so the name resolves to the same worker with no new deployment, and it is the only side that knows whether an address was *confirmed*. `customer.status` distinguishes an address someone typed from one they proved control of. The `accounts` table has no equivalent, so a lookup rooted there could not tell those apart, and that distinction is the most useful thing the endpoint says.

## Encoding the address instead of hashing it

I started from `did:web:xyz.tonk:member:{blake3(email)}` and talked myself out of it. The obscurity is thin: the input space is enumerable, so anyone with a wordlist can hash it and probe. And it costs a stored hash column, which D1 cannot backfill in SQL because it has no blake3, plus a nullable column where a row that missed the backfill is silently unfindable rather than loudly broken.

So the address goes in the DID. Storacha's [did:mailto](https://github.com/storacha/specs/blob/main/did-mailto.md) already fixed the split, domain first then the local part percent-encoded, and using that shape under our own `did:web` name gets ordinary resolution for free:

```
did:web:tonk.network:customer:example.com:jsmith
  → GET /customer/example.com/jsmith/did.json
```

The lookup becomes `WHERE email = ?` against an index, and the migration is a normalize plus a `CREATE UNIQUE INDEX`. The tradeoff is real and worth naming before these DIDs start landing in stored UCAN chains: the address is plaintext wherever one gets written down, a delegation, a log line, a browser history entry.

> [!caution]
> `did:web` resolution percent-decodes each path segment, and the local part's own encoding is that same encoding, so `tag%2Balice` arrives at the worker as `tag+alice`. Legal in a path segment, means space only in a query string. The handler has to read the raw segment; anything form-decoding on the way turns that `+` into a space and the lookup misses.

Two encodings are correct but do not resolve: an `@` inside a local part, and a `/`, which decodes back into a path separator and splits the route. Both fail closed with a 404 rather than reaching the wrong customer, and both are vanishingly rare, so the tests pin the behaviour rather than chase it.

## Status codes carry the registration state

200 active, 202 enrolled but unconfirmed, 410 suspended, 404 unknown. 202 rather than 200 for a pending customer because the DID is real and worth returning, but a caller about to act on it should know the confirmation has not happened. 410 rather than 403 or 404 for a suspension: the resource existed and is not currently available, which is what a suspension is, and it does not read as a permission failure on the caller's part. The document still comes back with `deactivated: true`, since a suspension is reversible and discarding the key mapping would make every caller re-resolve when it lifts.

## The two services disagreed about what an address is

The account service normalizes to `trim().to_lowercase()` on the way in. The access service only trimmed. That did not matter while nothing looked an address up, and it matters completely once the address *is* the key: `Alice@x.com` and `alice@x.com` would be different rows and different URLs.

`customer.email` stores the normalized form now, one shared helper so the writer and the lookup cannot drift, and a unique index because one address holds one customer. The migration normalizes existing rows and drops the duplicates that can create, keeping the highest `rowid`, which is fine because this service has no production deployment yet. It also fixes a latent thing: the re-enroll comparison is normalized against normalized, so re-enrolling with different casing no longer triggers a pointless email update write.

The cost is that the casing someone typed is gone. No delivery impact, no mail server treats the local part as case-sensitive in practice, but outgoing `To:` headers read lowercase from here on.

## Cache and rate limiting compose

A cached answer never reaches the worker, so it never counts against the limit. That is the right division: the cache absorbs repeat lookups of one address, and what reaches the limiter is closer to the distinct-address rate, which is the signal enumeration actually produces. So the limit is keyed by client IP, not by address, since a budget that reset per address would not constrain walking a list of them.

Only a settled answer is cacheable. A 202 and a 404 carry `no-store` and are stored nowhere, because both are about to change and the change is what a caller polling an address is waiting on. Setting the header matters as much as declining to store it: the header is what browsers and intermediaries obey, and my first cut stored only the 200 while telling everyone downstream to hold the 202 for a minute.

> [!note]
> The 410 has no end-to-end test. Nothing in the codebase writes `Suspended` yet, there is no admin suspension path, so the harness cannot produce one. Covered at the store level where the status can be written directly.

## Two bugs the tests found, both test-only

The native test server built its host from `req.uri().authority()`, which is `None` for the origin-form request line every real client sends, so it minted `did:web::customer:...`. The deployed worker reads `req.url()`, which reassembles authority from the `Host` header, so the served `/.well-known/did.json` was always right and I briefly claimed otherwise before checking staging.

And the test harness matched captured activation emails by verbatim address, which stopped finding them the moment enrollment normalized before sending. The same pattern is still in the e2e helper at `account_flow.rs:136`; harmless while every e2e address is lowercase, so it goes in a follow-up rather than restarting a green CI run.

E2e failed once on a browser wait timeout and passed on rerun, same code. Load, not the change.

## Email-first sign in, and a refusal that says whether to wait

The account panel forks before it knows anything: Create account or Log in, and you pick. Picking wrong is expensive in one direction. "Create account" with an address that already has one runs the whole WebAuthn creation ceremony, completes it, and only then hits `EMAIL_TAKEN` from `POST /accounts`, leaving an orphan passkey in the authenticator. Now that an address resolves to a `did:key`, the panel can ask first and route: 404 creates, 200 signs in, 202 signs in and lands on the waiting screen.

`preflight_account` was written for exactly this. Its doc comment says "reject a known uniqueness conflict before the browser creates or evaluates a passkey", it is routed, handled and tested, and it has zero callers in tonk-ui. Its companion `request_account_code` has exactly one occurrence in the tree: its own definition. Both need an emailed code, which is the friction the lookup does not have, so they go.

## Nothing should poll

The flow ends on "waiting for email confirmation" and that screen has to notice confirmation, including when the link is opened on a phone. I was heading toward an SW poll while `AwaitingActivation`. Irakli's answer was better: we already sync the account space, and while the customer is unactivated every one of those syncs is refused with a reason. Activation is the refusal clearing.

That also happens to be what `c939714f` argued when it deleted the status probe: "a suspension reaches the client the way it should: the access service denies service and says why in the refusal."

## A refusal is not a proof failure

The three refusals differed only inside a formatted predicate string, so telling "awaits email activation" from "is suspended" meant substring-matching prose. Both `provisioning.rs` and `error.rs` document, twice, that there is deliberately no code table beside the predicate, and both name a first-class upstream variant as the upgrade path. So: [dialog#470](https://github.com/dialog-db/dialog-db/pull/470).

First cut put the registration states straight into the variant, `AwaitingActivation | Suspended | Unprovisioned`. Irakli caught it: that is one service's vocabulary in a generic UCAN crate, and every other dialog consumer would inherit words that mean nothing to them.

The redesign is smaller and better. `Declined { recourse, reason }`, where `reason` is opaque, the responder's own words, carrying the same warning `Rejection::Unclassified` already has about matching on its text. The only structured part is `Recourse::{Retry, None}`, which answers the one question that generalises: is the same request worth making again. An unconfirmed address is `Retry` because opening the link is what clears it; a suspension and an unprovisioned subject are `None`.

> [!note]
> The variant mirrors no `CheckFailed` case, unlike every neighbour in that enum. No chain check produced it. That is also why it does not belong under `PolicyViolation`, which is specifically a delegation's policy rejecting the arguments.

A consequence worth stating: the client can no longer tell suspended from unprovisioned, only whether to keep waiting. That is genuinely all this flow needs, and it kept tonk's lifecycle out of dialog.

## Reading a fact instead of fetching one

`load_activation_notice` runs once per dashboard render, fetches `/api/customer`, and matches `state["status"].as_str()` against string literals. So it is a snapshot and it is stringly typed: confirm the email in another tab and this one still says "waiting" until you reload, and a typo in one of those literals compiles fine and silently never matches.

`AccountCustomer` is a real fact on profile main, so the row subscribes to it instead. Activation writes the fact, sync carries it, the subscription fires, every tab repaints. No reload, no page-side timer.

> [!caution]
> A concept resolves only when every field is present, so a query over `AccountCustomer` would miss exactly the awaiting-activation account if `provider` were absent. It is not: registration writes it as an empty string and `provider()` filters that, which is what keeps the pending row readable. Worth knowing before adding a field to one of these.

Also: `data-mode="blocked"` (set when the account service is unreachable) matches no panel in `set_mode`'s list and has no CSS rule, so it hides every panel and leaves a bare error string. Same state machine, fixing it while I am in here.

## The custody stack, live

Flattened the five custody PRs into #766 and merged: seeds sealed to the account's X25519 key, joins durable to whichever account the device has, rotation at sign-in, the worker asking the page for an assertion when custody needs a key the record does not hold.

Walking it live in Chrome found the bug the tests had not: rotation ran exactly once, inside the link call, and deferred because the key fact was not published yet, because hydration was blocked on my unopened activation email. Nothing retried, so my first spot stayed sealed to an onboarding account forever. Rotation now reads the recipient from the root record when the fact is absent and the worker's boot chores re-run it, so a stranded device heals on its next start. Watched the heal happen in the same browser session, which is a satisfying way to close a bug.

## Passkey ambushes

Every passkey prompt today arrived with zero context, and the worst one looped: the queued custody publish fired a discoverable assertion on /account load, my localhost passkey graveyard offered a stale credential, the derived custody space mismatched, the entry re-queued, and the next visit ambushed me again. Follow-ups: the publish became an offered button with the assertion pinned to the recorded credential (#772), the dashboard follows activation without a reload (#773), retirement now retracts the onboarding account's leftover facts (#774), and the CLI seals its spaces' seeds under account custody with rotation at login (#775).

The meta lesson is written down as its own workstream: prompts, publishes, and local-only states all happen silently here, and the communication pass should be one coherent design, not patches.

## The endless loader

The eternal "loading" spinner turned out to be the SW shell cache storing the SPA fallback, index.html with a 200, under a hashed asset URL during a rebuild window. Subresource integrity then correctly blocks HTML pretending to be JS, and only a background revalidation heals the entry, which is why refresh usually fixed it. First instinct was to drop SRI (#777), which was wrong and got closed; the real fix (#778) teaches the cache that an HTML answer for an asset path is a miss, not content.

## In flight

CLI gets a real onboarding account, same envelope and constants as the worker's, so unlinked spaces are custodied from birth and sign-in is an account rotation, not an adoption. The rotation core moved into tonk-schema as shared code the worker and CLI both call, and the word accreditation is being evicted for rotation throughout.

## Spaces stay local until someone can serve them

Creating a space on a device whose account has not confirmed its email wired it to a remote the access service refuses, so every sync answered `subject is provisioned by an active customer (the subject is not provisioned)`, and the account never got registered either. [#771](https://github.com/tonk-labs/tonk/pull/771).

The gate was reading the wrong thing. `require_account` asks whether a provider record is attached, and a device has an account from first boot, so "an account exists" says nothing about whether a space will be served. What matters is the customer's registration, and that now lives as `AccountCustomer` facts on profile main rather than in a device-local credential blob that only refreshed when you opened `/account`.

The provider address comes from the service now. Three paths derived it independently: the create wizard's `<tonk-default-remote auto>` prefill, the signed account descriptor, and `share.rs` asking the portal bridge for the guest's origin. The access service names it in the registration receipt instead, and only at activation, never at enrollment. That last part is what makes the state machine exact: an unactivated customer gets neither service nor provisioning, so withholding the address until activation makes "has a provider" mean "finished registering".

| fact | meaning |
|---|---|
| no fact | never registered |
| email, no provider | enrolled, awaiting the link |
| provider | served |
| `Suspended` | terminal |

> [!caution]
> Every attach path has to provision first. `enable_sync_inner` never called `/provider/add` at all, which is why opting a local-only space into sync reproduced the same 403: it wired an upstream to a subject nobody had provisioned. Best effort rather than fatal, though, since a remote is not necessarily our access service and refusing the attach would make a self-hosted endpoint unattachable.

## The account gate on create was already gone

Went to convert `POST /api/spaces` into a transient command and found staging had deleted the account gate, the replay, and `PendingIntent` independently while I was working. The endpoint was left with seven test callers and no production ones. [#776](https://github.com/tonk-labs/tonk/pull/776) retires it, along with its pinned `route_table.rs` entry.

Converting the tests surfaced two behaviours the endpoint had been hiding, both worth knowing beyond the tests. The remote attaches *after* the handler navigates, deliberately, so navigation does not wait on the network; the endpoint attached before answering, so a caller could create-with-remote and push immediately, and that same push now races the attach and answers `SYNC_UNAVAILABLE`. And creating a space navigates into it, so a test that then read the account panel was on the wrong page.

## Waiting on notifications, not clocks

The converted tests polled. Irakli's point: these states are subscribable, so wait on the notification. `POST .../query` with `Accept: text/event-stream` gives a snapshot then live updates, so the test opens one in the page and resolves on the first frame that matches. The remaining timeout is a deadline so a fact that never arrives fails with a message; nothing re-checks on a clock.

The wire queries derive from the concepts (`remote_concept_wire_query`, `replica_concept_wire_query`) the way `named_concept_wire_query` already did, so a shape change reaches subscribers without editing hand-rolled JSON.

## A refusal that says what to do about it

`resolve_remote_url` only sees the repository, so every unsynced spot read as `not-synced`, "attach a remote". That is right only when there is a provider to attach to. Three new classes split it by the registration state: `needs-account` (nobody registered), `needs-activation` (enrolled, link unopened), `suspended` (terminal). The share dialog offers registration for the first two rather than an attach that would fail.

> [!note]
> The bar is a sealed guest with no ceremony of its own, so confirming hands off to `/account` and you share again afterwards. Inline registration in the dialog is the version worth building, and it is a bigger piece: the clipboard write cannot survive a WebAuthn ceremony (measured: a pending promise holds fine for 45s, but a post-ceremony write costs a second permission prompt because the ceremony leaves no transient activation).

Still in flight: the native build now warns those variants are never constructed, since `explain_refusal` is wasm-gated, and `it_refuses_to_mint_without_a_remote` fails with `needs-account` against `not-synced`, which is the refinement working and the test encoding the old answer.
