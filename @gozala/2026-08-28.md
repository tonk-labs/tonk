## Two Safari PRs

dialog [#473](https://github.com/dialog-db/dialog-db/pull/473) carries the wrapped X25519 archive. tonk [#806](https://github.com/tonk-labs/tonk/pull/806) takes the signature out of the onboarding KEK: on first boot the KEK is 32 random bytes sealed to the custodian's `did:key` with dialog's `SealedSecret`, stored beside the envelope as `KekMethod::Custodian`, and revealed through the custodian's agreement key on every later boot. Same custodian, same non-extractable handle, same `retire`; only the way the KEK is reached changed, from "sign a fixed message" to "agree with yourself via an ephemeral key", which every platform answers the same way.

Legacy envelopes keep opening where signing is deterministic and are resealed on the first open. Where it is not, `read` signs the old context twice, and if the two differ the envelope is treated as replaceable rather than corrupt: it never opened on that device, so nothing was ever delegated to its account.

> [!note]
> Randomized Ed25519 does not touch anything that verifies. Three Safari signatures of one message, all different, all verified by OpenSSL. Passkey and phrase custody derive their KEKs from the PRF output and Argon2id, so they were never exposed. The only casualty was code that treated a signature as a value it could recompute.

Verified in Safari against a build carrying both PRs: the Hub reads "link an account", `/api/profiles` is 200, the custodian and profile credentials store in the wrapped shape, the envelope and its 92-byte sealed KEK land beside them, and "create a new space" navigates into a new space twice in a row, the second time through `read` revealing the stored KEK.

dialog #473 merged and is tagged `tonk-2026-08-28`; #806 now pins it (staging was on 08-25b, so the bump also brings `AuthorizeError::Declined`, answered 403 in the access service, the same three lines the enroll branch carries).
