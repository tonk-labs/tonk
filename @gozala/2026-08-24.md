# Sealing a secret to a DID

The vault sketch from the 21st needs one primitive it did not have: wrapping a key for a profile that has published nothing yet. When a profile is delegated onto an account, the account has to hand it the vault key by leaving a wrapped copy somewhere. The profile has no channel to announce an encryption key on first, so the wrap has to work from the DID and nothing else. [dialog#463](https://github.com/dialog-db/dialog-db/pull/463).

That constraint picks the design on its own. The Ed25519 to X25519 birational map means the agreement public key is the Montgomery form of the signing public key, so anyone holding `did:key:z6Mk…` can compute it. I went looking for a way to avoid reusing the signing key, and there is not one that keeps this property.

- Independent X25519 keys: the profile has to publish it, which is the thing we cannot do.
- BIP39 into an HKDF split: clean key separation, but HKDF is one way, so the DID tells you nothing about the sibling.
- BIP32 public derivation: needs an xpub, which is the public key *plus a chain code*, and a `did:key` carries no chain code. Ed25519 forbids it outright anyway, clamping breaks the homomorphism, which is why SLIP-0010 is hardened-only for this curve.

> [!note]
> I had BIP39 and BIP32 conflated. BIP39 is just mnemonic to seed bytes, no derivation in it at all. And even the BIP32 property is narrower than "derive the public key from the public key": it is watch-only derivation of *more keys on the same curve*, and it never crosses algorithms.

So it is derivation, and the cost is real: the agreement key cannot rotate without rotating the DID. That lands badly given rotation already hurts here. The escape hatch, if it comes to it, is letting a profile publish a rotated agreement key in the delegation it already sends, with derivation as the fallback.

## The browser cannot derive at all

WebCrypto has no Ed25519 to X25519 conversion, and a non-extractable Ed25519 key never gives its seed back. So the agreement key can only be made in the one moment the seed exists.

```
generate()
  → generateKey(Ed25519, extractable: true)
  → export seed
  → import both, non-extractable:
      Ed25519  usages: ["sign"]
      X25519   usages: ["deriveBits"]
```

The extractable original is dropped and the seed never leaves that function. Both keys end up non-extractable, and both get archived, because the seed is unrecoverable afterwards. `KeyExport::NonExtractable` grows an `agreement` component, carried as an extra property so an export still reads as a plain `{ privateKey, publicKey }`. Native derives on demand and stores nothing extra, so its credential bytes are unchanged.

## conceal and reveal

First cut exposed `diffie_hellman` returning `[u8; 32]`, which is the shape that invites every caller to use raw DH output as a key. It is not one: X25519 output is not uniform. With no callers yet there was no reason to keep the knob.

```rust
let sealed = profile_did.secret(VAULT).conceal(&vault_key).await?;
let vault_key = signer.secret(VAULT).reveal(&sealed).await?;
```

A verifier yields a `Seal`, which only conceals. A signer yields a `Secret`, which also reveals. Decrypting with a public key is a compile error rather than a runtime one. The X25519 types and `diffie_hellman` are crate-private now, so raw agreement output is unreachable.

Each `conceal` mints a fresh ephemeral pair, so the sender's long-term key never performs the agreement and a later compromise of it does not open past wraps. `Context` is a required argument, not a doc comment, which is the domain separation that makes the shared-scalar reuse defensible. The recipient's DID is the AEAD's associated data, so a wrap cannot be lifted from one vault row and replayed against another.

> [!caution]
> `x25519_dalek` does not reject low-order peer keys, it just returns an all-zero shared secret, where WebCrypto's `deriveBits` rejects them. Same hostile input, opposite behaviour per platform. Native errors now too.

## Testing across a boundary that does not exist

Native runs AES-GCM and HKDF through RustCrypto, the browser through WebCrypto. They cannot share a process, so "do these agree" is not directly assertable. Sealed a fixture with RustCrypto, checked it in, and the browser suite opens it. Same for the derived agreement key.

The one I would have skipped and been wrong to: the web export is a `CryptoKeyPair` dictionary with the agreement pair hung off it by `Reflect::set`, and whether **structured clone** keeps that property is a browser behaviour, not something reading the code settles. If it dropped it, every reload would give a signer that still signs and can no longer open anything sealed to its DID, with nothing erroring. Two tests now save a credential to real IndexedDb, seal to its DID, load it back in a later session, and reveal.

> [!note]
> The seal layer has no consumer yet. The vault wrapping from the 21st is where the ephemeral-sender assumption actually has to hold, and the API is shaped so static-static is unrepresentable, but nothing has exercised that against a real vault.

# Devices are delegations

Picking up where yesterday left off: the account panel's device list and the `devices` table under it. The table is not bookkeeping, it is a gate. `authorize_device_ceremony` looks the row up, refuses a non-`active` one, and then requires `proofs[0] == device.delegation_cid`. That last check pins an invocation to one exact delegation, which is stricter than revocation and no index can express.

Both are workarounds for revocations that did not work. They do now, so both go.

A device already is its `account → profile` delegation. That grant is a powerline, subject-open, so any authorized device can prove for the account subject, which is exactly the authority withdrawing an account-issued grant requires. So revoking another device never needed a passkey-signed artifact handed in from outside. `mint_delegated_revocation` was already there, `revoke_invite.rs` already used it, and `account_devices.rs` only ever called the self-revocation variant, falling through to "supply your own" for every other case.

`prf` answers may this principal invoke at all, `pth` answers why may they revoke *this*. Our own link for the first, the target's for the second, rebuilt from retained `dialog.ucan/*` facts rather than a stored copy.

## Facts on the delegation, or facts on the thing

Two pieces of authority wanted to be queryable, and they do not want the same home.

Device links have no other home. `profile.this()` appears exactly once in the whole schema, as a *field* on `Replica`, never as an entity. So the delegation's own entity, which dialog keys by blob hash and decorates with issuer and audience, is the only keying there is. It has the property you want too: revoke the delegation and the row goes with it, so a device cannot linger in a list after losing authority.

Space founding does have another home, and I nearly put it in the wrong one. The account directory already keys `Space`, `SpaceName`, and `SpaceLocal` by the space DID, and the Hub renders that row. Hanging `foundedAt` off the ownership delegation would have added a third entity keying and made every Hub row join through `dialog.ucan/subject` to show a creation date. It is a stamp on the directory entity, like `SpaceName`.

> [!note]
> `meta` is not decomposed into facts. `field_artifacts` emits audience, subject, issuer, command, expiration, notBefore, and stops, so metadata rides inside the signed envelope and is invisible to queries. Both are worth having: `meta` is the issuer's signed statement and travels, facts are the local projection. A fact can be rebuilt from the envelope, `meta` cannot be rebuilt from facts.

## A checker that answers no to everything

`InvocationChain::verify` checks every link's revocation status, and the `Revocations: RevocationChecker` bound makes a checker mandatory. Enforcement is not opt-in. What is optional is whether the checker knows anything: `UnverifiedRevocations::query` returns `Ok(None)` unconditionally.

Access-service registration and deletion both passed it, so a revoked device could still enroll or activate. `IndexedRevocations` was sitting in the same crate, wired into the presign path and nowhere else. Registration threads it now, bound per request off `REVOCATIONS_KV` the way presign does.

# The device registry is the account DB now

Picked up [#745](https://github.com/tonk-labs/tonk/pull/745) from the handoff and finished the retirement it stalled on. The account service's `devices` table is out of the loop: list, register, and revoke all go through the account space, which already syncs to every device.

The handoff's `mark_dirty` hypothesis was half right. The push scheduling was missing, but the real gap was that nobody asserted a `DeviceLink` fact outside the onboarding path at all. The rule that fixes it: ==whoever mints a device grant describes it==, in the same branch the chain is retained into. The approving page describes the device it just authorized, the account sweep describes the signing browser's own link, onboarding describes the local grant. Both lists (the panel's and `tonk account devices`) are one query over local facts, so they work offline and agree across devices.

Revocation got simpler for the same reason. The CLI revokes under its own powerline now: mint, publish to every access service, retract the rows. The browser handoff, the polling loop, the passkey ceremony, and the `signed_post` apparatus are gone. The UI stops gating "Remove access" on stored path evidence, since the worker rebuilds the path from retained facts.

Three bugs on the way there, each its own lesson:

- `grant_device` claimed re-minting was idempotent. It is not: every delegation carries a fresh nonce, so each pre-account space creation quietly added another grant and another row. It proves from retained facts first now.
- `retain` returns only what it newly wrote, and saving a grant to the access store retains the chain as a side effect, so describing after saving silently described nothing. The entity is derived from the certificate digest the way dialog derives it, and an existing row wins.
- A fresh sign-up renders its dashboard before the account ever hydrates (the link runs while the customer is unactivated), so the sweep hadn't described anything when the panel's one render happened. The list self-describes on the way through: local, idempotent, deterministic.

> [!note]
> Local wasm tests work after all. The SIGKILL was chromedriver 149 against Chrome 151; a matching driver from chrome-for-testing plus `CHROMEDRIVER=` runs the whole wasm suite in seconds, and the e2e suite too. That turned every remaining bug from a 25-minute CI cycle into a local loop.

> [!caution]

All three were stale expectations (404 for an unknown repo where absence is now the empty set, spaces delegating to the device key where they now delegate to the onboarding account, and a doubly-prefixed DID built from a name that is already one).

Local runs are fully green, native and wasm workspaces, clippy, and 15/15 e2e. Merging to staging once CI confirms.

## The e2e hang, for real this time

CI kept failing on `tonk account devices` after another device pushed to the account. I called it read-ahead claims (dialog #466) on mechanism plausibility, and the deterministic repro still stalled 40.00s per round against that tag. Lesson taken: nothing is "the fix" until the repro passes.

What found it was an in-memory step recorder in dialog (stderr breadcrumbs perturbed timing enough to make the stall vanish). The trail: `auth: walk start` over the access branch, a node not local, `networked: remote get start`, then `auth: resolve start reach=false`, a nested walk over the same branch, `cache: waiting on in-flight demand`. The outer fetch holds the node cache's single-flight claim while it waits for its proof; the proof is a reach-less walk over the same tree that needs the same node and joins that claim. A wait cycle through a channel plus authorization recursion, no I/O, nothing dropped. My 10s and 30s bounds are what turned it into 40s.

The setup is that profile db `main` is the access branch (`ACCESS_BRANCH = "main"`) and tonk-cli's `ensure`/`mount` bare-pulled it. A bare pull adopts the other device's head by root, and hydrating the access branch needs a proof that needs the access branch. The worker already pulled it with `download()`; the CLI didn't.

Fixes: dialog #468 (Jack's, stacked on my #467) drops single-flight waiting altogether, so a miss fetches for itself and the inner proof resolves from local content or fails. Tagged `tonk-2026-08-24d`. On tonk, `hydrate` and `ensure` pull with `download()`. Verified separately: #468 alone turns the hang into a loud `Blob not found` on every sync (bounded, but never recovers); the download makes it not happen. Audited every pull in tonk: all profile-main pulls download, content spaces stay lazy because their fetches are proven from `main`, not from themselves.

> [!note]
> Regression tests: dialog `it_never_waits_on_its_own_fetch_when_the_access_head_ran_ahead_of_the_archive` (reset a device's access head to the account's pushed head, pull must complete in 30s; 30s fail on main, 0.01s fixed) and tonk-cli `it_lists_devices_promptly_after_another_device_pushed` with a 5s bound.

Answers to my own earlier questions: surelock is compile-time ordering for sync mutexes and would not have modeled this (async, no lock). "Make drop fail the read" already exists (`Fetch::drop` withdraws the claim); nothing was dropped here, the owner was alive and waiting on its waiter.

## Space admins, and why the commands moved

Item 5 started as roster plumbing and turned into a capability question. The revocation rule, precisely: dialog asks the checker per link with the candidates being the subject and the issuers above that link, so a sibling's revocation reaches nobody; but a delegated revocation is recorded under the subject it is proven for, and for a space that is the space itself, which is above every hop. Whoever can present a chain covering `/ucan/revoke` for the space can remove anyone, founder included. Invites were minted at `/`. So every member already could.

The fix is what a chain covers, not a role fact. Irakli's call: remap the storage commands under `/use` in dialog rather than bundle two attenuated chains per invite in tonk. dialog-db#469: `Use` is a level of the hierarchy (`Subject → Use → Memory | Archive`), effects name verb and resource (`/use/get/memory/cell`, `/use/put/archive/block`, `/use/delete/memory/cell`), `/use` is read+write, `/ucan` is outside it, `/void` is reserved and empty. HTTP verbs won over query/change because retract needed a name. The authorizer keeps the old spellings for deployed clients. One trap found on the way: with `Memory` demoted to a policy under `Subject`, the customer deposit would have silently become `/` plus a policy; making `Use` a real level is what keeps it `/use`.

On `feat/space-admins`: invites mint at `/use` (worker route, `tonk:invite`, CLI); invite proofs search at `/use`; the space still delegates `/` to its creator's account; `MemberRole::admin` with badge and CLI classification; the join retains the claimed chain into the space so a member's own hop is individually revocable; `POST /api/repository/{repo}/admins` mints a `/` chain to the member's account and retains it beside the invites; `POST .../members/{did}/revoke` proves the member's own hop, revokes it under the remover's `/` chain (space db first, creation prefix as fallback), and retracts the roster rows. Founder and self are refused as targets. Pinned to the #469 head until it merges and gets a tag. No UI yet.

> [!note]
> `it_installs_a_claim_without_copying_the_space` (web release) failed once at 45 of 47 nodes on a loaded runner and passed on rerun. Load-sensitive, not the pin.
