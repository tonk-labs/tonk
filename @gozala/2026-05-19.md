## Sandboxing iframes

Spent some time capturing design for `<tonk-portal>`, the untrusted-HTML counterpart to `<tonk-display>`. Artifacts on the branch get rendered inside a nested iframe pair: a host iframe with `sandbox="allow-scripts"` (no `allow-same-origin`, unique opaque origin) runs a fixed bootstrap, and inside it the bootstrap creates a guest iframe whose `srcdoc` is the artifact's HTML verbatim. The guest inherits the host iframe's opaque origin via `srcdoc`, so the two are same-origin to each other but both cross-origin to the top frame, which means the artifact's scripts can reach `parent.tonk` synchronously while the top frame stays isolated. The host iframe constructs a `MessageChannel` and posts `port2` up to the top frame, which serves SW-backed queries on the artifact's behalf.

Since `ReadableStream` is now transferable across all major browsers, `tonk.subscribe` can just hand one back instead of streaming framed envelopes over the port. The top frame wraps the SSE in a stream, posts it over the port, and when the guest stops reading (cancel, lock-release, or GC) cancellation propagates back and aborts the SSE. No abort envelope, no subscription map, no correlation IDs for streams. Plan lives at [`plan/tonk-portal.md`][plan].

### Per-artifact subdomains (v2 idea)

The big limitation of the `srcdoc` approach is that artifacts can't load subresources, images, stylesheets, fonts, the usual web stuff. A possible v2: register `tonk.xyz` with a wildcard DNS record so `{fingerprint}.artifact.tonk.xyz` resolves for every artifact, all routed to the same static page we serve. The page would register a Tonk service worker scoped to that subdomain, so each artifact gets its own real origin (storage isolated per fingerprint, normal `fetch` APIs available) without artifact authors having to ship their own worker. First load needs network, but after that the SW handles offline. Captured in the plan under "Possible v2: per-artifact subdomains".

## Layered dialog

We have accumulated whole bunch of code that works around various limitations in dialog, namely

1. Inability to query transaction without committing changes

   > Interactive playground really suffers from this, if we had this we'd be able to visualize transaction effects without having to execute and commit.

2. Inability to inject some facts without committing them, think environment variables or ephemeral state. I envied datomic's [`d/with`](https://docs.datomic.com/clojure/index.html#datomic.api/with) for a long time.

   > Can not recall context exactly but I remember wishing I could expose current revision so it could be queried. This is also an example of a thing that you simply can not commit into database because that would make it stale since commit create new revision which includes hash of the tree.

3. Composing multiple branches or branches across repos into a composite that you can query as if they were all merged.

   >  This is one of the things you can not really do with conventional databases, so exploring what it can enable seems really interesting

There are more gaps, about I list above three because solution to all of them is what I previously referred to as "layers". I like inviting analogy to layers in photoshop, just like there you can have multiple layers and see composite picture. You can toggle layers on and off and see what layer contributes what to the image. I think we can build something like this, although not sure how useful it will end up being in practice.

✨ Anyway all this to say these features are finally available on [`feat/query-layer`](https://github.com/dialog-db/dialog-db/pull/340) and tagged as [tonk-2026-05-19](https://github.com/dialog-db/dialog-db/releases/tag/tonk-2026-05-19) you can use it as follows

```rust
let vault = profile
		.repository("vault")
    .open()
    .perform(&operator)
    .await?;

let main = vault
    .branch("main")
    .open()
    .perform(&operator)
    .await?;

// Define a concept with typed attributes.
#[derive(Concept)]
struct Employee {
    this: Entity,
    name: employee::Name,
    role: employee::Role,
}


let layer = main
	// assert any concepts or facts
	.with(Employee {
        this: Entity::new()?,
        name: employee::Name("Alice".into()),
        role: employee::Role("Engineer".into()),
  })
	// join any other branch even from other repo
	.join(vault
      	.branch("other")
        .open()
        .perform(&operator)
        .await?
	);

// query composite
layer.select(Employee).perform(&operator).await;
```

Not going to show transaction example, but you basically can assert / retract and query as if those changes were committed.

## Tile Manager

The idea is a `<tonk-layout>` web component: a niri-style tiling window manager, written in Rust like `<tonk-concept>` and `<tonk-display>`, and registered the same way. It arranges tiles on an infinite horizontal scrollable strip of columns, where each column is a vertical stack of tiles. Every tile mounts a `<tonk-display>` pointed at a branch entity, so the manager itself only owns geometry and focus while the tiles render real data. Sizing is relative (viewport fractions, niri's preset column widths) so a layout restores correctly at any resolution.

The layout itself is just more data in the dialog database. Rather than a JSON blob, it's stored as normalized entities: `workspace`, `column`, and `tile` concepts, with children pointing upward at their parents and a float `order` field so a column or tile can be inserted between two others without renumbering anything. Because every write goes through `/evaluate` (which re-polls subscriptions on commit), the manager is reactive across tabs and devices for free, and per-attribute merge means two devices rearranging different parts of the strip merge cleanly. Continuous gestures like drag-resize update the DOM optimistically and debounce the write, so we don't commit on every pointer event.
