# June 7th

## Effects via dialog's capability system

Two days ago I sketched what command effects should feel like: assert a transient concept, have a handler react to it the way rules do, and lean on dialog's capability system. Today I built it.

The frame I keep coming back to is managed effects, in the Elm sense. There you do not perform IO inline; you *describe* the effect as a value and hand it to a managed runtime that performs it and feeds the result back in as data. That is exactly the split here. A command is a description, a fact you assert. The runtime, the reactor plus the provider, is the thing that actually performs it. The code that wants the effect never does the IO; it only asks for it, declaratively, the same way a `<button onclick=…>` only asks.

Algebraic effects are the other half of the same picture. There the program *performs* an operation without naming who handles it, and a separate handler, installed somewhere up the stack, interprets it. The operation and its interpretation are decoupled. Asserting a command is the operation; the `Provider<C>` is the handler that interprets it. What makes this version stricter than a plain effect handler is the capability layer: which handlers exist at all is gated, so an operation can only be performed if a provider for it has been delegated. The effect is not just decoupled from its handler, it is decoupled from any handler you are not authorized to reach.

### A command is a transient concept

A command is an ordinary concept that gets asserted *transiently*: it exists only for the commit that asserts it, fires its handler once, and leaves no durable trace. `CreateSpace` is just a concept with the fields the handler needs.

```rust
#[derive(Concept)]
pub struct CreateSpace {
  pub this: Entity,
  pub name: SpaceName,
}
```

### The trigger is declarative

The nice part is how the command gets asserted: a view template carries a form, and the display layer's event machinery turns the submit into a transient claim and posts it to `/transact`. No bespoke UI code, no fetch handler. The "New space" form lives in `profile.yaml` now, right above the cards it sits with.

```html
<form onsubmit=space/create>
  <wa-input name="name"></wa-input>
  <wa-button type="submit">New space</wa-button>
</form>
```

The command's `name` field reads its value straight from the submit event, off the form's named input:

```yaml
command!: &space/create
  with:
    name:
      the: dom.event.current-target.elements.name/value
      as: text
```

> [!note]
>
> The form writes `name` under that attribute, and the handler decodes by the same attribute. Form-assert and handler-decode never have to agree on anything except the one `the:`.

### The handler is a Provider, not a function

I had considered an axum-like router: handlers as `async fn`s whose parameters declare what they need. But dialog already has a capability system, and it fits the model better. The whole point of this system is that an operator can only exercise the capabilities it has been delegated. A command should be the same: something you can run only if you hold the capability for it, not a function anyone can call.

So a command implements `dialog_capability::Command`, and the thing that runs it is a `Provider<C>`. The provider is a small tonk-owned env, `CommandEnv`, a cheap handle over `AppState`:

```rust
impl Command for CreateSpace {
  type Input = Self;
  type Output = ();
}

impl Provider<CreateSpace> for CommandEnv {
  async fn execute(&self, command: CreateSpace) {
    // re-lock through the env, do the IO, commit the outcomes
  }
}
```

Registration is just the type:

```rust
CommandRegistry::new().command::<CreateSpace>()
```

And `command::<C>()` only compiles when `CommandEnv: Provider<C>`. The capability is a compile-time bound: a command you have not provided cannot be registered, because the type system will not let you name it.

The dispatcher is almost nothing. After a commit it matches the transients against the registry and calls `execute` on each, concurrently. There is no outcome buffer and no dispatcher-side commit, because a command is self-contained: it does its own IO and commits its own outcomes through the env. The decode from raw facts to a typed command reuses the same derived query machinery a read subscription already uses, so a plain `#[derive(Concept)]` is decodable with nothing extra.

> [!note]
>
> The output is `()` on purpose. A command runs independently of the commit it is reacting to: it cannot fail that commit and it cannot block it, so there is no result to hand back. If a command needs to report something, success or failure, it does so by asserting a fact into the database, which the rest of the system reacts to like any other change. It is like getting an email asking me to do a thing. I do it once I have read the email, and if it cannot be done I reply to the email saying why not. The reply is just another message in the system, not a return value to whoever sent it.

### What is still owed

Today's gate is the compile-time one: you cannot register a command the env cannot run. The runtime gate, the genuinely UCAN-shaped one, is still owed. Right now `execute` does its work unconditionally; the next step is for it to succeed only when the operator actually *holds* the capability for each action it attempts, so creating a repository or committing to a branch is something the authority chain permits rather than something the env just does. The structure is in place for that; moving the providers from `CommandEnv` toward the operator's own capability chain is the path.
