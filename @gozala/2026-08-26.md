## The button dies, the ceremony signs ahead

Yesterday ended with a "finish backup" button and me asking why it exists at all. Today's answer: it does not. The creation ceremony is the one moment the custody key is in hand, so it now pre-signs the publish invocation, bounded to a month, and hands it back with the sealed cell. The worker drains it on activation, on boot, and when new work queues. No page, no assertion, no button. The cell is also recorded on profile main as a CustodyCell fact, so the account's own sync carries the recovery envelope and the vault copy only bootstraps a brand-new browser.

The old queue comment said an invocation "cannot outlive a wait for an email click" because of its five-minute expiration. We own the expiration. A regression test now pins that a month-old signature still redeems: the service bounds registration ceremonies, not an owner's own cell.

## The dead invite I was told about twice

I reported the share button clean after testing the wrong space. Irakli insisted the consumer was never provisioned, and he was right: one spot carried an attached upstream with no consumer row, share minted link after link for it, and every recipient pulled straight into "the subject is not provisioned". The gate only asked whether an upstream exists. Also in that hunt: the Hub's "local" marker is a boot-time overlay meaning "present on this device", it silently missed a space after a service worker restart, and I diagnosed a sync problem from a styling stamp. Cosmetic bug, real confusion, still unfixed.

## The endless loader, actually

Not slow loading. The service worker's shell cache stored the SPA fallback, index.html with a 200, under a hashed asset URL during a rebuild window. Subresource integrity then correctly blocked HTML pretending to be JS, and only a background revalidation healed the entry, which is why refresh usually fixed it. First instinct was to drop SRI; wrong, closed, kept. The right fix teaches the cache that an HTML answer for an asset path is a miss, not content.

## The profile is not a repository named "profile"

Autocomplete was dead on `/inspector`: typing `sp` suggested nothing, while the same editor on `/space/did:key:…/inspector` completed fine. The inspector stamps `(repo, branch)` into each cell's LSP buffer URI, and `/inspector` mounts with `with="main@profile:tonk"`. `Location::space()` returns `None` for a profile context, so `resolve_context` fell back to the literal string `profile`.

Nothing downstream can use that. The profile lives in its own namespace behind `profile_repository()`, never `repository(name)`, and `Location` already rejects a bare `profile` token for exactly this reason. The worker looked up a repo that does not exist, opened no branch, and the language server degraded to the nine built-in concepts. `space` is published on the profile branch, so it was never in the list.

The two sides had also drifted on spelling. The LSP documented `<profile>` as the profile repo segment and returned `None` for it; the inspector emitted `profile`. Both dead-ended, so no URI could reach a profile branch at all.

> [!caution]
> The seam was `open(repo: &str, branch: &str)`. A bare string cannot say "the profile", so every layer had to invent a name for something that has none, and each one invented a different one. It now carries a `Repo` enum and the flattening is gone.

Diagnostics and hover resolve through the same `open_for`, so they were degraded on that page too and come back with the same change. [#787](https://github.com/tonk-labs/tonk/pull/787)

> [!note]
> Picked `profile:<name>` over the `<profile>` sentinel because it is the same token the `branch@repo` grammar already speaks, and it carries the name if profiles ever become plural.

## A blank page, and one recursive lock

The whole sealed guest was dying on mount:

```
cannot recursively acquire mutex
  at ui_sync_status::paint
  at UiSyncStatus::connected_callback
  at TonkFab::inject_children → set_inner_html
```

`paint()` in its headless branch reports onto its PARENT rather than drawing a disc of its own, and it does that from `connected_callback`. The parent is also a custom element observing those attributes, so the write re-enters that element's `attributeChangedCallback` while `custom_elements` still holds this one's state mutex. On single-threaded wasm `Mutex::lock` asserts instead of deadlocking, so it panics, and guest startup aborts before anything downstream registers.

> [!caution]
> This is the failure mode of any element that writes to a neighbour during its own lifecycle callback. The custom-element reaction queue will happily deliver that write synchronously, back into a crate that is mid-borrow. A microtask is the whole fix, but the shape is worth recognizing.

Came in with [#746](https://github.com/tonk-labs/tonk/pull/746) (`371c24ee`), the commit that moved the disc to reporting onto its parent. Backported to staging as [#793](https://github.com/tonk-labs/tonk/pull/793).

> [!note]
> I found this only after driving the browser myself instead of asking Irakli to paste console output. Should have done that several rounds earlier; the panic was sitting at the top of the log the whole time, underneath the symptoms I was chasing.
