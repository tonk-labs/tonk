### Update to Notation

Last week I raised the issue that the old notation made it dangerously easy to confuse two very different operations. Consider:

```yaml
view! person:
  display: |
    <ul><template><li>{name} is {age}</li></template></ul>
```

What does this do? Two plausible reads:

1. Define a `display` for the `person` *concept* — i.e. publish a view tied to the concept entity.
2. Update the entity currently *named* `person` by giving it a `display` field.

The old notation collapsed both into the same surface, and the only way to ask for #2 was to switch to a query variable (`view! ?person: …`) making it too easy to replace `person` with something different, *I actually made that mistake more then once*.

While [floating alternatives in the thread](https://discord.com/channels/1423258342578589749/1501644962092027985) I also realized the underlying data model was wrong: `dialog.meta/name` was defined as an attribute *on the entity* being named (cardinality-many, "entity → names"). But a name is meant to be other way around, one name points to at most one entity, while an entity can be reached by many names. Git branches/tags are the right mental model. So the [name concept](https://github.com/tonk-labs/tonk/blob/0bb14f37f963112f938fd67d278dc1d2c8a79f97/rust/tonk-schema/src/builtin.rs#L110-L134) was reshaped: a name is itself an entity (With `id` URI scheme so `foo` refers to `id:foo`) whose single claim points at its target.

Once names became entities, the surface ambiguity above resolved by separating the two operations into two distinct shapes, see [updated guide](https://github.com/tonk-labs/tonk/blob/30046c73d9bdf2e99707f4ed8892f1848bb40f99/rust/tonk-notation/guide.md):

**Define a view on the `person` concept (and publish a name for it):**

```yaml
view!: &person-view
  display: |
    <ul><template><li>{name} is {age}</li></template></ul>
```

The `&person-view` is a YAML anchor on the head's value. It desugars into two separate claims in the same transaction:

```yaml
# 1. assert the view itself
view!:
  this: ?view
  display: "<ul>…</ul>"

# 2. publish id:person-view to point at it
name!:
  this: id:person-view
  entity: ?view
```

Two claims, two entities, one transaction. The thing that was previously crammed into a single `view! person:` head: "make a view *and* associate a name with it". It is now visibly two operations with YAML anchoring as convenient shortcut.

**Update the entity currently named `person`:**

```yaml
view!:
  this: person
  display: |
    <ul><template><li>{name} is {age}</li></template></ul>
```

The `this:` key carries the subject. `person` here is a bare symbol that resolves through the `name` concept  to whatever `id:person` currently points to. If you wanted to operate on the name *itself* rather than its target, you'd write `this: id:person`.

#### Bare symbols for references (with a tradeoff)

The other notable change is that attribute references in concept bodies used to require a leading `.`, which I think was a wart and something I kept forgetting myself. Originally it was a workaround that allowed to disambiguate reference from the string literals:

```yaml
concept!:
  name: person
  with:
    name: .person-name
    age:  .person-age
```

That is no longer needed, now references are bare symbols and resolve through the name concept at transaction time:

```yaml
concept!: &person
  with:
    name: person-name
    age:  person-age
```

**Tradeoff**: single-word values that *happen* to look like symbols (`name: alice`) are now references, not strings. To disambiguate you need to vote them:

```yaml
person!:
  name: "alice"
  age: 28
```

I think improvements in [LSP](https://microsoft.github.io/language-server-protocol/) will help us avoid mistakes there, also worth noting that symbols can not include upper case letters so following works fine and is interpreted as string

```yaml
person!:
  name: Alice
  age: 28
```

## Updates not propagating properly problem

I discovered an incorrect behavior when asserting fact that supposed to supersede existing one. I managed to reproduce it with a following test case

```rust
pub mod name {
    use super::{Attribute, Entity};

    /// The `dialog.meta/named-entity` attribute — the entity a
    /// name currently points at. Cardinality `one` (the derive
    /// default), so re-pointing a name supersedes the prior
    /// claim instead of accumulating.
    #[derive(Attribute, Clone, PartialEq, Eq, PartialOrd, Ord)]
    #[domain("dialog.meta")]
    pub struct NamedEntity(pub Entity);
}

/// A user-published name — an `id:<n>` entity carrying a
/// single `entity` claim that points at the target the name
/// currently identifies.
///
/// `this` is derived from the name string by prefixing `id:`.
/// `entity` is the target. Asserting two `Name` claims for the
/// same `this` with different `entity` values supersedes the
/// prior claim because the backing attribute is cardinality
/// one.
#[derive(Concept, Debug, Clone, PartialEq, Eq, PartialOrd, Ord)]
pub struct Name {
    /// The name entity — `id:<n>` for user-published names,
    /// `db:<n>` for built-ins.
    pub this: Entity,
    /// The target this name currently identifies.
    pub entity: name::NamedEntity,
}

#[cfg(test)]
mod tests {
    #[dialog_common::test]
    async fn it_resolves_only_latest_name_target_via_name_concept() -> anyhow::Result<()> {
        use crate::meta::{Name, name};
        use dialog_query::Output as _;
        use dialog_repository::helpers::{test_operator_with_profile, test_repo};

        let (operator, profile) = test_operator_with_profile().await;
        let repo = test_repo(&operator, &profile).await;
        let branch = repo.branch("main").open().perform(&operator).await?;

        // Use the `concept:` scheme for targets — this matches
        // the real-world case where `concept!: &page` derives a
        // content-hashed `concept:…` entity URI for each body.
        // Same supersession path, different value scheme; this
        // catches a bug where the cardinality-one filter was
        // sensitive to the value's URI scheme.
        let id_page: Entity = "id:page".parse()?;
        let page_v1: Entity = "concept:Fx8sv1aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa".parse()?;
        let page_v2: Entity = "concept:AfmLeBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB".parse()?;

        // tx1 — point id:page at v1.
        branch
            .transaction()
            .assert(Name {
                this: id_page.clone(),
                entity: name::NamedEntity(page_v1.clone()),
            })
            .commit()
            .perform(&operator)
            .await?;

        // tx2 — point id:page at v2. Cardinality-one supersedes v1.
        branch
            .transaction()
            .assert(Name {
                this: id_page.clone(),
                entity: name::NamedEntity(page_v2.clone()),
            })
            .commit()
            .perform(&operator)
            .await?;


        assert_eq!(
            branch
            .select(Query::<Name> {
                this: id_page.clone().into(),
                entity: Term::var("entity"),
            })
            .perform(&operator)
            .try_vec()
            .await?,
            vec![Name {
                this: id_page.clone(),
                entity: name::NamedEntity(page_v2.clone())
            }]
        );
    }
}
```

After investigation, I rediscovered that it's actually not a bug but currently implemented behavior 😩 we have never got around to updating. Specifically we have there is a [document describing version control](https://github.com/dialog-db/dialog-db/pull/240/changes) that is planned for dialog, where's current design simply assumes that you set `cause` field pointing to a fact you want to be retracted as a part of assertion.

Ended up doing [dialog-db#333](https://github.com/dialog-db/dialog-db/pull/333) to make `cardinality: one` actually mean it: cardinality-one writes route through a new `Change::Replace`/`Instruction::Replace` that supersedes any prior value at the same `(entity, attribute)` at commit time, with reasserting the same value being a no-op. Drops the dead `cause`-gated branch from `Assert`. Lines up with how the version-control doc imagines `Cause(Vec<Version>)` working — once that lands, the auto-captured priors slot in naturally.

## Raw identifier keys leaking into JSON

Another agent flagged that a concept like:

```rust
#[derive(Concept, ...)]
pub struct AnonymousAttribute {
    pub this: Entity,
    pub id: attribute::Id,
    pub r#type: attribute::Type,
    pub cardinality: attribute::Cardinality,
    pub description: Description,
}
```

…produced a descriptor whose `with` map contained `"r#type"` instead of `"type"`. Same root cause for snake/camel/Pascal-cased fields: the derive called `ident.to_string()` directly, so `display_name` stayed `display_name` instead of becoming `display-name` per the formal-notation convention used everywhere else (attribute names, etc.).

Fix in [dialog-db#334](https://github.com/dialog-db/dialog-db/pull/334): normalize at derive time — `unraw()` drops any `r#` prefix, then `convert_case::Case::Kebab` folds snake/camel/Pascal into kebab-case. Single-word lowercase names are unchanged. Applies to both `Concept` and `Formula` derives.

## Account System

Thinking about potential goals we have for account system:

1. Cross device access recovery

2. Billing and rate limiting

   > Account can be billed according to their usage of the service & can be rate limited to load balance availability across accounts.

Notably there is nothing here about account being something globally identifiable or memorable necessarily. I think this implies that account could be represented as a delegation from the service provider (tonk) to a [did:key][] principal allowing it to provision remote for desired [did:key][] identified space and then get billed by resource use.

> I have designed [similar system in the past](https://github.com/storacha/specs/blob/main/w3-account.md) where user registered their email address with the system, and after proving ownership of the email were able to [provision spaces](https://github.com/storacha/specs/blob/main/w3-provider.md#consumeradd) by adding **consumer** spaces to their account's provider (service).

I think with advance of [web authentication API](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential) it would make sense to not add email into the loop, but instead generate [persisted public key credential](https://developer.mozilla.org/en-US/docs/Web/API/PublicKeyCredential) that can be used as an account. This credential could be leveraged to address cross device access recovery, without imposing billing & rate limiting. Later can be accomplished by registering public key credential with an a system (e.g. tonk) and setting up billing relation. When billing is set up tonk system principal can delegate capability to the account to add customer space's to the system for which account will be billed by usage.

### Identity

Identity is useful outside of service accounts as it allows collaborators to identify who the participants are and calibrate how much they can trust them. I believe this does not require rolling out custom identity system, instead system may be better served by providing verifiable claim that participant is the same person as some other identifiable persona e.g. email address, phone number or an [at-proto handle](https://atproto.com/specs/handle). This also means they can provide multiple proofs of identity not just one.

Simplest solution here would be to repeat what [keybase.io](https://keybase.io/) did, by publishing a claim on their feed that they can be also identified by a public key credential and produce signature with corresponding private key proving it. Merkle proof for the claim than can be verified by anyone allowing them to recognize public key credential as the publisher of the claim.
