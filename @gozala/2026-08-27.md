## Safari drops the profile credential

Safari was broken in three ways at once: the Hub read "account" instead of "link an account", pressing it opened the menu with an HTTP 500, and "create a new space" did nothing. All three are one failure. `GET /api/profiles` answers `failed to open the registry profile: Storage error: Space already exists: Profile/tonk`, and the create handler opens the same registry.

The chain, read off the worker's own log ring (`GET /api/health` from the page, since Safari's WebDriver has no service worker console): boot loads the registry profile, misses (`IndexedDB database not found: tonk.profile`), creates it, saves the signer. The very next open loads it again and gets `Credential not found: key/self`. The loader turns that into `NotFound`, `Profile::open` treats any load error as "absent" and falls to `Create`, and `Create` refuses because boot already mounted that location. So the message names the wrong problem: the record is not readable, not duplicated.

Why the record is unreadable is a WebKit bug: Safari 27 can serialize an ==X25519== `CryptoKey` but cannot deserialize it. `structuredClone(x25519Key)` throws `TypeError: Unable to deserialize data`, `postMessage` of one delivers `messageerror`, and IndexedDB, which is the same serializer, swallows the failure: `put` reports success with the key, the transaction completes, `count()` and `getAllKeys()` see the row, and `get`, `getAll` and a cursor all hand back `null`. No error event anywhere. Every other key type round-trips (Ed25519, ECDSA and ECDH P-256, AES-KW, AES-GCM, HMAC, extractable or not), and it makes no difference whether the X25519 key is public or private, generated or imported from JWK/raw, bare or inside an object or array. One X25519 key anywhere in the value poisons the whole value, so an Ed25519 pair stored next to it is lost with it. Same in a dedicated worker.

Minimal repro, any origin:

```js
const k = await crypto.subtle.generateKey({ name: "X25519" }, false, ["deriveBits"]);
structuredClone(k.publicKey); // TypeError: Unable to deserialize data
```

dialog's signer export carries a derived X25519 `agreementKey` next to the Ed25519 pair since [#463](https://github.com/dialog-db/dialog-db/pull/463) (tag `tonk-2026-08-24`), and we picked that up with the custody pins. Chrome stores it fine, Safari stores a row it can never read.

> [!caution]
> This is worse than a broken Hub. On a service worker restart the fresh loader misses the same way, `Create` mints a new signer and overwrites `key/self`, so a Safari device gets a new profile DID every restart.

Two fixes, both upstream: don't persist an X25519 `CryptoKey` on the web, and make `OpenProfile`'s open-or-create fall back to `Create` only on a real `NotFound`, never on a read-back failure.

The first has a workaround that keeps the agreement key non-extractable, verified in Safari. `generate()` has the seed in hand when it derives the X25519 key, so at that moment: wrap the private key with a non-extractable AES-KW key (`wrapKey("pkcs8", …)`, 48 bytes, so AES-KW's 8-byte rule holds), store `{ kek, wrapped, pubRaw }` instead of the `CryptoKey` pair, and on load `unwrapKey` into a non-extractable X25519 key and `importKey("raw")` the public half. `deriveBits` agrees with the original. AES-GCM over the JWK form works too, and so does the plain fallback of storing the pkcs8 bytes and importing non-extractable on read, at the cost of the secret sitting in IDB in the clear.

> [!note]
> Safari's WebDriver has no service worker console, but the SW glue keeps a log ring and answers `GET /api/health` from the page. That is how the boot-then-fail sequence became visible; worth remembering before reaching for the Web Inspector.

## The wrapped archive, and the bug behind it

dialog `fix/x25519-safari-archive` (polly worktree, off main) lands the workaround in `dialog-credentials`. The archive shape is decided where the X25519 key is derived, since that is the only moment the secret is in hand: `structuredClone` a freshly imported X25519 public key once per thread, and if it throws, archive `{ wrappingKey, wrappedKey, publicKey }` (a non-extractable AES-KW key, the PKCS#8 private wrapped under it, the public as raw bytes) instead of `{ privateKey, publicKey }`. Readers take both. A restored key keeps its wrapping material so a re-save writes the same record. The probe has a `cfg(test)` override, so Chrome runs the wrapped path in tests: the same seed derives the same public key and the same shared secret either way, a wrapped archive survives a `JsValue` round trip non-extractable, and `generate()` archives wrapped when told keys do not clone.

Verified in Safari against tonk by pinning the worktree: the Hub reads "link an account", `/api/profiles` is 200, the log ring has no "already exists", and `key/self` in IndexedDB holds the wrapped shape.

Create-space then failed one step later, and this one is ours, not WebKit's. `onboarding::derive_kek` seals the onboarding account under a KEK expanded from the custodian's ==Ed25519 signature== over a fixed context, re-signed on every boot. Safari's WebCrypto randomizes Ed25519 signatures (two signatures of one message differ; ECDSA too, as expected), so the envelope is sealed under one key and opened with another: `the onboarding account did not open: the envelope did not open`. Chrome is deterministic, which is why it never showed.

> [!caution]
> WebCrypto does not promise RFC 8032 determinism. A KEK has to come from something reproducible by construction: an X25519 agreement between the custodian's agreement key and a stored ephemeral public, or a random KEK wrapped under the custodian. Envelopes already sealed the old way need a read path that still opens them where signing is deterministic.
