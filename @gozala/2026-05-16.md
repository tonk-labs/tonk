## Macro System for Notation

Spent the day thinking through whether the notation should have a proper macro system, what shape it would take, and how it relates to the substrate. The trigger was a frustration I keep running into: the `concept` concept can't describe itself in the notation because `with:` is dictionary-shaped, so the parser ends up special-casing it. Same goes for rules (whose `assert`/`when`/`unless` are also dictionary or list shaped). I wanted to know if we could collapse these into the regular machinery instead of growing the parser.

### Framing: Datalog × Scheme with content addressing

The frame that stuck: think of it as Datalog + Scheme macros, with content addressing as the binder. The IPFS analogy fits. Git's content-addressed DAG plus BitTorrent's peer-to-peer fetch, with content addressing promoted from feature to substrate. Here the parents are Datalog (set semantics: facts are their content) and Scheme (s-expressions are code-as-data), and the child makes content addressing literal at the storage layer.

Why this matters concretely: hygiene. Scheme [gensym](https://docs.racket-lang.org/reference/symbols.html#%28def._%28%28quote._~23~25kernel%29._gensym%29%29)s to prevent variable capture across expansions. Content addressing inverts the problem. Identifiers are computed from content, so two expansions producing the same content produce the same identifier on purpose. Capture becomes merge. Hygiene by convergence, not uniqueness.

### Grammar

The substrate's syntactic forms land close to EDN:

```
ATOMS
  symbol       foo, ?x, _, ns/foo, id:foo, did:key:zHj…
  literal      "text", 42, true

COMPOSITES
  { k: v, … }  keyed set
  [ v1, v2, … ]  unkeyed set
```

Two atom kinds, two composite kinds. The conventions on symbols (`?` for variable, `_` for blank, `/` for qualified, `:` for URI scheme) are purely lexical. Interpreter dispatches on shape; parser doesn't decide what `?` means.

Lists-as-sets cleans up a lot. Conjunction (`when:`, `unless:`) is naturally set-semantic. Canonicalization gets one rule: sort children by content hash at every level. The `digest` function trivializes.

### Macro shape

Macros take `pattern:` and `expand:`. Pattern is an expression with variables, expand is a list of expressions (templates). Pattern matches an asserted expression, bindings substitute into expand, expanded expressions get asserted. Same shape as [`syntax-rules`](https://docs.racket-lang.org/reference/stx-patterns.html#%28form._%28%28lib._racket%2Fprivate%2Fstxcase-scheme..rkt%29._syntax-rules%29%29).

Iteration falls out of the pattern shape. A pattern entry whose key is a variable, like `with: { ?k: ?attr }`, matches each entry of the source map: a literal key can only match one entry, a variable key can only mean "every entry." The pattern itself carries the multiplicity.

### Datalog disjunction over pattern dispatch

For attributes inside `with:`, there are three forms the user can write: a URI reference (`xyz.tonk.person/name`), a bare symbol that resolves through names (`person-name`), or an inline definition (`{ the: xyz/age, as: int, cardinality: one }`). Two structural shapes really: atom (URI or symbol) and map (inline def).

Write one macro per variant with disjoint patterns. The kernel rule that makes this work is "variables match only atoms; to match a composite, write the composite pattern explicitly." Two macros, side by side:

```yaml
macro!:                          # attribute-reference variant
  pattern:
    concept!:
      this: ?this
      with:
        ?k: ?attr
  expand: ...
```

```yaml
macro!:                          # inline-definition variant
  pattern:
    concept!:
      this: ?this
      with:
        ?k:
          the: ?the
          as: ?as
          cardinality: ?card
  expand: ...
```

The reference variant matches when the value at `?k` is an atom (symbol or URI). The inline variant matches when it is a composite with `the`, `as`, `cardinality`. The two patterns can never both match the same entry, so dispatch is structural.

A mixed concept assertion like:

```yaml
concept!: &person
  with:
    name:  person-name
    email: xyz.tonk.person/email
    age:  
    	the: xyz.tonk.person/age
    	as: int
    	cardinality: one
```

ends up with the head-macro firing once, the reference-macro firing twice (for `name` and `email`), the inline-macro firing once (for `age`). Each entry produces exactly one constellation, by exactly one macro, with no overlap.

### Fresh entities by inlined content

The macro shown below needs to introduce a "field entity" linking each `with:` entry to its attribute. Rather than introduce a binding form, inline the entity's content where the entity reference would go and have the substrate hash it to derive the id.

```yaml
macro!:
  pattern:
    concept!:
      this: ?this
      with:
        ?k:
        	the: ?the
        	as: ?as
        	cardinality: ?card
  expand:
    - attribute!:
    		the: ?the
    		as: ?as
    		cardinality: ?card
    - assert!:
    		the: db.field/name
        of: !entity
        	name: ?k
        	attribute: ?the
        is: ?k
    - assert!:
    		the: db.field/attribute
        of: !entity
        	name: ?k
        	attribute: ?the
				is: ?the
    - assert!:
    		the: db.concept/field
    		of: ?this
    		is: !entity
        	name: ?k
        	attribute: ?the
```

The `!entity` tag marks a map as an entity reference: the substrate hashes the tagged content and uses the resulting digest. Same tagged content in two places refers to the same entity by construction. The reference is the content.

### Hygiene for pattern variables

The remaining piece is canonical naming of pattern variables. A rule's content addressing should be invariant under variable renaming: two rules that differ only in the names of their pattern variables should produce the same entity.

The procedure operates on a rule's free variables (locals — those not named after the head's fields). Head-bound variables keep their names; locals get canonical names.

1. For each local `v`:
   - For each `when:` clause `E` that mentions `v`, build `skel(E, v)`: replace every variable position in `E` with a placeholder, marking `v`'s positions as `self` and others as `other`.
   - Hash each `skel(E, v)`. Keep every hash, including duplicates — the count matters. Two clauses producing the same skeleton contribute two copies.
   - Sort the list and concatenate. This is `v`'s fingerprint.
2. Sort locals by fingerprint.
3. Rename locals in sorted order: `?0`, `?1`, …, `?n-1`.

Worked example. Inductive case of transitive closure:

```yaml
rule!:
  assert: foaf
  when:
    - friend-of: { this: ?this, to: ?y }
    - foaf:      { this: ?y, to: ?to }
```

`?this` and `?to` are head-bound and keep their names. `?y` is the only local, appearing in both `when:` clauses:

- `friend-of: { this: other, to: self }` (`?y` in `to:` of the first clause)
- `foaf:      { this: self,  to: other }` (`?y` in `this:` of the second clause)

With one local, sorting is trivial: `?y → ?0`. The rule's digest is invariant under the author's choice of name for the helper.

### When fingerprints tie

A natural follow-on: can two locals end up with the same fingerprint? Yes, in genuinely symmetric rules. The clearest case is a rule with multiple locals in symmetric positions — a three-hop chain, for instance:

```yaml
rule!:
  assert: foaf
  when:
    - friend-of: { this: ?this, to: ?p }
    - friend-of: { this: ?p, to: ?q }
    - friend-of: { this: ?q, to: ?to }
```

For `?p`, the first two `when:` clauses:

- `friend-of: { this: other, to: self }` (`?p` in `to:` of the first)
- `friend-of: { this: self, to: other }` (`?p` in `this:` of the second)

For `?q`, the last two `when:` clauses:

- `friend-of: { this: other, to: self }` (`?q` in `to:` of the second)
- `friend-of: { this: self, to: other }` (`?q` in `this:` of the third)

Identical multisets. Their fingerprints tie.

The tie is real but inconsequential: the rule is invariant under swapping `?p` and `?q` (the `when:` set is the same up to alpha-renaming), so either choice of tie-breaker (`?p → ?0, ?q → ?1` or the reverse) produces the same canonical rule body and the same digest. Whatever order the tie-breaker picks, the name only enters the choice of slot, never the canonical content.

Cycles of three or more variables in symmetric positions tie the same way for the same reason: the rule is invariant under the cyclic permutation; the tie-breaker doesn't affect content. Outside symmetric/cyclic structures I don't see how two pattern variables can tie — distinct structural roles produce distinct fingerprints automatically — and the cases where they do tie are precisely the ones where the choice can be arbitrary without affecting digest.

### Where this leaves things

The substrate's surface lands at:

- **Atoms**: symbol, literal.
- **Composites**: keyed set, unkeyed set.
- **Primitive**: `assert!` (write a triple). The only place `!` carries semantic weight.
- **Macros**: `pattern:` + `expand:`. Static head dispatch. Variables match atoms; composites need composite patterns. Variable-in-key implies iteration. Entity references can be inlined as content; the substrate hashes to derive the id.
- **Hygiene**: by content addressing. Pattern variables canonicalize by structural fingerprint; identical content produces identical digest across writers.

### Open items

1. How queries actually decompose. The assertion side is well-defined now; the query side is not. A naive macro-mirror (`concept:` decomposes the same way as `concept!:` modulo the leaf operator) doesn't survive because at query time the concept's schema isn't known to the user-facing form. Queries are probably schema-driven, and the right place for that decomposition is the worker layer, not the macro layer.
2. How `this:` is auto-derived when absent. Probably: substrate computes the digest of the body and injects `this: id:<digest>`. That's the one place the substrate has to know about content addressing as production rather than comparison.
3. How effects fit. Effects look like rules-with-a-shape (command pattern in `when:`); they should compose with the macro system without new kernel work. Worth writing out the `state-transition` macro for the counter case from yesterday and checking it falls out cleanly.
4. Whether the parser should hand-roll any of this or whether the YAML layer is enough. The `&anchor` desugaring as a macro depends on the parser mapping YAML anchors to an `anchor:` field, which is the one place YAML semantics still leak into the substrate.
