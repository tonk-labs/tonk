# June 10th

## Deleting the tonk-concept crate

After the `<tonk-concept>` element came out, the `tonk-concept` crate was left as an rlib of shared notation-template machinery. A whole crate for two modules consumed by exactly one sibling is not pulling its weight, so I folded it into `tonk-display` and deleted it.

Only `tonk-display` actually used it: the `template` module (segment parsing, the chrome/repeat binding plan, field substitution) and the source-parsing/query helpers in `resolve`. `tonk-layout` carried a `tonk-concept` dependency too but never used it, a dead line I removed. The `error` module was redundant: tonk-concept's `ErrorDetail`/`ErrorKind` were byte-identical to `tonk_host::error`, which tonk-display already imports, so I dropped it and retargeted the moved code at tonk-host's. No new dependencies or web-sys features were needed; the remaining template code only touched types tonk-display already had.

The `resolve` module name collided, since tonk-display already has its own `resolve` with different functions, so I merged the two rather than nesting a module. Net is one less crate and about 140 fewer lines, with the template logic living next to its only consumer.

The diff also surfaced something I want to keep out of this PR. A pile of `tonk-layout .niri-concept-list`, `.picker-row`, and friends in styles.css got swept into the removal because the word "concept" matched. Those are old tonk-layout selectors for the niri concept tiles and the picker dialog, already dead on staging before this branch touched anything. Safe to delete, but they are tonk-layout cleanup, not tonk-concept removal, so they should land separately rather than ride along here.

## Retiring tonk-layout too

That stray CSS was the thread that pulled the rest. The niri-style `<tonk-layout>` was the workspace metaphor made literal, columns and tiles you arranged by hand, and the binder model replaced the whole idea. The crate was still there, still registering its element, still watched by the dev server, and still wired to a `space/:space/layout/:workspace` route that nothing in the UI navigated to anymore. Dead weight that looked alive.

The one thing to be careful about was that the route was genuinely wired, not just defined: `TonkLayoutView` created the element and the launcher registered the path. So this was not an isolated crate delete, it was removing a feature. I took the whole thing out: the crate, the view component and its route, the `register()` call, the workspace member and dependency, the Trunk watch path, and the orphaned niri styles. About 2600 lines gone, no dangling references left.

If we want tiling layouts again they should be rebuilt on the binder rather than revived from this crate. The old one assumed a workspace that owns membership, which is exactly the assumption we just removed.

## Creating a repository whose name comes from its own DID

I wanted to name a new repository after the last 8 chars of its `did:key`, which is a chicken-and-egg problem: the name has to exist before `profile.repository(name)`, but the DID only exists once a keypair is generated, and `CreateRepository::perform` was generating that keypair internally, after the name was already locked in.

The seam was already there at the effect layer. `space::Create` carries a `Credential` and just stores whatever it is handed; only the `CreateRepository` convenience wrapper was minting the signer itself. So the fix was to expose that seam rather than fight it: `CreateRepository::with_credential(impl Into<SignerCredential>)` takes a pre-generated signer, and `perform` now delegates to `with_credential(Ed25519Signer::generate().await?)`. The default auto-generate path is unchanged and existing callers are untouched. Now the call site reads generate signer, derive name from `signer.did()`, then `profile.repository(name).create().with_credential(signer).perform(&op)`.

Two small design calls. I kept the naming policy out of the library: the caller derives the name (the "last 8 chars" rule lives in their code, not buried in an API method), and `with_credential` takes `impl Into<SignerCredential>` so it accepts an `Ed25519Signer` today or other signer types later. And I returned a distinct `CreateRepositoryWith` builder rather than threading an `Option<credential>` through the existing one, so that once a credential is supplied, keypair generation is statically impossible and that path's only failure mode is storage.

Done in the tom worktree on `feat/repo-creation`, with a round-trip test that generates a signer, names the space from its DID, creates, and loads it back. Full suite green (1392 tests), clippy clean.

## Making the inspector a host-driven notebook

The `<tonk-inspector>` had grown its own opinions about the worker. It fetched the repository directly, owned a branch selector, a header, push/pull sync, and remotes views, all of which duplicate machinery the rest of the app already gets for free from the outer `<tonk-host>`. I want it to be a plain consumer, the way `<tonk-display>` is: just a notebook of `<tonk-code>` cells that evaluate and render results, dispatching events instead of fetching, with no opinions about branches.

So I rewrote it. The notebook dispatches `tonk-evaluate` on its editor element and lets the surrounding routing context, the `<tonk-repository>` and `<tonk-branch>` ancestors a display route mounts under `<tonk-host>`, annotate space and branch and perform the IO. No `fetch`, no `api::*`, no branch state of its own. Dropped the branch selector, the header, the sync chips, and the remotes. To keep the two evaluation modes I taught the host's evaluate path a `transact` flag: a dry-run preview on every clean LSP diagnostics frame, and a committing submit on Shift+Enter or the play button.

The cleanup rippled. Once the inspector stopped reusing the shared `BranchRow`, the whole Repository-side sync apparatus, sync state, pull/push, status polling, upstream badges, branch-channel watches, was dead, because the only remaining caller is the profile route and a profile branch never has an upstream. I stripped all of it and left the profile path working.

The part I had not considered, and the part that bit, is the LSP. The language server derives `(repo, branch)` from the buffer URI to source branch-aware completions and hovers, and my first cut handed it a context-free `tonk-inspector:///scratch-{id}` URI. Syntax diagnostics and auto-eval still worked, but completions went dumb. The worker's LSP handler has no DOM, so it can only learn the branch from what the browser sends it, and the document URI is that channel. So the right move, and the idiomatic LSP one, is to compute the URI: the notebook reads the same routing ancestors the host annotator reads and builds `tonk-buffer:///<repo>/<branch>/scratch-{id}` from them. The inspector still holds no branch state, it just reads ambient DOM context, the same way the evaluate path does.

Left `core.yaml`'s inspector concept alone. It keeps its `source` field as the entity anchor and the element simply ignores it, so no stdlib reseed. PR #508 against staging.

There is something still wrong in the running app, though. I am seeing "Not Found / no concept matched", which smells like requests landing in the wrong repo or branch. Picking that up next.

## Repositories identified by did:key, names as metadata

We were identifying repositories by the name a user typed, which forces names to be unique and makes renaming impossible. Those are two different things wearing one hat: identity and a label. So I split them. A repository's identity is now its credential's did:key, and the routing/storage key is that did's suffix. The name a user types is just metadata.

The chicken-and-egg from a few days ago is what unlocked this: with `with_credential` we generate the signer first, so the did exists before we name the space, and the name can derive from the did rather than the other way around. Creation mints the credential up front, two spaces can share a label, and a create never collides. URLs became `{branch}@{label}:{key}` where the key is the text after the last colon, so `/space/did:key:z6Mk…` routes by its suffix and the label in front is cosmetic. Bootstrap stopped pinning a `home` address and just creates a default space when the profile has none. No migration: old name-mounted replicas will not resolve, which is fine pre-release.

Then the name itself. I put it in the repository's own database as a `tonk/repository` concept keyed by the subject, so the repo is self-describing and the name travels with it. The banner reads and edits it in place through a `<tonk-editable>`, a small contenteditable control where Enter commits, Escape reverts, and blur fires the rename. Two custom-element papercuts cost me time there: the renderer assigns the bound value as a property when the element exposes one, so a getter-only `value` silently dropped the binding and the field showed the literal `{name}`; and a contenteditable does not fire `change`, and the one I dispatched did not bubble, so the rename command never reached the delegated listener. Both are the usual "looks like an input, isn't quite" gaps.

## The name cache was the wrong idea

I had built a clever Rust handler that, on rename, also updated the name in the profile's replica index so the Hub listing would reflect it. Then I realized it only updates on the device where the rename happened. The profile is per-device, so everywhere else the listing stays stale. I had cached a value whose source of truth lives somewhere that actually syncs, and the cache could only ever be right on one machine.

The repository's own `tonk/repository` name, by contrast, lives on its content branch, which syncs to everyone with access. That is the real source of truth. So the fix was to delete the cache rather than maintain it: drop `Replica.name` entirely, keep the replica only as the membership index of which spaces exist, and have each Hub card resolve its name from the space's own repo through a repo-scoped `<tonk-display>`. Until that resolves the card shows an "Untitled" placeholder so it never reads as blank. Renames now propagate to every device the ordinary way, through content sync, and the whole "what name do we set on join" question dissolves: there is no name to set, the card reads it from the repo.

The refactor was wider than it should have been, because `Replica.name` had been threaded through every `Replica::new` call site, and because I had to tear out the rename handler I had shipped one commit earlier. The lesson is the one the cache itself taught: decide where the source of truth lives before you build anything that mirrors it.
