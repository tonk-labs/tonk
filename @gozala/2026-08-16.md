# August 16

## Making signatures algorithm agnostic

Everything in credentials was welded to ed25519. There was no way to say "a principal, whatever the algorithm", which we need for did:web and did:plc since those resolve to verification methods of any curve. Turned out the varsig `Signer`/`Verifier`/`Resolver` traits were already generic and async (the `Resolver` doc even named did:web/did:plc as the reason), so the fix was not a new abstraction, just concrete `Ed25519*` types leaking into two places: stored signer fields and a couple of resolver bypasses.

Landed as [#446](https://github.com/dialog-db/dialog-db/pull/446): agnostic `Signature`/`Signer`/`Verifier` enums that are what credentials exports now (ed25519 the default feature, everything else opt in), plus a real second algorithm (P-256, native and browser WebCrypto since that is the curve passkeys use). The credential storage format was already multicodec tagged, so threading the enums through was just dispatching on the tag instead of assuming ed25519, and old credentials keep loading byte for byte.

> [!note]
> The signer/verifier split fell out nicely: a ==signer is a wrapped key you already hold==, a ==verifier is something you resolve==. So `WithDid` wraps a signer to present a `did:web` name while signing with its own key (the ucanto `withDID` trick), and resolution became an ambient `.perform` capability so the environment owns the cache and the network policy.

## did:web

[#447](https://github.com/dialog-db/dialog-db/pull/447), stacked on the above. New `dialog-did-web` crate: `Resolve { did }` capability returning the agnostic verifier, a did:key provider (local), a did:web provider (fetch `.well-known/did.json`, `publicKeyMultibase` or `publicKeyJwk`), a method dispatcher, and a caching provider. `reqwest` without the `stream` feature compiles for wasm, same trick remote-s3 uses to dodge the wasm-streams collision. End to end now: an ed25519 or p256 key signs under `did:web:issuer.example`, the doc resolves the key back, the invocation verifies.

The whole thing is header driven: varsig encodes the algorithm in the header, so decode takes it from there and refuses when the header and the signature disagree, rather than guessing from bytes. A mixed chain (ed25519 delegates to p256 which invokes) verifies in one pass, each link under its own header.

## Delegation signatures were never verified

While writing a did:web signing test the agent noticed the prover never checks delegation signatures. Chased it because it sounded too serious to be true, and it was true: `Invocation::check` verified only the invocation's own signature, and the chain check (`syntactic_checks`, sync, no resolver) only checked structure. `Delegation::verify_signature` existed with zero non-test callers, and `AuthorizeError::InvalidSignature` existed but was never produced. The check was designed and dropped.

> [!caution]
> ==Any peer with push access could forge authority.== Write a `dialog.ucan/*` fact plus a self-consistent envelope claiming `issuer: Alice` with a signature that is not Alice's, and it splices into a chain: facts agree, coverage passes, Alice's signature is never checked. The existing guard verified the fact and envelope agree with each other, not that Alice signed the envelope. It is on `main`, predates all the agnostic work.

Fixed in [#448](https://github.com/dialog-db/dialog-db/pull/448), both paths. The authorizer verifies each link and returns `InvalidSignature`. The prover (the primary path, delegations as synced facts) verifies each envelope signature at admission via the local `Ed25519KeyResolver` (did:key needs no network, the key is the identifier) and ==skips== a bad candidate rather than erroring, so a forged fact cannot deny-service a request a valid delegation still authorizes. Two tests pin it: forged-only stays unproven, forged plus a valid alternative still proves. did:key needs no resolver, and because `verify_signature` is parameterized over one, did:web threads through the same call site later.

## Variable length signatures

Also fixed the agnostic signature being a fixed `[u8; 64]`, which is wrong: varsig means variable signature, the header carries the length. Now a `Box<[u8]>` with per-algorithm length validation. ed25519 and p256 stay byte identical since the wire form was already `serde_bytes`. This unblocks reviving RSA and WebAuthn, both of which were closed back when everything was ed25519 bound.

> [!note]
> Next: did:web/did:plc docs carry a key set, so resolving to a single key is wrong. Going to resolve to a verifier over all the keys (any one verifies, header prunes by algorithm) and leave room for a `kid` hint in metadata as a later fast path.

## Delegations live in the account now

[#705](https://github.com/tonk-labs/tonk/pull/705), which started as one missing edge and turned into three. The account repository was already mounted and syncing but only carried a display name and passkey metadata. Space delegations went to the profile's own access branch and to a hex chain blob in R2, so the facts a second device needs never travelled with the account and recovery had to fetch artifacts over HTTP.

Space creation now retains the `space → account-root` prefix into the account space, where it decomposes into ordinary `dialog.ucan/*` facts. Dialog already had both ends (`Delegations::retain` writes, the `dialog-operator` proof walk reads), so this was wiring, not machinery. Retain is content addressed, so re-retaining an identical chain commits nothing and the call is safe unconditionally. Best effort on purpose: a space is usable the moment its delegation reaches the profile's access branch, and failing creation because a hidden system repo was mid hydration would trade a working space for a recoverable one.

> [!note]
> Found a real bug doing this: adopt only ran on the re-link path, never on a first time link. So the very case the feature exists for was the one it skipped.

## CLI authorization through the browser

Once delegations sync, `account link` does not need its own ceremony. The browser holds the passkey, so the CLI opens the same page it already opened, passing its profile as audience and a loopback callback URL, and the page delegates from the account and posts the result back.

Form post rather than fetch, because it crosses origins with no preflight and no CORS header to arrange. The page never stores a UCAN, the CLI stores both halves of the union. Declining reports back to the same endpoint instead of leaving the CLI to time out.

## Migrating spots written before the dialog upgrade

The part I expected to need a dialog change and did not. Export with the last build that can read the old format, remap `dialog.*` to `db.*`, import here. Identity is retained rather than reminted, so a migrated spot is the same spot to its peers.

Two binaries are unavoidable: push has to read the old tree to compute the difference, so no force push or sync base trick gets around it. But we do not need `push().override()` either. Reading the revision the remote's memory points at and using it as the precondition does the same job and fails when the pointer has moved, which is the behaviour we actually want.

> [!note]
> Credentials have to migrate first. Until the certificate store moves, this build sees no account at all and `spot new` refuses outright with "A Tonk account is required". The ordering is not documentation, the command enforces it.

Detection is structural, not string sniffing: decode the revision as a map and probe for the `branch` key. Old revisions are a 7 field map, new ones 6. That keeps working in the service worker, where downloading an old binary is not an option.

Test drives the real commands against a fixture that is the old build's own on disk state with an account attached, generated under v0.6.7 since this build cannot write that format. It ends in a push against a live access service, which is what proves the credentials came across and not just the data. Checked the push assertion actually fails by pointing it at a dead port first.

> [!caution]
> Multi branch migration is limited by the old build, which only exports `main`. `--branch` exists on this side for when that stops being true.
