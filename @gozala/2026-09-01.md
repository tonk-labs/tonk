# The dot that was not a loader

The share flow on [#820](https://github.com/tonk-labs/tonk/pull/820) kept ending in a space view stuck on a pulsing dot, and only a reload fixed it. It read as "iframe keeps loading" for days because the dot is pixel identical to the loading placeholder. It is not the loader. It is the `no-entity` slot: the view subscribed fine, got an answer, and the answer was that its site entity does not exist.

Finding that took driving the whole flow through raw CDP: a rig that creates a space, signs up, activates over HTTP, and clicks copy share link in a throwaway browser context on the same Chrome I test in. The inner space frame turned out to be invisible to every normal probe. It shares the guest's process, so it has no target in `/json` and no entry in the outer frame tree; the only way in is `Runtime.enable` on the guest and evaluating by execution context. Once inside: one display, `model=tonk:site`, `state=no-entity`, pointing at a `site:` uuid baked into the srcdoc that no branch carried. Dispatching the self heal's `tonk-claim` by hand rendered the space in seconds, which settled the diagnosis before touching any code.

The stamp is a transient in the branch session overlay, and the share flow was throwing it away. `refresh_branch` existed to pick up an upstream wired on a separate handle, and it did that by opening a fresh session and swapping it into the cache. The swap adopted subscriptions but a fresh open mints an empty overlay, so every session fact (the tab's site stamp, sync status) silently vanished the moment enable sync wired the remote. Dialog already had the right primitive: `Branch::refresh` re-resolves head and upstream in place on the cached handle. The reactor uses that now, and the whole swap apparatus (adopt, rebind, the retained plan) is deleted.

The same commit fixed CI. The web leg failed on `it_broadcasts_the_invite_minted_by_profile_routed_enable_sync` with `rows[0]` on an empty delta: the rebind forced a replacement snapshot that could race in ahead of the invite mint with zero rows. No rebind, no empty snapshot. A new test pins the real invariant, an overlay fact asserted before the refresh must reach a fresh subscriber's snapshot after it.

> [!note]
> Two lies cost hours today. `grep -rlc` said the retry fix was missing from the served wasm; grep skips binaries, `strings` found it immediately. And the rig declared WEDGED on the passing run because its frame check looks for an iframe target in `/json`, which a same-process inner frame never gets.

Earlier the same night: one shot subscription dispatches were dying during racy boots ("no host claimed the event"), so `subscribe_claimed` retries the dispatch bounded and display, fab activation, and site heal use it. Necessary, not sufficient; the retry cannot help the two ghosts still in the console, a sync status subscribe that gets claimed with no subscription written, and a detached fab dispatching from a document fragment. Follow ups.

# Dictionaries fixed the views

Dialog's keyed collections landed a while ago (dialog #472): an attribute can be a dictionary, declared as `{[symbol]: text}` or `{[position]: entity}`. The entry form `{key: value}` binds both halves, the key rides its own `field/key` operand, and storage is one fact per entry: `<subject> domain/<key> <value>`, cardinality one per key so re-asserting an entry supersedes it. Symbol keys give you named slots, position keys give you sequences with float ordering.

This week that shape ate the whole view system, and it fixed a problem I had been living with. In the old model a view was its own entity carrying a `model` back pointer and a `display` template, with a separate concept per presentation kind (`view`, `view/directory`, `view/label`, `view/title`). Nothing stopped two views from pointing at the same model, and the renderer picked a winner by entity hash. Author a second card for `person` and one of them silently wins, forever, on every device that happens to sort the same way. The CLI even grew `--anchor` so you could pin the view entity just to make re-authoring hit the same one.

The dictionary dissolves the whole problem, because the identity moves to where it belonged. Now `this` on a view IS the model entity, and the one field is `show: {[symbol]: text}`: facets as keys, templates as values. `show: {ui: ..., directory: ..., label: ..., title: ...}` on the model itself. The storage key is (model, facet), so there is no second view to compete with; re-asserting a facet supersedes it by cardinality, and asserting facets separately just fills in more of the same dictionary. Four concepts collapsed into one, the back pointer is gone, and there is no view entity left to name, anchor, or order by. `view=` in displays and routes now names a facet, not a concept.

The notation grew up around it in the same push: a dictionary literal can carry several entries at once on every side. In an assertion each entry becomes its own claim, and one map can mix asserts and retracts (`{alpha: "A1", beta: _}`). In a query `show: {ui: ?ui, directory: ?d}` joins per entry, so only models carrying both facets match, and open queries fold the per-entry rows back into one dictionary per entity. Same story in rule premises, one proposition per entry. The engine holds one key slot pair per field, so extra entries ride satellite queries equi-joined on `this`; you never see that from notation.

The same keyed shape is waiting for the other places I still hand roll ordering: workspace sheets and board columns as `{[position]: entity}`, table cells by address. Views went first because they hurt the most.
