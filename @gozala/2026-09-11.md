# The serial load that would not reproduce

Tonk loads serially. A throttled HAR of a sign-in shows 20 block GETs at peak 1 in flight, while the push of the same tree reaches peak 15. Same app, same link, same remote: one direction fans out and the other does not.

Every test I wrote against dialog said the download was fine.

The tests were measuring the wrong things, one at a time. Counting block reads instead of round trips, so local reads (which overlap for free) made the number look healthy while every fetch was serial. A replica sharing the source's storage, so nothing crossed the wire. A replica holding *nothing*, which is worse than it sounds: with no base tree the merge has no diff to compute, so it fetches nothing and the download that follows finds everything already local. And measuring the push next to the pull, where the push's fan-out hides the pull's serial run inside one peak.

What broke the deadlock was giving up on synthetic fixtures. dialog now reads and writes snapshots as [CARv1](https://ipld.io/specs/transport/car/carv1/), tonk grew a profile export route behind an `Accept` header, and I captured a real account and a real first-load device out of a running app. The test replays the actual scenario: a device that already seeded its own profile adds the account as a remote and pulls.

It passed. Natively.

```
native:  58 fetches, peak 15, longest serial run 0
wasm:    prepare  60 fetches, serial run 30
         download 52 fetches, serial run 31
```

Same code, same fixtures, same test. The browser serializes 30 fetches back to back, in both phases independently, and native never serializes at all.

## Why

On native the first poll of a request registers a socket with the reactor, and the kernel carries it from there. The bytes arrive whether or not anything polls again. On wasm the request *is* the polling: `reqwest` wraps `fetch()`, so a future nobody polls has never called it. A loop that awaits one read at a time issues one request at a time, and the concurrency that `buffered(16)` and `FuturesUnordered` express never reaches the wire.

Both the merge's descent and the download's walk have that shape, which is why they fail independently.

> [!caution]
> A peak cannot see this. One phase fanning out lifts the peak above 1 while another is strictly one-at-a-time, so the test now measures the longest run of fetches with nothing else in flight. That number is 0 natively and 30 in the browser.

## The hard part

Three fixes measured and rejected: draining each traversal level before yielding (patches one loop, doubles reads), `spawn` in the walks (needs `'static`, and they hold borrowed storage, so the bound cascades out of the crate), `spawn` inside the hydration flight (detaches the work, but the caller still awaits it alone).

What is needed is the effect native gets for free: queued reads that keep progressing while the loop is busy elsewhere. Something pool-shaped, where polling any member drives them all. That is a structural change, so the reproduction lands first: [dialog-db#505](https://github.com/dialog-db/dialog-db/pull/505).
