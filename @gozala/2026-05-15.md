# May 15

## Templates with subviews

In passing @goblinoats mentioned that the way templates iterate over children was not very intuitive. We did not really talk about it and I never communicated the rationale I have for the current approach, which I should have. I'll start by saying that it was something I put a lot of thought into and am continuing to think about. Let's compare what you'd do in a typical todo list case across various libraries.

### The data model

For the comparison we'll use a todo-list where each item is rendered by its own subview. The outer view only knows item URIs and the per-item rendering lives in a separate template. In TypeScript a developer would probably write the data model like this:

```ts
type Todo = {
  title: string;
  done: boolean;
};

type TodoList = {
  name: string;
  items: Todo[];
};
```

`TodoList.items` is an array of `Todo` objects nested inside the list. That's the shape almost any JS library will assume, and it leaks straight into how the view template iterates: `list.items.map(...)`, `v-for="item in list.items"`, etc.

> [!warning]
>
> It's worth calling out that arrays are inherently positional, which complicates replication. In fact every system that gives you something array-shaped ends up turning it into a [list CRDT, which is really a tree](https://mattweidner.com/2022/10/21/basic-list-crdt.html).
>
> I have plenty of bad experience with libraries that try to hide the underlying structure and pretend to give you an array, because code like this can cause unintended consequences where every item is treated as new and unrelated to its prior version:
>
> ```typescript
> const update = (state: Todo, action: Action) => {
>   switch (action.type) {
>     case "complete-all": {
>       return {
>         ...state,
>         items: items.map(item => ({ ...item, done: true }))
>       }
>     }
>     // ...
>   }
> }
> ```
>
> _[Automerge even warns you not to do this exact thing](https://github.com/SmartBear/automerge/blob/3b1827dda85632ac6499d5bb9f5fc9cba71a30c6/README.md#making-fine-grained-changes)_, but I digress.

In dialog the same data model is described relationally rather than through data structures:

```yaml
concept!: &todo-list
  description: List of todo items
  with:
    name:
      description: Name of the list
      the: xyz.tonk.list/name
      as: text
    item:
      description: Item in this list
      the: xyz.tonk.list/item
      as: entity
      cardinality: many

concept!: &todo
  description: Todo item
  with:
    title:
      description: Title of the todo item
      the: xyz.tonk.todo/title
      as: text
    done:
      description: Whether the todo item is done
      the: xyz.tonk.todo/done
      as: boolean
```

The subtle but important difference: `item` here isn't a *field that holds* an array of Todos. It's an attribute on the relation between the list entity and any todo entity. Each `{the: "xyz.tonk.list/item", of: list, is: item}` fact is independent. The list "has many items" because many facts match its `this`, not because the list carries a payload. There's no array data type, no "list of Todos" container, just a many-cardinality reference.

> [!note]
>
> This means if I want to add another todo it's just a new fact. I don't have to update an array or shift any elements.

This matters for the iteration discussion because in tonk the same model can be navigated in either direction: "what items does this list have" is symmetric with "what lists is this item in." Neither side owns the other. And cardinality is a property of the relation, not the value type, so the *same* concept could accept one item today and many items tomorrow without changing the data type. We'll come back to this point.

### The views

```yaml
view!:
  model: todo
  name: "basic"
  display: |
    <div>
      <input type=checkbox checked={done} />
      <span>{title}</span>
    </div>

view!:
  model: todo-list
  name: "basic"
  display: |
    <article>
      <h2>{name}</h2>
      <ul>
        <li subject={item}>
          <tonk-display entity={item} model=todo view=basic />
        </li>
      </ul>
    </article>
```

Notice how the template refers to `item` the same way it refers to `name`, even though a list may have one name but many items. I believe this is the confusing part, we'll get to that after comparing with popular libraries. Before we do I'd like to point out a couple of interesting things:

- The basic `view` we defined for `todo-list` simply uses a `tonk-display` element to embed each item as defined by the `todo` concept using its "basic" view.

- The view for `todo` can be independently defined or changed without coordinating with the view for `todo-list`. If a named view does not exist yet, the engine renders a built-in chooser that lets you pick from all the views defined for the concept. If none are defined, the engine renders a fallback view that lets you inspect the data.

  > Thinking here is that if a view does not exist, an error is not a great solution. Why not allow the user to pick a view instead, and whatever they pick can become the "basic" view for "todo". If no view exists yet, why not let the user define one in the context and have it become the "basic" view. In other words, define the environment incrementally as you interact with it.

- Everything is reactive. If the `todo` view is updated, the list updates in place to reflect that, with no code compilation, no deployment, no refresh. The system doesn't just react to state changes, it reacts to conceptual-model changes the same way.

- By breaking the rendering into separate `tonk-display` elements we let the system grow more intelligent over time and be clever about when it pulls in `todo` details per entity. One obvious thing _(that advanced systems tend to do)_ is to defer loading until the data is in the viewport, progressively loading things in as you scroll.

Now let's compare how similar UI could be expressed in popular libraries.

#### React

```jsx
function TodoList({ list }) {
  return (
    <article>
      <h2>{list.name}</h2>
      <ul>
        {list.items.map((todo, i) => (
          <li key={i}>
            <Todo todo={todo} />
          </li>
        ))}
      </ul>
    </article>
  );
}

function Todo({ todo }) {
  return (
    <div>
      <input type="checkbox" checked={todo.done} readOnly />
      <span>{todo.title}</span>
    </div>
  );
}
```

Iteration is `Array.prototype.map`; `key` keeps reconciliation honest. The subview is a separate function component receiving the todo as a prop.

#### Vue

```html
<!-- TodoList.vue -->
<template>
  <article>
    <h2>{{ list.name }}</h2>
    <ul>
      <li v-for="(todo, i) in list.items" :key="i">
        <Todo :todo="todo" />
      </li>
    </ul>
  </article>
</template>

<!-- Todo.vue -->
<script setup>
defineProps(['todo']);
</script>
<template>
  <div>
    <input type="checkbox" :checked="todo.done" />
    <span>{{ todo.title }}</span>
  </div>
</template>
```

`v-for` directive on the `<li>`, explicit `:key`. The subview is a separate single-file component receiving `todo` as a prop.

#### Solid

```jsx
function TodoList({ list }) {
  return (
    <article>
      <h2>{list.name}</h2>
      <ul>
        <For each={list.items}>
          {(todo) => <li><Todo todo={todo} /></li>}
        </For>
      </ul>
    </article>
  );
}

function Todo({ todo }) {
  return (
    <div>
      <input type="checkbox" checked={todo.done} />
      <span>{todo.title}</span>
    </div>
  );
}
```

`<For>` is a component that emits children directly (no wrapper), iteration value is the implicit key. Subview is a function component.

#### Svelte

```svelte
<!-- TodoList.svelte -->
<script>
  export let list;
</script>
<article>
  <h2>{list.name}</h2>
  <ul>
    {#each list.items as todo, i (i)}
      <li><Todo {todo} /></li>
    {/each}
  </ul>
</article>

<!-- Todo.svelte -->
<script>
  export let todo;
</script>
<div>
  <input type="checkbox" checked={todo.done}/>
  <span>{todo.title}</span>
</div>
```

`{#each ... (i)}` compiler block, explicit key in the parentheses. Subview in its own file receiving `todo` as a prop.

#### Lit

```js
class TodoList extends LitElement {
  static properties = { list: {} };
  render() {
    return html`
      <article>
        <h2>${this.list.name}</h2>
        <ul>
          ${repeat(
            this.list.items,
            (_todo, i) => i,
            (todo) => html`<li><todo-item .todo=${todo}></todo-item></li>`,
          )}
        </ul>
      </article>
    `;
  }
}

class TodoItem extends LitElement {
  static properties = { todo: {} };
  render() {
    return html`
      <div>
        <input type="checkbox" .checked=${this.todo.done}>
        <span>${this.todo.title}</span>
      </div>
    `;
  }
}
```

`repeat()` directive with explicit `(items, keyFn, templateFn)`. Subview is its own custom element receiving `todo` as a property.

### Comparison

All of the popular libraries seem to carry out the same general idea with different flavor: map each `item` to a subview using a custom DSL or JavaScript. I'd argue all the ceremony, whether JS or DSL, is [incidental complexity](https://www.infoq.com/presentations/Simple-Made-Easy/). But that aside, there are a few key differences with our templates.

#### No JavaScript, no compiler

Every other example sits inside a JS file processed by a build step (or a tagged-template runtime in Lit's case). Our views are stored as data: template strings inside a concept definition, parsed at runtime by the browser. And views are concepts themselves, linked to the concepts they render.

> [!note]
>
> The engine doesn't do this yet, but type incompatibility between the conceptual model and the view could be pointed out at definition time in the embedded editor. At runtime the engine could tell you exactly what the inconsistencies are and hopefully let you correct them in place.

#### No need to worry about keys

Libraries need to correlate the model with the view in order to distinguish an item being changed from an item being replaced. In React you use `key` to do it; if you don't provide one, updates are a lot costlier. That means you need some unique (within the collection) identifier, usually computed.

In our system you don't need keys, because everything is described through relations between entities, and entities are system-wide unique identifiers. All cardinality-many relations have entities in value position, and so the template engine knows how to key things without you having to tell it.

> [!note]
>
> The implication is subtle but important. I've seen many bugs in my time where derived keys weren't exactly unique and led to strange runtime behavior that's hard to debug. I've also seen cases where applications started without keys because there were just a handful of entries, but had to introduce them later as performance degraded with growing data.
>
> Not having a `key` means these kinds of problems aren't possible.

#### One syntax for one and many

I deliberately don't treat cardinality-one and cardinality-many differently. The same `{title}` placeholder works whether the field carries a single value or a set of them. That is deliberate: it means changing the data model with respect to cardinality does not break or invalidate views. It doesn't mean things will look beautiful (they probably won't), but they'll still work, and that will be an invitation to pop the hood and adapt the view.

Relatedly, what happens if `item` has cardinality one? It renders as one item in our system. In React what you'd see is a `.map is not a function` error because `item` isn't an array. Alternatively you might get even stranger output if `item` happens to expose a `.map` function of its own.

>  [!note]
>
> Here again we choose to make this kind of error impossible to have, because you can't try to iterate over a non-collection. We're trying to bring the [Kintsugi](https://en.wikipedia.org/wiki/Kintsugi) philosophy of repair-by-mending into the environment.

In other words sometimes things may be aesthetically wrong but *not broken*. The list is visible. The user sees their data. The author can update the view at their leisure to a more appropriate shape. No runtime crash, no silent stringification, no "I forgot this field could be a list."

#### One placeholder, no directive

`subject={item}` in the view above is the spot @goblinoats called unintuitive. It's there because the natural iteration root for `{item}` would otherwise be the inner `<tonk-display>` (the only element actually consuming `{item}`), which would produce `<ul><li><tonk-display/><tonk-display/><tonk-display/></li></ul>` instead of three separate `<li>`s. `subject={item}` lifts the iteration root one level up to the `<li>` by giving it an `{item}` placeholder of its own.

> [!note]
>
> Also note that `subject` is not a special attribute, it could be anything: the engine doesn't care. It's just the outermost reference to a cardinality-many field, and the engine repeats the element it sits on for each value.

The fix for the loss of visual cue isn't a new directive, it's authoring affordance. The language server already knows which fields are cardinality-many; the view editor could underline iteration roots, annotate them in the gutter, or surface them as loops on hover. That gives the reader the *signal* of `v-for` without inventing one in the template language.

## Problems discovered while dogfooding

- URLs being different across users is a huge source of pain. I can't paste a link and assume it will take someone to the same destination.

  > I think we probably could either substitute space names for DIDs, or include the DID in addition so the link works even if the names don't match.

- Repository names being case-sensitive appears to be a major pain, amplified by the fact that Chrome seems to remember URLs you've navigated to in the past and change casing for you.

- Manually pushing and pulling means having to remember to do it. That works for git in the CLI, but goes against intuition when you're doing things in the browser.

  > We probably should resurrect the background-sync function, and maybe have a way to opt out if you want to diverge. Alternatively we could embrace branches, where `main` syncs automatically and if you want to do some changes without having them replicated in the background you branch out and then merge when you want to propagate.
  >
  > 🤔 Although what if you want to share changes on your branch also? Maybe that would be more like a fork.

- DIDs in the `h1` element seem to break layout, especially on small screens.

  > We can probably do some overflow handling to address this, but showing `did:key` in the UI is probably not the right solution anyway.
  >
  > 💡 I think it would be interesting to automatically create 5-6 character names for all DID keys. That way URLs become nicer too.
  >
  > I also kind of feel it would be nice if the `h1` were editable so you can update the name in place.

- In retrospect the error message kind of said what happened:

  > [!caution]
  >
  > Error from local API: name resolve returned 404 Not Found

  But if it mentioned the name it was unable to resolve, I wouldn't have had to guess what it was failing on. I was under the impression that it was failing to resolve the entity name `gavin-05-13`, when it was actually failing to resolve the repository name `tonk`.

## Effects

I want ability to define abilities and associate them with concepts so that when we render a concept we could also render abilities that could be invoked to cause corresponding effects

```yaml
# Defines increment abiity that when asserted
# on the `effect` entity will cause a behavior
# on the subject entity
concept!: &increment
	description: Command to increment
	with:
  	subject:
  		the: tonk.xzy.command/subject
  		as: entity


# defines behavior of counter caused by increment action
effect!:
  description: Effect increments counter on increment command

	# asserts counter concept
  assert!: counter
  where:
  	this: ?this
  	count: ?count

	when:
	  # Counter exists
    - assert: counter
    	where:
        this: ?this
        count: ?last-count
        
    - assert: increment
    	where:
    		this: effect:system
    		subject: ?this

    # Derive count by incrementing last count by 1
    - assert: +
    		of: ?last-count
        with: 1
        is: ?next-count
  # this is for ilustration purposes showing that
  # effect can be disabled
  unless:
  	- assert: disable
  		where:
  			this: effect:system
  			ability: counter
        
# invoke increment on counter
increment!:
	this: effect:system
	subject: ?counter
```

So what does effect concept decomposes to

```yaml
- assert!:
	the: dialog.effect/ability
	of: did:key:zEffect
	is: increment

- assert!:
	the: dialog.effect/assert
	of: did:key:zEffect
	is: counter
	
- assert!:
	the: dialog.effect/premise
	of: did:key:zEffect
	is: did:key:zInitCounter

- assert!:
	the: dialog.premise/predicate
	of: did:key:zInitCounter
	is: did:key:zCounter
	
- the: dialog.application/prameter
  of: did:key:zInitCounter
  is: did:key:zInitThis
  
- the: dialog.parameter/name
  of: did:key:zInitThis
  is: "this"
  
- the: dialog.parameter/binding
  of: did:key:zInitThis
  is: "?this"

- the: dialog.parameter/name
  of: did:key:zCount
  is: "count"

- the: dialog.parameter/binding
  of: did:key:zCount
  is: "?last-count"

# ...
```
