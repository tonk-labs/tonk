## Templates with subviews

In passing @goblinoats mentioned that the way templates iterate over children was not very intuitive, we did not really talk about it and I never communicated rational I have for current approach which I should have. I'll start by saying that it was something I put a lot of thought into & continuing to think more about. Lets compare what would you do in a typical todo list case across various libraries.

### The data model

For the comparison we'll use a todo-list where each item is rendered by its own subview. The outer view only knows item URIs and the per-item rendering lives in a separate template. In TypeScript a developer would probably write the data model like this:

```ts
type Todo = {
  title: string;
  done: boolean;
};

type TodoList = {
  name: string;
  items: Todo[];
};
```

`TodoList.items` is an array of `Todo` objects nested inside the list. That's the shape almost any JS library will assume, and it leaks straight into how the view template iterates: `list.items.map(...)`, `v-for="item in list.items"`, etc.

> [!warning]
>
> It's worth calling out that arrays are inherently positional which complicate replication, in fact every system giving you something like array turns it into a [list CRDT which ends up being a tree](https://mattweidner.com/2022/10/21/basic-list-crdt.html).
>
> I have plenty of bad experience libraries try to hide underlying structure and pretend to give you array, because code like this can cause unintended consequences of all the items being new and unrelated to prior ones
>
> ```typescript
> const update = (state: Todo, action: Action) => {
>    	switch (action.type) {
>      	case "complete-all": {
>        	return {
>          	...state,
>          	items: items.map(item => ({ ...item, done: true }))
>         	}
>       	}
>       	// ...
>     	}
> }
>   ```
> 
>_[Automerge even warns you to not do this exact thing](https://github.com/SmartBear/automerge/blob/3b1827dda85632ac6499d5bb9f5fc9cba71a30c6/README.md#making-fine-grained-changes)_, but I digress here

In dialog the same data model is described relationally rather than through data structures:

```yaml
concept!: &todo-list
  description: List of todo items
  with:
    name:
      description: Name of the list
      the: xyz.tonk.list/name
      as: text
    item:
      description: Item in this list
      the: xyz.tonk.list/item
      as: entity
      cardinality: many

concept!: &todo
  description: Todo item
  with:
    title:
      description: Title of the todo item
      the: xyz.tonk.todo/title
      as: text
    done:
      description: Whether the todo item is done
      the: xyz.tonk.todo/done
      as: boolean
```

The subtle but important difference: `item` here isn't a *field that holds* an array of Todos. It's an attribute on the relation between the list entity and any todo entity. Each `{the: "xyz.tonk.list/item", of: list, is: item}` fact is independent. The list "has many items" because many facts match its `this`, not because the list carries a payload. There's no array data type, no "list of Todos" container, just a many-cardinality reference.

> [!note]
>
> This means if I want to add another todo it's just new fact I don't have to update array or shift any elements

This matters for the iteration discussion because in tonk the same model can be navigated in either direction: "what items does this list have" is symmetric with "what lists is this item in." Neither side owns the other. And cardinality is a property of the relation, not the value type, so the *same* concept could accept one item today and many items tomorrow without changing the data type. We'll come back to this point.

### The views

```yaml
view!:
  model: todo
  name: "basic"
  display: |
    <div>
      <input type=checkbox checked={done} />
      <span>{title}</span>
    </div>

view!:
  model: todo-list
  name: "basic"
  display: |
    <article>
      <h2>{name}</h2>
      <ul>
        <li subject={item}>
          <tonk-display entity={item} model=todo view=basic />
        </li>
      </ul>
    </article>
```

Notice how template refers to `item` just the same it refers to `name` even though list may have one name but many items. I believe this is the confusing part, we'll get to that after comparing with popular libraries, but before we do I'd like to point out couple of interesting things

- Basic `view` we have defined for `todo-list` simply uses `tonk-display` component to embed item as defined by `todo` concept using "basic" view.

- View for `todo` can independently be defined or changed all together without coordinating any of it with the view for the `todo-list`. In fact if named view does exist yet engine will render built-in view that allows you to choose one from all that are defined for the concept. And if none are engine comes with fallback view that allows you to inspect data for it.

  > Thinking here is if view does not exist error is not the great solution, why not allow user to pick view instead and whatever they pick can become "basic" view for "todo". If no view exists yet why not allow user to define one in the context and let it become "basic" view. In other words define environment incrementally as you interact with it.

- Everything is reactive, If `todo` view is updated  list updates in place to reflect that no code compilation, no deployment no refresh. In other words not just system react to state changes it reacts to conceptual model changes just the same.

- By breaking up into separate `tonk-display` elements we allow system to grow more intelligent over time and be clever about when should it pull in `todo` details per entity. One obvious thing _(that advanced systems tend to do)_ is to defer loading until data is in viewport, that progressively load things.

Now lets compare how similar UI could be expressed in popular libraries

#### React

```jsx
function TodoList({ list }) {
  return (
    <article>
      <h2>{list.name}</h2>
      <ul>
        {list.items.map((todo, i) => (
          <li key={todo.id()}>
            <Todo todo={todo} />
          </li>
        ))}
      </ul>
    </article>
  );
}

function Todo({ todo }) {
  return (
    <div>
      <input type="checkbox" checked={todo.done} readOnly />
      <span>{todo.title}</span>
    </div>
  );
}
```

Iteration is `Array.prototype.map`; `key` keeps reconciliation honest. The subview is a separate function component receiving the todo as a prop.

#### Vue

```html
<!-- TodoList.vue -->
<template>
  <article>
    <h2>{{ list.name }}</h2>
    <ul>
      <li v-for="(todo, i) in list.items" :key="i">
        <Todo :todo="todo" />
      </li>
    </ul>
  </article>
</template>

<!-- Todo.vue -->
<script setup>
defineProps(['todo']);
</script>
<template>
  <div>
    <input type="checkbox" :checked="todo.done" />
    <span>{{ todo.title }}</span>
  </div>
</template>
```

`v-for` directive on the `<li>`, explicit `:key`. The subview is a separate single-file component receiving `todo` as a prop.

#### Solid

```jsx
function TodoList({ list }) {
  return (
    <article>
      <h2>{list.name}</h2>
      <ul>
        <For each={list.items}>
          {(todo) => <li><Todo todo={todo} /></li>}
        </For>
      </ul>
    </article>
  );
}

function Todo({ todo }) {
  return (
    <div>
      <input type="checkbox" checked={todo.done} />
      <span>{todo.title}</span>
    </div>
  );
}
```

`<For>` is a component that emits children directly (no wrapper), iteration value is the implicit key. Subview is a function component.

#### Svelte

```svelte
<!-- TodoList.svelte -->
<script>
  export let list;
</script>
<article>
  <h2>{list.name}</h2>
  <ul>
    {#each list.items as todo, i (i)}
      <li><Todo {todo} /></li>
    {/each}
  </ul>
</article>

<!-- Todo.svelte -->
<script>
  export let todo;
</script>
<div>
  <input type="checkbox" checked={todo.done}/>
  <span>{todo.title}</span>
</div>
```

`{#each ... (i)}` compiler block, explicit key in the parentheses. Subview in its own file receiving `todo` as a prop.

#### Lit

```js
class TodoList extends LitElement {
  static properties = { list: {} };
  render() {
    return html`
      <article>
        <h2>${this.list.name}</h2>
        <ul>
          ${repeat(
            this.list.items,
            (_todo, i) => i,
            (todo) => html`<li><todo-item .todo=${todo}></todo-item></li>`,
          )}
        </ul>
      </article>
    `;
  }
}

class TodoItem extends LitElement {
  static properties = { todo: {} };
  render() {
    return html`
      <div>
        <input type="checkbox" .checked=${this.todo.done}>
        <span>${this.todo.title}</span>
      </div>
    `;
  }
}
```

`repeat()` directive with explicit `(items, keyFn, templateFn)`. Subview is its own custom element receiving `todo` as a property.

### Comparison

All of the popular libraries seem to carry out same general idea, but with different flavor. You map each `item` to a subview either using custom DSL or Javascript. I'd argue that all the ceremony JS or DSL is [incidental complexity](https://www.infoq.com/presentations/Simple-Made-Easy/), but that aside there are few key differences in our templates

#### No JavaScript, no compiler

Every other example sits inside a JS file processed by a build step (or a tagged-template runtime in Lit's case). Our views are stored as data: template strings inside concept definition, parsed at runtime by the browser. And views are concepts that are linked to concepts they render. 

> [!note] 
>
> Engine does not do this yet, but type incompatibility between conceptual model and view could be pointed out at definition in the embedded editor. And at runtime engine can tell you exactly what are the inconsistencies and hopefully allow you to correct them in place.

#### No need to worry about keys

Libraries need to be able to correlate model with a view to identify item being changed from item being replaced e.g. in react you use `key` to do it & if you do not provide `key` updates will be a lot costlier. In turn that means you need some unique (within collection) identifier usually computed.

In our system you don't need keys, because everything is described through relations between entities and entities are system wide unique identifiers. That means all cardinality many relations have entities in value position and therefore template engine knows how to key things without you having to tell it anything.

> [!note]
>
> Implication here is subtle but important. I have seen many bugs in my time where derived keys weren't exactly unique and led to strange issues at runtime that are hard to debug. I also have seen cases where applications started without keys because there were just handful of entries, but over time had to introduce them because performance degraded as number of entries grew. 
>
> Not having a `key` means these kind of problems aren't possible.

#### One syntax for one and many

I deliberately don't treat cardinality-one and cardinality-many differently. The same `{title}` placeholder works whether there is a single value or a set of them. That is deliberate, it means changing data model in regards to cardinality does not break or render views incompatible. That is not to suggest that everything will just work out beautifully, that is unlikely, however things will still work even if UI will not look perfect, that would be an invitation to pop the hood up and adapt the view.

Relatedly what happens if `item` has cardinality one ? Well it will render like one item in our system. On the other hand in react what you'll see is `.map is not a function` error because `Item` is not an array. Alternatively you may get even stranger output if `Item` has `.map` function.

>  [!note]
>
> Here again we choose to make error impossible to have, because you can't try and iterate over a non collection. Basically we're trying to bring [Kintsugi](https://en.wikipedia.org/wiki/Kintsugi) philosophy of repairing broken by mending into our environment.

That is to say sometimes things may be aesthetically wrong (the author probably didn't mean to repeat the heading) but *not broken*. The list is visible. The user sees their data. The author can update the view at their leisure to a more appropriate shape. No runtime crash, no silent stringification, no "I forgot this field could be a list."

`subject={item}` in the view above is the spot @goblinoats called unintuitive. It's there because the natural iteration root for `{item}` would otherwise be the inner `<tonk-display>` (the only element actually consuming `{item}`), which would produce `<ul><li><tonk-display/><tonk-display/><tonk-display/></li></ul>` instead of three separate `<li>`s. `subject={item}` lifts the iteration root one level up to the `<li>` by giving it a `{item}` placeholder of its own. 

> [!note]
>
> Also note that `subject` is not some special attribute, it could be whatever engine does not care, it's just known outmost reference with cardinality many and renders it for each one. 

The fix for the loss of visual cue isn't a new directive, it's authoring affordance. The language server already knows which fields are cardinality-many; the view editor could underline iteration roots, annotate them in the gutter, hover-tooltip them as loops. That gives the reader the *signal* of `v-for` without inventing one in the template language.

## Problems discovered while dogfooding

- URLs being different across users is huge source of pain I can't paste a link and assume it will take to the destination.

  > I think we probably could either substitute space names for did's or we include did in addition so it works even if names do not match

- Repository names being case sensitive appears to be a major pain, amplified by a fact that chrome seems to remember URL you've navigated to in the past and change casing for you.

- Manually pushing and pulling means having to remember to do it. Works for git in CLI, but goes against intuition when you're doing things in browser.

  > We probably should resurrect background sync function and maybe have a way to opt-out if you want to diverge. Alternatively we could embrace branches, that way main syncs automatically and if you want to do some changes without getting those replicated in the background you branch out and then merge when you want to propagate.
  >
  > 🤔Although what if you want to share changes on your branch also, maybe that would be more like a fork

- DIDs in H1 element seem to break layout especially on small screens

  > We probably can do some overflowing to address this, but showing `did:key` in the UI is probably not a right solution anyway.
  >
  > 💡I think it would be interesting to maybe automatically create 5-6 char names for all DID keys that way URLs become nicer also.
  >
  > I also kind of feel it would be nice h1 was editable so you can update the name in place.

- In retrospect error message kind of said what happened

  > [!caution]
  >
  > Error from local API: name resolve returned 404 Not Found

  But then if it mentioned name it was unable to resolve it would not have required guess work of what is it not able to resolve. I was under impression that it was failing to resolve entity name `gavin-05-13`, where it was failing to resolve repository name `tonk`.
