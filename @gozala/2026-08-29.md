## Service worker upgrade path

An audit of the service worker turned up eight findings and a five step path: atomicity, liveness, discovery, an escape hatch, hygiene. [#816](https://github.com/tonk-labs/tonk/pull/816) carries all five.

The install now precaches `worker_bg.wasm` and verifies its hash against a stamp the build writes into the glue, so a glue/wasm pair that drifted fails the install instead of half swapping. `hash-guest.sh` hashes both halves together into a `BUILD_ID`, which also names the caches, so two builds can never share cache state. LSP shutdown became terminal and the SSE routes answer 503 with `Retry-After` instead of pinning the retiring worker alive on a stream that never settles. Discovery is a `version.json` probe plus an `x-tonk-build` header the worker compares against its own; a stale write gets 409 and the page shows an update bar. A build that cannot boot shows a failure page with a reset ladder after three attempts, and a `kill-switch.json` naming a build unregisters it everywhere.

Two things that looked like the fix and were not:

The update prompt started as `updatefound` listening, which ping-ponged between tabs: one tab announces, you reload, the other announces. `registration` is shared across every tab on the origin, so each one sees the other's lifecycle events. Gating on `registration.waiting` did not help either, because `skipWaiting()` means the slot is almost always empty. It is a build comparison now, `build !== ourBuild`, which is a question about state rather than about who observed which event.

The version handshake first refused every request from a stale page. `POST .../query` is a subscription despite the verb, so a normal swap 409'd the subscriptions and froze the page. It refuses writes only now, `/transact` and `/evaluate` by path.

> [!caution]
> Publishing the build id as `window.tonk` broke navigation everywhere and took a while to find. `page_effect::forward` tests for `window.tonk` to decide "am I the sealed guest", so the top page started forwarding `navigate` to a bridge that was not there and returned early. Links died silently: the handler ran, called `preventDefault`, and nothing happened. Forms still worked, which is what made it confusing. It is `globalThis.tonkBuild` now. Loosening the sandbox with `allow-same-origin` to introspect the guest is what found it.

Two follow ups on top. [#817](https://github.com/tonk-labs/tonk/pull/817) takes the revocation probe off the boot path. It was two `no-store` fetches in front of `register()` on every load, for a file that does not exist, which an SPA host answers with the whole 40KB shell at 200. It runs unawaited after registration now, and an empty `kill-switch.json` ships so the probe gets 22 bytes of real JSON. [#818](https://github.com/tonk-labs/tonk/pull/818) puts the `x-tonk-*` headers in the CORS allow list. The guest has an opaque origin so anything with a custom header preflights, and the list named none of the five the bridge sends. A rejected preflight is not an error the caller sees; the request just never arrives.

> [!note]
> The kill switch cost a manual file deletion to break once. `selfDestruct` reloaded its clients, which reinstalled the revoked build, which unregistered again. It does not navigate now, on either side.

Tests are 43 JS and 100 Rust. The JS suite loads the shipped `service_worker.js` through a data URI with stubbed globals, so it tests the artifact rather than a copy of it. Every new case is checked against a mutation. That caught a weak one: "boots from cache without touching the network" asserted zero fetches, which the eviction fallback also satisfies by returning early, so it now asserts on the log line that proves which path ran. The CORS test greps the routes for the headers they read rather than restating the list, with a second test so the grep cannot pass by matching nothing.
