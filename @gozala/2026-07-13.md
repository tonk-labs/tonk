# The invite shortener that only the CLI could reach

The shortcut service shipped, but the copy button still handed out 1,100-character URLs. Shortening lived in the HTTP `create_invite` route, which is what the CLI calls. The UI fires the `tonk:invite` command, and its handler never built a URL at all: it wrote `access`/`remote`/`code` into the overlay and left five view templates to concatenate `{dom.host/data-base}?access={access}{remote}#{code}` themselves. A template cannot await a `PUT`, so the copy button could only ever produce the long form.

So the mint handler now assembles and shortens the URL, and stores the finished thing as one field. Views render `{link}` and the five concatenations are gone. Shortening is best effort: a failed PUT logs and falls back to the long URL, which works fine. The origin comes from the service worker's own scope, the only origin that can serve the shortcut's relative redirect back (and a sealed guest's `window.location.origin` is the opaque `"null"`).

`link` lives on `tonk:credential`, the overlay-only concept, because it carries the seed in its `#` fragment and is therefore exactly as secret as the seed. It inherits the never-replicated guarantee instead of needing its own. [#586](https://github.com/tonk-labs/tonk/pull/586).

> [!note]
> The whole design leans on RFC 7231 fragment inheritance: the service redirects to a *relative* `/join?…` with no fragment, and the browser re-attaches the short link's own `#seed` to the target. The seed never touches the wire, and the shortcut store only ever sees the path and query.

## Trunk ate the redirect

Opening a short link answered `405 Method Not Allowed`, which is a strange thing for a redirect to say. The access service was right: `GET /@/{hash}` returns a 301 with a relative `Location`. Trunk's proxy follows redirects itself, so it consumed the 301, re-requested `/join?…` against the *access service* (which does not route `/join`), and passed back its refusal.

The fix is one line, and the reason it took so long is the spelling:

```toml
[[proxies]]
backend = "http://127.0.0.1:8787/@"
no_redirect = true
```

> [!caution]
> Trunk's TOML key is `no_redirect`. The CLI flag is `--proxy-no-redirect`, so I wrote `no-redirect` and trunk ignored it without a word. That made the proxy look like it could never pass a 301 through, and I told Irakli the feature could not work in dev. It can.

The proxy also needs a static backend URL, so `tonk-access-local` now binds a fixed port instead of an ephemeral one. `AccessServiceSettings` still defaults to `0`, so tests keep binding ephemerally and parallel runs do not collide.

## The tests were green over a hole

Nothing covered the seam that broke. The shortcut service was tested in isolation, and mint-to-join was tested by *rebuilding* the URL from the stored `access` + `seed`. So no test ever looked at the URL the handler actually mints and the user actually copies. An empty or malformed `link` would have sailed through.

Wrote three tests and sabotaged each one to make sure it failed for the right reason. The first attempt at the join test passed even with the seed fragment deleted from the minted URL, which is how I found the real problem: the browser harness's worker scope reports no `location.origin`, so a mint always takes the no-origin fallback and the branch that runs in production is unreachable from any test. Splitting `long_invite_url` out of `invite_url` makes both branches testable.

> [!caution]
> The seed belongs in the fragment, and a test now pins that. In the query it would be uploaded to the shortcut service in plaintext, since shortening PUTs the path and query.
