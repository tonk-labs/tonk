# August 18

## Registration shipped end to end

Claude drove the registration stack today while I dropped notes in passing. [#713](https://github.com/tonk-labs/tonk/pull/713) now carries the whole loop: signup asks for an email, does the passkey dance, attaches, and the worker enrolls the account with the access service by depositing a device-issued access delegation the server walks back through the `root → device` grant. The email-code ceremony is gone from signup; the activation email is the email verification now. `/activate` is a new top-document page whose accept button just presents the service-signed invocation, so any device finalizes without a key. The real-browser test passes the full loop: signup, pending-activation notice on the dashboard, open the captured link, accept, active.

The service side got two reworks from my notes: `Store`/`EmailSender` use dialog's dual `async_trait` forms so one generic `Provider` impl serves every environment, and the activation link embeds the complete invocation instead of a delegation, which deleted the audience-pinning walk and the cross-device relay question with it.

## CLI linking is callback-first

`tonk account link` always goes through the loopback callback now; the handoff registry, its polling, and the pending-login states are deleted from the CLI. The page can pass a `redirect` on its own origin and the callback answers with a 303 carrying `?link=ok|denied|invalid`, so the outcome renders in the account page's styling instead of the bare loopback page. Linking registers the customer too, and `tonk account register` / a `registration:` status line handle resends and a wiped dev service.

> [!caution]
> Found while wiring: the callback ceremony lives at `/account/link`, not `/account`; defaulting to the wrong page would have silently landed on the dashboard and ignored the query.

## Provisioning and metering stacked behind it

[#714](https://github.com/tonk-labs/tonk/pull/714): `/provider/add` provisions a space under the invoking customer, depositing the powerline the space already mints to the account as its consent. Worker provisions at space creation next to the retain, CLI at spot bootstrap, both best effort. [#715](https://github.com/tonk-labs/tonk/pull/715): phase 0 metering — every permit and attributable denial lands a row in a second ingest D1, with invocation bytes inline and the flattened proof set written once per session. `POST /ucan/` had to move off the Router onto the fetch event, since only the event's `Context` can carry the write past the response.

The account model draft is in `plan/Account model.md` on [#702](https://github.com/tonk-labs/tonk/pull/702); Claude's review flagged that the registration deposit should eventually be account-signed at ceremony time (the doc's own compromise-path logic), and that the deposit currently grants `/` rather than a scoped branch. Charge cron is next.

## The deposit got scoped, then account-signed

Both flaws from the model review closed today. [#719](https://github.com/tonk-labs/tonk/pull/719) replaces the `/` deposit with two capability-derived delegations: `/memory` pinned to a branch named by the service DID, `/archive` pinned to the index catalog. One definition in `tonk_account::customer::deposit_scopes`, shared by the client that mints and the server that verifies; anything broader is refused. [#723](https://github.com/tonk-labs/tonk/pull/723) then moves the minting into the passkey ceremony, signed by the account root itself, so revoking a device no longer kills the service's grant. The invocation presenting them stays device-signed: that part is authentication, and the device is who is talking.

Registration is web-only now. `tonk account register` is gone, the CLI keeps a read-only probe line, a fresh browser opening a CLI approval link runs signup first and flows into the approval panel, and a signed-in browser the service does not know auto-enrolls from the dashboard. That last one is the whole migration plan for old accounts: no batch job, just every login and dashboard visit converging lazily.

## Also landed: linked state and pre-account spaces

[#720](https://github.com/tonk-labs/tonk/pull/720) reads linked-ness from the account replica the profile repo indexes instead of treating the provider record as the flag; a record whose mount never completed reads as unlinked and re-linking heals it. [#721](https://github.com/tonk-labs/tonk/pull/721) drops the account gate on space creation: a space delegates to the root when one exists, else the device key, and linking adopts profile-delegated spaces (redelegate, retain, provision).

## Driving the flow by hand found the real bugs

The e2e suite passed and the flow was still broken in three ways only a human hit. The approval page signed the descriptor with the account-service URL instead of the page's `/ucan/`, so a linked CLI mounted an account it could never reach: forever unhydrated, probing registration at the wrong host. The callback link never activated the CLI's account session, so every account command still said to log in. And nothing registered the CLI device with the account service, which refuses requests from unregistered devices. All three fixed, plus the payload now carries the deployment's account service URL so `--service-url` is no longer needed for local testing.

> [!caution]
> A sync chip stuck on `sync--unavailable` with every visible request returning 200 means the worker failed while assembling the proof, before any request left. The metering ingest count is the tell: if it does not move during a sweep, nothing reached the service.

The unavailable chip in the private window came from exactly that: storage cleared client-side, in-memory access service restarted server-side, so the `space → root` delegation existed nowhere and the sweep could never prove. Two fixes out of it: `ACCESS_STATE_DIR` opts a dev run into persisting control DB, service key, and a blob snapshot across restarts (regular runs stay ephemeral), and the "cannot prove" state still needs its own chip instead of masquerading as temporarily unavailable.

## The account should be the profile's upstream

The three-IDB-database question turned into the real architecture correction: I expected the profile repository to have the account as its main-branch upstream, not a separate hidden account repository. Dialog already supports subject-different remotes, and reading §5 literally means exactly that. The consolidation dissolves the mount/hide/retain/backup/restore apparatus into ordinary branch sync: a new device links, pulls main, and has the space list and delegations. Profile main becomes account-synced state; credential sites and the meta branch stay device-local. That restructure comes after the current stack lands.

## Custody: the account becomes a secret, the passkey becomes a wrapping

The envelope idea from the handoff survived scrutiny and turned into a spec, [#725](https://github.com/tonk-labs/tonk/pull/725). The account is a 32-byte random secret; HKDF domains split it into the signing root and a reserved E2EE root; every custody method, the first passkey included, is an interchangeable AEAD wrapping of that same secret. That kills the two structural problems at once: one credential is no longer the identity, and WebAuthn leaves the account-creation critical path. The account moment becomes email submission.

The bootstrap design went through three shapes before landing. First a did:web document carrying an account-to-custody delegation, then a bespoke `/custody/publish` capability, and finally the realization that `/provider/add` already encodes the bidirectional consent we kept re-inventing: provision the passkey-derived custody key as an ordinary space (the consent deposit is the passkey's agreement) and write one raw memory cell with the wrapped secret. No repository, no branches, no third database. Then the delegation itself fell out: both designs unwrapped the secret exactly once per fresh link, so publishing a delegation next to it bought nothing. Whoever can unwrap holds the account and self-issues the device delegation on the spot. Retraction is withdrawing providership, complete by construction, since no standing grant ever exists.

> [!note]
> Verified along the way: the presign path never consults repository or consumer records. A memory cell is just `{subject}/{space}/{cell}` in storage, created on first PUT. The whole custody surface is machinery that already ships.

> [!caution]
> I had the verification rules written as "issuer = X" twice before catching it. Issuer never matters, the subject does; any valid chain to the subject carries the same authority as the root key. Worth keeping in reflex for every capability spec.

First code is up on [#726](https://github.com/tonk-labs/tonk/pull/726): the envelope core (domain-separated derivations, strict binary format with the header as AEAD associated data, pinned vectors as the derivation tripwire) and custody passkey ceremonies that evaluate both custody salts in one PRF assertion, with the user handle pinned to a blake3 hash of the account DID so re-enrollment overwrites instead of accumulating.

## And then we built it

The whole custody arc is implemented on [#726](https://github.com/tonk-labs/tonk/pull/726), spec to working flows in one pass. The envelope core and custody passkey ceremonies, the raw-cell protocol proven end to end against a real access service (enroll, provision with the custody consent, presigned PUT of the sealed envelope, resolve with nothing but the custody key, unwrap to the same account), the local wrapping under a non-extractable WebCrypto KEK, and the account page rewired: create is email submission with zero WebAuthn, the dashboard offers adding a passkey, log in is one assertion plus one GET.

The same branch carries the upstream restructure. Profile main now follows the account as a subject-different remote, the hidden account repository is gone, and with it the third IndexedDB database. Delegations, passkey facts, display names, and the space list itself all ride profile main. The claim e2e test says the quiet part: enrolling a passkey before clearing storage is what makes an account recoverable, because the local wrapping is the only custody a fresh account has.

> [!caution]
> Dialog remotes are create-only, so a profile that unlinks and later links a different account hits "profile main already follows a different account remote". Same limitation the hidden repo had, but it now lives on a branch we cannot recreate. Needs a story before unlink ships prominently.

## Late revision: nothing stored, ever

Two more design cuts before the day closed, both Irakli's. The published delegation went first: both designs unwrapped the secret exactly once per fresh link, so whoever can unwrap can self-issue the device delegation on the spot, and publishing a delegation next to the cell bought nothing. Then the local wrapping went too. I had built a non-extractable WebCrypto KEK holding a sealed copy of the secret in IndexedDB, and the argument against it is clean: non-extractability protects the KEK, not the secret. Compromised page code needs no extraction, it can decrypt in place and walk the plaintext out silently. So the first custody passkey moved into the account-creation ceremony itself, atomic with the secret and the published cell, and now no key material is stored anywhere. Every root operation derives its keys inside a fresh user-verified assertion. The cost is one create() prompt at signup and a hard dependency on PRF support, which the phrase wrapping will later relax. The legacy PRF-derived root is deleted wholesale along with the establish-repository apparatus and the hidden-repository middleware. [#726](https://github.com/tonk-labs/tonk/pull/726) carries all of it.
