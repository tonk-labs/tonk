# June 28th

## Deductive rules land

DB-backed deductive rules are working end to end and on a PR against staging (#545). A deductive rule is a fact you store on a branch that the query engine consults at query time to *derive* instances that were never written. This is the thing I wanted when I kept asking why `search/candidate` returned nothing: I want to define "an entity is a candidate if its description matches" as data, not as something compiled into the engine.

The notation is `assert:` with no bang for the head. The bang has always meant "this mutates on commit", so dropping it is exactly right: a deductive rule writes nothing, it derives on read.

```yaml
rule!:
  assert: search/candidate
  when:
    - assert: description
      where:
        this: ?this
        description: ?source
```

Install that and a query for `search/candidate` returns one candidate per matching `description` fact, even though no `search/candidate` fact exists anywhere. The premises stay put; the rule is what turns them into a derived concept at query time. `transaction.assert(rule).commit()` persists it; `.with(rule).query(..)` supplies it for a single query without storing, which is how you try a rule before committing to it.

What it enables in practice: views and queries over relationships you never materialized. Search, derived classifications, "things like this", any concept that is a function of other facts rather than a fact in its own right. And because it is data, you install and retract it like anything else instead of shipping a new build.

Retraction is the symmetric `rule!: this: <entity> ..: _`, the same delete-everything sentinel concepts use. A retract entity can name either an inductive or a deductive rule, so the analyzer resolves both and removes whichever exists. I wrote the test that actually proves the behavior rather than just the lowering: install the rule, query the conclusion, see one derived instance; retract, query again, see zero, with the premise facts untouched the whole time. That is the only test that shows the rule is doing the deriving and that pulling it stops it.

## Cache, identity, the boring-but-load-bearing parts

The rule body is stored as canonical dag-cbor under `db.rule/source`, and identity is content-addressed (`rule:<blake3(dag-cbor(descriptor))>`), so asserting the same rule twice is idempotent and a stored body rehydrates to the same rule. Resolution is always on but cheap: discovery is cached per branch head, hydrated bodies and plans are cached content-addressed. The plan cache moved off a process global onto the branch (SIEVE-backed), which is a better fit for forking and has no immortal static. That shipped in dialog as `tonk-2026-06-27`.

The bulk of the diff is deletion. The old reactor rule-carrier apparatus is gone because resolution lives in dialog now, so the tonk side just stores and queries.
