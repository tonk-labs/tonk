## June 1st

## Simpler Views

> [!caution]
>
> Both me and @jackddouglas ran into the problems using currency view definitions are they aren't unique at which case system pick one out of several that have same name / model.

I proposed alternative design for doing views specifically this one:

```yaml
concept!: &view
  description: |
    A view template defined for the `model` concept as shown below
    
    concept!: &counter
      description: Basic counter
      with:
        count:
          description: Current count
          the: xyz.tonk.counter/count
          as: unsigned-integer

    view!:
      description: Display current count of the counter
      model: counter
      display: <span>{count}</span>
    
    
  with:
  	description:
  		description: Description of this view presented to a user when they are picking one
      the: xyz.tonk.view/description
      as: text
  	model:
  		description: Concept this view is defined for
  		the: xyz.tonk.view/model
  		as: entity
    display:
      description: HTML template for the view
      the: xyz.tonk.view/display
      cardinality: one
      as: text
```

Initially I assumed this meant closed world model, but after chatting more with @goblinoats  I realized it does not actually has to be a closed world model and in fact we can use an open world model as long as the contract is clear for those who define them:

> [!warning]
>
> Custom view type MUST be a superset  `text` field named  `display` containing HTML template that system will project into and be a superset of the following `display` concept

```yaml
concept: &display
  description: |
    Abstract concept that associates it with a conept via `model`.
    It is expected that actual view would also have a `display` field for HTML template of the view.
  with:
  	model:
  		description: Concept this view is defined for
  		the: xyz.tonk.view/model
  		as: entity
```



With that user can define their own custom view type for example like this

```yaml
concept!: &preview
  description: |
    A view template for previewing
  with:
    model:
    	description: Concept this view is for
    	the: xyz.tonk.view/model
    	as: entity
    display:
      description: HTML template for the view
      the: gozala.io/preview
      cardinality: one
      as: text
```

We could support arbitrary views through `tonk-display` web component

```yaml
<tonk-display entity="id:demo-couner" model=counter view=preview />
```

> [!note]
>
> The `view` attribute can be made optional, if omitted we use built-in `view` concept.

My hope is that in the future we will extend dialog's capabilities and notation to simplify this even further and have more general view concept like this

```yaml
concept!: &view
  description: |
    A view template defined for the `model` concept as shown below
    
    concept!: &counter
      description: Basic counter
      with:
        count:
          description: Current count
          the: xyz.tonk.counter/count
          as: unsigned-integer

    view!:
      description: Display current count of the counter
      model: counter
      basic: <span>{count}</span>
    
    
  with:
  	description:
  		description: Description of this view presented to a user when they are picking one
      the: xyz.tonk.view/description
      as: text
  	model:
  		description: Concept this view is defined for
  		the: xyz.tonk.view/model
  		as: entity
    ?display: # 👈 View name is becomes attribute name
      description: HTML template for the view
      the: xyz.tonk.view/?display
      cardinality: one
      as: text
```

## Opener View

We should also implement another built-in view type I'll call it "opener" (but would love someone to propose better name). Which will be used by the system when `entity` attribute of the `tonk-display` is omitted. General idea being that it gives you a way to pick and open one of the entities that matches the specified `model`.

```yaml
concept!: &opener
  description: View for openining entities
  with:
    model:
    	description: Concept this view is for
    	the: xyz.tonk.view/model
    	as: entity
    display:
      description: HTML template for the view
      the: xyz.tonk.view/opener
      cardinality: one
      as: text

opener!:
   model: todo-list
   display: |
     <tonk-selector onsubmit=open>
       <tonk-option value="{this}">{title}</tonk-option>
     <tonk-selector>
```

We will probably also need a way to let `opener` tell the host `tonk-display` about chosen entity to be opened which we can do with predefined command like

```yaml
command!: &open
  description: Command to tell tonk-view to open an entity
  with:
    entity:
      description: Entity to open
      the: dom.event.current-target/value
      as: entity
```

With that tonk-display can react to command, set `entity` attribute and consequently switch from `opener` to open view.

> 🤔 I think it would be nice to inherit view identifier that was specified so opener can reuse it internally but that is not super critical so pinning it for now.

If model does not have an associated opener we could have a default fallback in the system, that gives you generic picker probably rendering each matching entity via specified (or default) view that you can select.

## Page View

One other view we will want to support is a page view. Main difference from other views is that pages do not use templates to render instead they use raw HTML that will be loaded in a primed, sandboxed iframe

```yaml
concept!: &page
  description: |
    An HTML used for rendering a concept in the portal (sandboxed iframe)
    
    page!:
      description: Display current count of the counter
      model: counter
      display: |
        <html>
          <head>
            <script>
            parent.model.subscribe(counter => {
          	  this.querySelector("#count").textContent = counter.count
            })
            </script>
          </head>
          <body>
            <h1 id="counter"></h1>
          </body>
        </html>
    
  with:
  	description:
  		description: Description of this view presented to a user when they are picking one
      the: xyz.tonk.resource/description
      as: text
  	model:
  		description: Concept this page is going to render
  		the: xyz.tonk.resource/model
  		as: entity
    content:
      description: HTML template for the view
      the: xyz.tonk.resource/content
      as: text
```

With the above definition we could now have `<tonk-portal />` web component that is almost identical to `<tonk-display />` but under the hood it uses frames in order to allow script tags and more isolation.

> [!note]
>
> It is very tempting to unify portal and display and to make page into just another view, but I worry about confusion it may lead to. Perhaps other way to go about this could be introduction of additional attribute on `display` that will make distinction clear e.g.
>
> ```yaml 
> concept: &display
>   description: |
>     Abstract concept that associates it with a conept via `model`.
>     It is expected that actual view would also have a `display` field for HTML template of the view.
>   with:
>   	model:
>   		description: Concept this view is defined for
>   		the: xyz.tonk.view/model
>   		as: entity
>   	type:
>   		description: Display mode either `text/html` or `text/dialog-ui`
>   		the: xyz.tonk.view/type
>   		as: text
> ```

This way if `type` is `text/html` it is rendered inside iframe, and if it is a `text/dialog-ui` it is rendered inline. Another alternative would be to simply look at the contents of the `display` field and if root element is [`template`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/template) treat it as a template. Otherwise treat it as a resource to be loaded in the iframe.

## Artifact

Artifact simply becomes binding of entity with model and a view + some extra metadata like title shown in the tab and maybe icon also displayed in the UI.

```yaml
concept!: &artifact
  description: An entity that can be displayed as a sheet in the UI.
  with:
  	title:
  		description: A title shown in the sheet tab
  		the: xyz.tonk.artifact/title
  		as: text
  	icon:
  		description: An icon displayed in the sheet tab.
  		the: xyz.tonk.artifact/icon
  		as: text
  	entity:
  		description: |
  			An entity displayed an the sheet. On a new artifact this can be set to 'about:blank'.
  		the: xyz.tonk.artifact/entity
  		as: entity
  	model:
  		description: |
  		  A model concept used to display the entity. On a new artifact this can be set to `about:blank`.
  		the: xyz.tonk.artifact/model
  		as: entity
  	view:
  		description: |
  			A view concept used to display the `entity`. On a new artifact this can be set to `about:blank`.
  		the: xyz.tonk.artifact/view
  		as: entity
```

Tonk artifact basically becomes state of the the `tonk-display` with two extra attributes used to for displaying sheet tab in the UI  _(which perhaps could just be another view instead)_.
