# August 19

## The stale space list was never corruption

Testing the custody branch across browsers kept producing the same wreckage: a spot per device in the Hub, new spots not propagating in either direction, and workers bricking on restart with `Blob not found in storage`. We treated it as write-tearing first, and some of that was real enough to fix: the account ensure and the drain are serialized now, the drain sweeps the account explicitly (profile main had dropped out of the pull population when the hidden repo dissolved), and the Hub got an account-level space directory keyed on the repository's own entity, one entry per space no matter how many devices mounted it, with delete being account-wide.

Then a log line told the actual story: `account push failed: Blob not found in storage`, a LOCAL miss. Jack had the right instinct, the diff descends nodes we never fetched. A quiet pull adopts the upstream head by root (scenario 3, zero reads), a buffered commit writes novelty near the root without descending, and the push novelty diff then walks base against current through a local-only store and dies subtracting base nodes that were never fetched. The failed push never advances the sync base, so it fails identically forever. Every device wedges within about a minute of login, pulls keep working, the remote freezes at everyone's post-login snapshot. Stale in both directions with no corruption anywhere; the Clear-site-data ritual was never necessary.

> [!caution]
> The push code even documented this as a known limit, but only for pushing to a *different* remote. After any scenario-3 pull the base itself is by-reference, so the very next push to the *same* remote hits it. The everyday case was the unconsidered one.

## Absence is information

Pinned it in dialog with an integration test (deep remote history, zero-read adoption asserted, one commit, push: the exact production error), then fixed it on the invariant instead of hydration: a replica stores every block it mints, so a block it does not hold is not its novelty. The differential got a per-side `MissingBlocks` policy where an absent node settles the walk (contributes its routed ops, never descends, never reported novel) instead of erroring. Base side is lenient unconditionally, because the base is the target's own last-synced tree. The one-line NetworkedIndex fallback would have worked too, and was rejected for the right reason: it turns push into a replication engine for history the replica deliberately holds by reference.

## N remotes, minimum requests

Irakli asked for the general algorithm rather than a single-remote gate, so [dialog-db#454](https://github.com/dialog-db/dialog-db/pull/454) carries the whole thing. The walk records the by-reference frontier it could not enter, and push adjudicates each frontier root, cheapest evidence first: attribution when the target is the only tracked remote (zero requests), one existence probe otherwise (a hit prunes the whole subtree, a virgin target skips probes entirely), and fetch-forward for content the target provably lacks, streamed through the pusher from whichever remote holds it without ever being persisted, blobs and spilled values included. Held novelty uploads children before parents in concurrent waves, so an aborted push leaves every store prefix-closed; that ordering is what makes a positive probe a proof for the subtree beneath it. The bridge test is the proof of the whole shape: 300 facts plus a spilled value adopted by reference from remote A, pushed to a virgin remote B, read back completely by a replica that has only ever heard of B.

> [!note]
> The flush-prediction idea (reconstruct the counterparty's node by applying our ops to a held child and compare hashes; refuted for free when an op still sits in the parent's buffer) is written into `notes/version-control.md` rather than implemented. Under a minimum-network objective it saves only local reads: it applies exactly where the pre-state is held, which is where reads already avoid the network. Watermarks are recorded there too, as routing, never proof of block presence, since a peer that merged the same facts may hold different node encodings.

Tonk now pins dialog to the branch, which meant riding out dialog main's move to algorithm-agnostic signatures: issuers go through the polymorphic `Signer`, chains carry `AnySignature`, verification resolves via `DidKeyResolver`, swept across the whole workspace.

> [!caution]
> The worker-init brick is the sibling case and still open: the session-open candidate scan has a remote fallback, but the session being opened is what would authorize the fetch. Circular, so a by-reference access branch bricks the origin at boot until that path gets its own story.
