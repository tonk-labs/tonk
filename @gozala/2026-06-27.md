## Plan cache off the global and onto the branch

The deductive-rule plan cache (planned `Conjunction` per `(rule, adornment)`) was a process-global static with clear-on-full eviction. Two things wrong with that and I'd been defending both.

First the eviction. Clear-on-full only behaves if you assume the working set stays under the cap, which is just me guessing how many rules there will be. SIEVE eviction reclaims the coldest entry instead of dropping the whole table, so it degrades gracefully at any cardinality and I get to stop guessing. We already had the cache for this: `dialog_search_tree::Cache`, which wraps `sieve-cache`, the same thing the node cache uses. I didn't pull `dialog-search-tree` into `dialog-query` though, they're siblings and that'd be a new sideways edge just to borrow a type. `sieve-cache` was already a workspace dep so `dialog-query` depends on it directly and mirrors the wrapper shape (`ShardedSieveCache` native, `Rc<RefCell<SieveCache>>` wasm). One line added to the lock.

Second, and this is the one that actually mattered: a process-global static is hidden state with no lifecycle. It accumulates dead plans for the life of the process and is invisible to the branch it's caching for. It belongs on the `Branch`, beside `node_cache` and `RuleCache`, created once at open, dropped when the handle is. So `PlanCache` is now a branch field and `ConceptRules` carries a shared handle. The repository hands each per-query assembly the owning branch's cache, which is what makes the cross-query reuse work at all, since a fresh `ConceptRules` is assembled every query and its own per-instance plan map is cold each time.

The peer-branches detail: a query reads from a stack of layers with no distinguished branch, so there's no single owner. But the key is content-addressed (`rule.this()`), so a plan is correct no matter whose cache it sits in. `execute` just rides the first branch's cache, and a branchless overlay-only query falls back to a private default. Kept `ConceptRules::new`'s signature so the ~18 test and registry callsites didn't move, only `assemble` and `Branch` changed.

Where it actually wants to land, postponed for now: the cache should be a capability on the operator env, not a field on the branch. Everything here is already capability based, the query threads the env through every planning site, so a `Provider<PlanCache>` would mean the operator decides the sharing scope and the peer-branch "ride the first one" awkwardness disappears. The argument that makes it worth doing is forking. A fork shares the parent's env but gets a new `Branch`, so a branch-owned cache re-plans everything the parent already planned even though the content-addressed key would have hit. Capability-on-env means the fork shares the parent's cache for free. Branch is the wrong owner precisely because forking duplicates the branch and not the env. Modeling note: `Provider<C>` is request/response (`Input -> Output`), and a cache is get-or-insert-with-closure, so the capability is "hand me the cache handle" not "do the cached lookup".
