# The counter that would not move

Incremental delta subscriptions are wired end to end, but the counter demo stayed stale on every increment. Evaluate to N, durable reads N, screen shows N-1. Looked like the delta apply was broken, so I spent a while on `apply_delta`'s drift heal (retract by value equality leaves a duplicate row when the base drifted, so an asserted row for an entity should supersede its stale rows). Wrote unit tests, they passed. Full-DOM integration test, passed. And it still did not work in the browser.

So I stopped guessing and traced the live path with logging: reactor, SSE, parse, `apply_delta`, render. Every layer was correct. The delta arrived tagged `entity`, parsed clean, and `apply_delta` produced exactly `[count:N]`. Then `handle_entity_frame` ran, `slides=1`, `call_render` fired. And the DOM did not change.

The tell was that `Renderer::apply` never once received a frame carrying `count`. The counter uses the `_:_` default view, which renders an entity as `<tonk-notation>` text via `mount_notation_fallback`. That path formats the conclusion once at mount and has no update path. Its slide's `view_el` is a `<tonk-notation>`, which has no `draw` method, so the `call_render` loop no-ops on it. And `update_notation` reads `notation_source`, which is only set in carousel (multi-view) mode, so it is `None` in single mode. Nothing re-renders the default dump. Fix is one line of intent: store the fallback's `<script>` in `notation_source` so the existing `update_notation` call re-formats it on every entity frame. tonk PR [#583](https://github.com/tonk-labs/tonk/pull/583).

> [!note]
> The bug was never in `apply_delta`. The isolated tests all passed because none of them drove a real SSE frame through the live default-view path. A test that calls `on_update` directly is not a test of the thing that renders.

## The stale guest bundle trap

This cost more cycles than the bug did. The service worker caches the sealed-guest wasm by content hash. A page reload with `--ignoreCache` busts the page cache, not the SW's guest cache, so the inner iframe kept loading a guest bundle from a build or two ago. My newest log would be missing and I would misread it as execution stopping there. Twice I chased a phantom "it dies right after this line" that was just the loaded guest predating that line.

> [!caution]
> To trust guest-side logs you have to clear caches and call `registration.update()`, then hard reload. Otherwise the guest you are debugging is not the guest you just built. `--ignoreCache` is not enough.

Also worth noting: guest `console.log` does reach the top page console (I could see `tonk-host: installed on about:srcdoc`), so logging in the doubly-nested guest is observable, once you are actually running it.

## Streams were a red herring too

Earlier in the same stretch I was convinced a transferred `ReadableStream` orphaned across a sealed-iframe teardown was crashing the renderer, and rewrote the portal to drain bodies over a MessagePort instead. Then the crash persisted, and the user pointed out it reproduces on staging with none of my changes. A/B stress settled it: the transferred-stream build crashes at the same rate. So it is a pre-existing Chromium nested-iframe teardown race, independent of body delivery. Reverted to transferred streams and kept the branch diff focused. The crash mitigation is still open, but at least I stopped fixing the wrong thing.

## Along the way

The page bundle carries the whole datalog engine for no reason. `tonk-host` is a pure relay that never touches dialog, yet it dragged the engine in through a single `tonk-schema` edge that existed only to resolve one rustdoc intra-doc link. Made the link plain text, dropped the dep, engine gone from every bundle that links host. `tonk-ui` also lost leptos entirely (the runtime mounts custom elements, the leptos components were dead) and a pile of unused renderer crates.

> [!note]
> That is only the easy part. Measured debug vs release on `guest.wasm`: 6.68 MB vs 3.84 MB, so about 40 percent is debug-profile overhead. The other 60 percent is real monomorphization, dialog-query and its serde derives. The main page holds the engine because the wire DTOs are colocated with engine-using handlers in the same crates, not because any DTO field references the engine. Splitting wire types from the engine is the real cut, next.

Wrote up the deeper design as a plan for later: one retained set per consumer, a delta-native `draw`/`update` renderer (the DOM is already the keyed state, the reactor already sends deltas), revision-stamped frames so a consumer can detect a dropped frame and reopen, and reactor-side priority dispatch so a parent's pruning delta is sent before a doomed child's. `plan/tonk-display-delta-rendering.md`.
