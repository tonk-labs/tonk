## Namespace prefix duplicated on autocomplete

BUG-21: in the inspector, typing a partial namespaced name like `tonk/emp` and accepting `tonk/employee` gave you `tonk/tonk/employee`. Flat names were fine.

The language server's completion items carried only `label` + `insert_text`, no `text_edit`. Without an edit range the CodeMirror client (`@codemirror/lsp-client`) falls back to `wordAt()` to decide what to replace, and its default word regex excludes `/`. So with `tonk/emp` typed it only saw `emp`, replaced that, and left the `tonk/` I'd already typed in front of the full insert.

Fixed it server-side, which is the LSP-correct place: each item now ships an explicit `text_edit` whose range spans the whole partial token. I walk back from the cursor over the symbol charset plus `/`, stopping at the `?`/`&` sigil or whitespace, so the namespace prefix is part of what gets replaced. Rather than thread that through all six completion builders I funneled every path (head, premise-assert, variable, field) through one range-application step in `complete()`. No JS change, the stock client already honors a server `textEdit`, so nothing to rebuild on the editor side.

## Retracting fields from a concept

BUG-20. I wanted to drop the legacy `active` field off the `tonk:binder` concept and there was just no way to do it. Editing a concept was additive only: you could add a field but omitting one from a `this:`-pinned `concept!:` body silently left the old `dialog.concept.with/active` fact behind. So the concept kept a field I thought I'd removed.

The fix follows from how things are stored. Concept fields are facts, and `concept!:` is an assertion of the `concept` concept like any other head, so `_` should carry its usual retract meaning. `with: { active: _ }` retracts the named field, `..: _` at the top level retracts all of them. I deliberately did not make concept assertion diff-and-replace (omitting a field still leaves it alone), to stay consistent with every other assertion head. That was the call worth getting right before writing code.

The interesting wrong turn: my first cut resolved the pinned concept off the branch and put the field's attribute entity into the retraction as a constant. Committed nothing, revision didn't move. Turned out the evaluator already has a retraction model and it's the opposite of what I assumed: a field gets dissociated only when its term is blank, in which case it queries the branch for the current value itself. A constant term reads as an assert target and gets skipped. So the fix got simpler, emit blank terms and let the evaluator find the value, same machinery instance `..: _` already uses.

Made it strict per the choice in the bug: must pin with `this: <uri>`, the concept must exist, each named field must be present, else a clear error. And `..:` nested inside `with:`/`maybe:` is now rejected rather than misread as a field literally named `..`, which is what it did before. I caught that one just by trying `maybe: { ..: _ }` and watching it produce a nonsense "cannot retract field `..`" message.

## Finishing the model to concept rename

BUG-19. An earlier pass had renamed the machine-readable tokens (the web component attribute, the core.yaml field key, the query term, the subscription tag and data-state) but stopped there, so the codebase still said "model" everywhere it meant a concept: comments, doc-comments, internal Rust identifiers, error strings. This pass finishes it. The rule I held to: rename "model" wherever it names a concept, leave it where it means something else (data model, mental model, IPLD data model, the tonk-tree `model` module). Most of the work was a guarded whole-word sweep per file with those phrases excluded, then fixing the awkward "concept concept" the sweep produced from "model concept".

While in there I renamed the `entity` web component attribute to `this`, matching the notation keyword for the subject. Scoped tight on purpose: only the attribute. The subscription frame tag stays `"entity"` (it's a hardcoded literal independent of the attribute name), the route DSL `{entity}@{concept}` keeps its `entity` slot, and the `dialog.name/referent`-backed query field stays `entity` too.

Then the part I'd been avoiding: the stored attribute URIs themselves. `xyz.tonk.view/model`, `.../artifact/model`, `.../tile/model` to `/concept`. These are the dialog-db keys facts live under, so renaming them orphans any existing repo's view/artifact/tile concept links. Decided no migration, the repos are disposable and fresh ones re-seed from core.yaml. Worth being explicit that this is a data-losing change, not a pure refactor.

The recurring trap was wasm-only tests. They compile fine on native and even `cargo test --no-run --target wasm32`, but the assertions are runtime, so a stale `resolves_template("entity")` sailed through every local check and only blew up in CI under headless Chrome (which I can't run locally, the chromedriver/Chrome skew). Fixed it, then grepped exhaustively for the same shape rather than wait another 15-minute CI round to find the next one.
