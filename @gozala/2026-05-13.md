### Extending types with cardinality 

Alternative way to go about cardinality would be to alter key layout from

```` rust
/E/entity/attribute/value_type/value_hash
/A/attribute/entity/value_type/value_hash
/V/value_type/value_hash/entity
````

To layout which makes `value_hash` optional (well `x0` pad it or use some other sentinel)

 ```rust
 /E/entity/attribute/value_type/?value_hash
 /A/attribute/entity/value_type/?value_hash
 /V/value_type/?value_hash/entity
 ```

Idea then would be that cardinality **one** assertions will share a key, but for cardinality **many** it will appear indistinguishable from other assertions.

> [!NOTE]
>
> This has a real appeal because we leverage structure to enforce cardinality one and force resolution on merge as opposed to at query. It also nicely avoids secondary scans currently updates take when updating value index where you need to ensure that after asserting cardinality one it is indeed the only entry.

It does comes with a non-obvious tradeoff which held me back from embracing this - cardinality *one* data model is completely blind to the fact that there are bunch of facts in cardinality many space. In practical terms lets imagine two issue trackers where one model single assignee and other models multiple assignees, I would expect that former would show latest assignee as an assignee as opposed to no assignee at all. I wrote bunch more about this in [modeling cardinality](https://gozala.io/dialog/modeling-cardinality) which BTW assumes dialog embracing [divergence clock][]s that have being superseded by newer [version control][] design.

For what it's worth I still do think there is some merit to the idea of having special key for cardinality *one* assertions and maybe doing some hybrid approach where cardinality one queries fallback  to latest cardinality *many* assertion, open question is what happens when I cardinality *one* fact gets superseded, yet there is same value asserted as cardinality *many* ? Keeping later one seems counterintuitive as you could argue that intuition was to replace assignee, but at the same time you could probably argue that intention was not to remove assignee but to assign issue to specific assignee. 🤔 Given that application doing assignment was ignorant of a fact that there could be multiple assignees how could it have intended to not replace them. So maybe rational choice would be to remove fact from across cardinalities 🫠 Anyway I get stuck looping here so we end up not having that special entry for cardinality one.

## Racy Evaluation is back

Got sidetracked trying fixed race I thought I fixed yesterday. If you type `per` pause, you'll get LSP report

> [!CAUTION]
> Asserted notation expects a mapping at the document root (head → body).

Then you type `son:` but nothing happens. If you type quickly before LSP broadcasts diagnostics then you get results printed out. For the context `tonk-code` block dispatches `idle` event when editor is idle for preconfigured duration, and handler posts typed code to `/repository/home/branch/main/evaluate?transact=false` in order to provide live feedback, but it only does so if there are no error diagnostics. The race that was taking place is you get diagnostics late and now editor thinks there is an error suppressing evaluation.

Fix was to stop guessing freshness inside `<tonk-code>` and let the LSP tell us directly. Our server was sending `null` for the document version in `publishDiagnostics`; once it echoes the version it analyzed, `@codemirror/lsp-client` drops mismatched-version frames per spec, so every diagnostic the editor sees is provably current. With that primitive in place the `idle` event went away entirely — `<tonk-code>` now fires a single `diagnostics` event per fresh server frame, consumers auto-evaluate directly off that, and the editEpoch / diagnosticsEpoch / idle-timer state machine collapses to nothing.

## tonk-display

Originally `tonk-concept` component meant to be stepping stone to implementing something that is more like what `tonk-display`. General ideas is we have concept of a **view** is a named description, of how specific **concept** can be displayed through an HTML template. 

```yaml
concept!: &view
  description: HTML template used for displaying a concept
  with:
    name:
      description: Name of the view
      the: xyz.tonk.view/name
      as: text
    model:
      description: Concept being displayed
      the: xyz.tonk.view/model
      as: entity
    display:
      description: HTML template used for displaying source entity
      the: xyz.tonk.view/display
      as: text
```

Then given some concept like 

```yaml
# Define the concept being displayed.
concept!: &greeting
  with:
    message:
      description: Message to be displayed
      the: xyz.tonk.greeting/message
      as: text
```

You can define a view for it

```yaml
view!:
  model: greeting
  name: "basic"
  display: |
    <p class="greeting">{message}</p>
```

Assuming above concepts definitions exist and an instance like this

```yaml
# Example instance of the greeting concept.
greeting!: &demo
  message: Hello, world!
```

You can use web component to display  **greeting** with a **basic** view

```html
<tonk-display entity="did:key:zThing" model=greeting view=basic />
```

Admittedly not an impressive view, but interesting things happen under the hood. Web component subscribes to a query that is roughly as follows

```yaml
# Find concept greeting for the entity  
greeting:
  this: did:key:zThing

# And fine view for the concept named "basic"
view:
  model: greeting
  name: "basic"
```

Now if state of the entity changes view reactively updates. If the view definition itself changes rendered view reacts to that also because of the above query.

Web component uses another `token-view` web component which does actual rendering, but isn't reactive it just given a template and model knows how to render it and incrementally update it. In other words `tonk-display` handles subscription and when things change it updates rendered `tonk-view`.

It is also worth noting that `view` attribute is optional, and if omitted `tonk-display` renders [wa-carousel][] with all the views the available views for the concept allowing you to swipe between them. In fact if there is no view defined for the concept then `tonk-notation` web component is used to render syntax highlighted concept providing inspection view. Like before `tonk-display` takes care of subscription and updates views whenever state or view(s) change. In fact if new view is defined it is immediately added to the carousel, because when view name is not specified query gets them all.

>  [!note]
>
> Idea with `tonk-concept` is to eventually be more like a deck of `tonk-display` elements as opposed to table is it was originally presented.

Currently this is all feels like basic reactive views, but this same machinery is going to power behavioral subsystem through inductive rules, which I'm starting to call effects. Here is the rough sketch of what that would look like

```yaml
# model for the counter
concept!: &counter
  description: Counter
  with:
    count:
	    description: Current count on this counter
  	  the: xyz.tonk.counter/count
    	as: signed-integer

# view of the counter
view!:
  name: Counter
  model: counter
  display: |
    <div class=counter>
      <button onclick name=Increment>+</button>
      <span>{count}</span>
      <button onclick name=Decrement>-</button>
    </div>

# behaviour of the counter defined as effects
effect!:
  assert:
  	counter:
      this: ?this
      count: ?count
	when:
    # Counter exists
    - counter:
        this: ?this
        count: ?last-count
    # there is increment-counter associated on this counter
    - command:
        this: ?this
        name: Increment
    # Derive count by incrementing last count by 1
    - +:
    		of: ?last-count
        with: 1
        is: ?count
```
