## Catching Up

### Polling Frequency

> The quickest fixes are to backoff polling on idle tabs and to cache the UCAN authorization, though in the future it could be interesting to use a Durable Object that pings clients when the revision cell moves so the client can intelligently pull only when there are changes to receive. At the current scale that might not matter, but in the future it would probably be much cheaper and worth it.

I think caching revision reads is a good idea and in fact we could probably even pre-sign revision read URLs with a higher TTL e.g. day (can't recall what is max in S3). This way we'll reduce requests to `/ucan` significantly. If you need to sync cache will not help there, but it's definitely worth doing.

As of backgrounds tabs aggressively polling that is not exactly right (unless that has changed), we should have sync engine that schedules polls based on activity if you've changed state locally it will be put in a high priority poll bucket. If tab is active (issuing queries) it's next high priority everything else still gets polled but under much lover priority.

We have not really calibrated frequency here and it is worth doing.

> [!warning] 
>
> I'm less eager to adopt durable objects, as it introduces infrastructure subtle infra dependency. We may have to do it still, but I'd prefer to exhaust our other options before going down this route.

One other idea worth exploring is actual broadcast of updates, potentially over WebRTC so peers can broadcast when they update providing a real time signal to everyone online. In fact they could even broadcast blocks they've created allowing peers to catchup without even polling anything.



## Accounts

### Creation time

> Now, you must create an account with email and passkey before creating a space.

I don't like having to create account before you create a space. I think right approach is to create account before you're able to share space (recover access on another device). Basically you create an account when you need to go multi-device.

> Devices are first-class and revocable. You can see every linked browser and CLI and cut one off. 

How do you actually cut one off ? As in do we have UCAN revocations implemented, unless we do we can't really revoke access we simply don't expose delegations I think.

### Less services the better

> our account service merely holds delegation chains that could be interoperable with competing account/access services in the future

I'm not yet sure what the account service is, but I do think account should just be another space / db where we store delegations. When you link profile following should take place:

1. Profile should be handed delegation from account to profile
2. Profile uses that delegation to access account db and obtain all the delegations stored there.
3. Profile delegates everything back to account (power-line delegation).
4. Profile delegates from all local spaces to an account

Last one could in fact be manual interaction. For example we can show that spaces aren't recoverable _(because they're not linked to any account)_ and have a way to setup recovery by linking to an account, which simply does power line delegation to account.

### Permissions

>  Since the data is local and unencrypted we can’t enforce a proper mapping. Instead, we show solely the spaces that belong to the current account

We do not enforce read permission (by design) that is if I have data locally I should be able to read it, but I'm pretty sure we do enforce write permission that is if operator has no write access it will not be able to transact. There is a chance this does not work exactly this way, but if so we should fix it.

There has also being previously discussion whether it should be possible to write locally even if you have no authorization, which I think is defensible position. You can write but you won't be able to publish changes under that database name because you don't have a permission from it, but later if you obtain permission you'll be able to then.
