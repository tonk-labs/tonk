# July 8th

## Sync was starving everything, and it was two separate bugs

The complaint was simple: with sync on, reload and navigation drag; pause sync and it is visibly faster. Sync also finds nothing new yet still slows things down. I was sure it was contention but not where, so I stopped guessing and profiled. Timestamped logs at every shared chokepoint (the AppState lock, the pull, the pause handler, the DOM paint) plus controlled experiments that raced a query against a sync. The AppState read lock was innocent, waits were always 0ms, reads interleave as designed. The real culprits were two, in different layers.

First, dialog. `StorageCache::get` held one global cache mutex across the backend network fetch on a miss. Every block read in the whole worker funnels through that lock, so on the single-threaded service worker one in-flight fetch froze all other reads. A query on a completely different repo blocked 3ms to 1787ms behind a space sync, which is the tell: not per-handle, whole-thread. The fix is the textbook one, never hold a mutex across IO: drop the lock before the fetch, re-acquire only to insert. Two concurrent misses may both fetch, harmless since blocks are content-addressed. That alone took a no-op sync from 6-8s to about 600ms and a cross-repo query during sync from 1.8s to 0.3s. Shipped as dialog #373, tagged tonk-2026-07-07, and tonk bumped to it (#574).

Second, and this was the "we are doing something stupid" one Irakli suspected: the reactor re-polled every subscription on the branch after every pull, even a no-op. A background sync that finds nothing still re-ran the whole branch's queries. That is why sync-on felt slow and pause felt fast. Gate it: compare the tree before the pull to the post-commit revision, only re-poll if it actually moved. Subtlety that decides where the gate goes: pulls never touch the session overlay, but overlay writes (the sync status stamp the pause dot reads) change query results without moving the tree. So the gate belongs at the pull site, not in the poll path, or overlay-driven updates would silently stall. Idle syncs now do zero subscription work. #573.

Together, query-during-sync went from ~1.8s to ~0.4s and idle sync is nearly free.

Irakli asked whether push re-polls too. It does not, and by design: push doesn't change local state, so the reactor's push already skips the poll. Audited the rest of the poll callers while there. Transaction, overlay write, and import all legitimately change results and should poll (import always commits assertions, so no no-op case). Pull was the only one wrongly polling on a no-op. So the poll discipline is now: poll when local state actually changed, never on a no-op sync.

## Deferred: the evaluate read-lock was a red herring

Early in the hunt I found `/evaluate` still takes an AppState write lock while its sibling `/transact` was migrated to a read lock in the June 22 less-locking work. It looked like the contention. Profiling proved it was not, the lock waits were 0ms. Switching evaluate to a read lock is still correct hygiene and claim/assert + claim/retract are dead routes worth decommissioning, but neither is urgent now that the real cause is fixed. Parked.

## Smarter polling, and the rule complication

Even a pull that DID change the tree re-runs every subscription, and a status stamp re-polls the whole branch (~500ms). The better model, which Irakli framed: a subscription is a query over known concepts and attributes, and a transaction carries the attributes it asserts or retracts. Intersect them. If a transaction touches no attribute the subscription reads, skip it. The infrastructure is mostly there: schedule_poll already has the Changes in hand and throws them away, each Subscription holds its ConceptQuery, and commands already do attribute-indexed dispatch via trigger_attributes. The complication is deductive rules: asserting a premise attribute can change a query over a concluded attribute, so the affecting set has to be closed over the rules. Dialog already models rules as head-cacheable `db.rule/conclusion` facts, so the closure is buildable and invalidates when the head advances. And a tree-moving pull is the escape hatch, it must re-poll everything since a wholesale tree swap is not attribute-scoped. Real work with correctness stakes (a wrong skip is a silently stale UI), so it is a design-doc-first job, not started.

## Next lever: a service worker per space

The fixes above stop sync from blocking other work, but sync still occupies the one thread for its ~600ms of network per tick, and everything still shares a single service worker. The structural answer is a service worker per space. Each space gets its own worker, its own storage scope, its own reactor and sync loop, so a slow sync on one space cannot touch another, and the profile chrome (hub, FAB) runs in yet another that never syncs a space at all. This is the real parallelism, not cooperative yielding on one thread.

It is a big change and the hard parts are known. Scope: today one SW owns every repo; per-space means routing `/space/:did/*` to a space-specific worker and partitioning storage so workers do not fight over the same IndexedDB. Coordination: the profile branch is shared (membership, replica index, the FAB reads it cross-space), so either it lives in a coordinator worker the space workers message, or it is replicated read-only into each. Lifecycle: spin a worker up on first navigation to a space, tear it down when the last client leaves, which is the SW-restart-survival problem multiplied. And the bridge already assumes one host relay per document; N workers means N relays or a router in front. Worth it because it turns sync from a shared-thread tax into an isolated per-space background task, but it wants its own plan before any code.

Alternatives short of that, in increasing cost: sync only when the thread is idle (defer while a query or transact is in flight), sync the in-view branch first and defer the rest to the next tick, or run sync concurrently rather than serially per branch. Cheaper, partial, and they do not remove the shared-thread coupling the way per-space workers do.

## The type-system arc is done: recursion, then subscriptions that maintain themselves

The dialog roadmap Irakli set (composite types, stratification, subscriptions) landed as a nine-PR stack, [#375](https://github.com/dialog-db/dialog-db/pull/375) through [#382](https://github.com/dialog-db/dialog-db/pull/382), each gated on the full suite (1687 tests) and clippy clean.

The type-system half first. Composite types (#375) let a concept field declare `#[dialog(conforms = Employee)]`, enforced structurally by conjoining the target concept as a premise, and ordered variants desugar to negation of the earlier arms, so "first variant to conform wins" is plain stratified Datalog. Stratification itself (#376) is the Apt-Blair-Walker dependency graph with Tarjan SCCs; negation through a cycle is rejected at query time, never at registration, because replicas must converge on whatever rules arrive. Then the fixpoint evaluator (#377): semi-naive over the queried concept's SCC, compute the closure once, join caller bindings against it. Ported the recursion tests from the old JS `loop.spec.js` and the nl-datalog Simpsons program so recursive rules have real expected-value coverage.

> [!note]
> The tautology rule (`X :- X`) returns empty under least fixpoint. The legacy JS engine returned the base rows there, which was a deliberate divergence, now pinned in a test with a comment saying so.

## Subscriptions without DBSP

We had already rejected DBSP for this: retained operator state re-materializes exactly what a partial replica exists to avoid. The shape that fits is pull-driven demand transformation. A subscription records its ==demand cover== at the Select boundary, the key ranges it actually touched, misses included. On poll, a cover-scoped tree diff (`differentiate_within`) prunes any subtree whose span misses the cover without loading it, which is the partial-replica-friendly property: a change outside your cone costs you nothing, not even reads.

When the diff does intersect, DRed-style maintenance instead of recompute: over-delete the affected entities, re-derive goal-directed through `Application::restrict`, diff before against after. That started gated to flat entity-local rules, then grew. Delta-join discovery (#380) handles cross-entity rules at arbitrary nesting depth: bind the changed fact into whichever premise it matches, sideways-join the rest, project the head entity, and run that bottom-up over the concept graph (pinned with a Chief to Report to BadgeHolder test where a badge change three layers down maintains the top query).

Chasing that surfaced a pre-existing hang: the repository's rule resolution did no recursion analysis at all, so a recursive durable rule recursed top-down unboundedly. Now it walks the reachable rule set, checks stratification, and attaches the recursion closure.

## Recursive cones go incremental too

The last two increments make recursion itself incremental rather than recompute-on-change. The subscription retains the SCC's answer table across polls (#381); additions extend it semi-naively, and the source premise stays in the sideways join on purpose, since the point lookup re-verifies the fact and preserves cardinality-one winner semantics. Deletions were the hard half (#382), and the trap is worth recording.

> [!caution]
> You cannot find DRed suspects by evaluating the deleted fact against the store: the fact is gone, so its joins evaluate to nothing and you find zero suspects. Over-delete by pattern-matching the retained answer table on the head-operand bindings instead. The store tells you what is derivable now; only the table remembers what was.

Re-derivation then rescues survivors (delete edge d to c from a diamond and the (d,c) ancestor pair dies but paths through the other side live), and delta rounds propagate the losses. The ancestor lifecycle test runs extensions, a deletion, and a post-deletion extension with zero recomputes end to end. Rebuild remains the fallback for the shapes where DRed is unsound: a deletion matching a negated or optional premise (rows can appear when facts disappear), or two premises of one body matching the deletion set.

Closing decisions with Irakli: the memcomparable value-key encoding is his separate index workstream, not a subscription dependency (covers inherit the tighter ranges automatically when it lands, so the dep is unlinked in beads), and GC is real but not urgent, since pinning is trivially satisfied while nothing collects.
