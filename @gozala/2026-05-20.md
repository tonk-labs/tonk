## 💡Queries inside markup

I have being thinking it might be good idea to have queries inside script tag in the guest iframe of the tonk-portal, it would be same query you can type now in the editor for evaluation and it's the same as what you pass into slide. Neat thing about it is that sort of works around lack of first class support for graph queries, yet we already do it in the evaluation endpoint. Here is the example of the page that will be loaded in the iframe

```html
<html>
  <script language="application/dialog+yaml">
    # figure out entity being rendered 
    environment:
    	subject: ?list
    
    # query subject as a todo-list
    todo-list:
      this: ?list
      name: ?list-name
    	item: ?todo
    
    # query items of the todo-list
    todo:
    	this: ?todo
    	done: ?done
    	title: ?title
  </script>
  <script type=module language="text/javascript">
  	self.onmessage = ({ data }) => {
  		console.log(`🔄 Received updates for ${data.list} named ${data["list-name"]`)
  	}
  </script>
  <body>
    <!-- Your view here -->
  </body>
</html>
```

General idea is that artifact declares everything it needs in terms of state going to arbitrary depth of graph and query things in either direction and then simply gets updates via `postMessage`. If there is an error with a query, host will need to render different page describing a problem and maybe even offer a way to correct with built in editor that has that query in the buffer and offers diagnostics to illustrate where the error is, as you type shows queries etc… Once query fixed it can take you back to the artifact.

> [!warning]
>
> One downside of this is you may want to get some state once without being updated every time it changes, which becomes  impossible to express with this, but if things are fast maybe answer is you just don't care and ignore those updates 🤷‍♂️

## Causing Effects

This does not really cover how do you go about altering state if you need it ? I think we could probably do it same way also with a named script tag so you can refer to it

```yaml
<html>
  <script id="update-todo-status" language="application/dialog+yaml">
    # get parameters from the environment
    environment:
    	todo: ?todo
    	done: ?done
    
    # and update desired todo
    todo!:
    	this: ?todo
    	done: ?done
  </script>
  <script id="create-new-todo" language="application/dialog+yaml">
    # get parameters from the environment
    environment:
    	title: ?title
    	list: ?list

		todo!:
			this: ?todo
			title: ?title
			done: false
		
		todo-list!:
			this: ?list
			todo: ?todo
  </script>
  <script type=module language="text/javascript">
    export updateStatus = ({todo, done}) => {
  	  postMessage({ 
  	  	"update-todo-status": { todo, done }
  	  })
  	}
  	
  	export addTask = ({list, title}) => {
  		postMessage({
  			"create-new-todo": { list, title }
  		})
  	}
  </script>
  <body>
    <!-- Your view here -->
  </body>
</html>
```

### Inductive Rules

Above may look familiar, if you've seen my [entry about effects](./2026-05-17.md#weekend-journey-into-effects), main difference is that what is passed in environment paired with a name is what I called abilities, and you caused them by asserting them and rest of update logic is then described as an effect. My thinking evolved a bit since my last entry about effects and I'm going to write about that, but in the meantime here is how above could be expressed with effects (I hope in a near future)

```yaml
concept!: &update-todo-status
  description: |
  	Signals environment to update `done` field of the specified `todo` concept.
  # Non durable concept which exists for a single update cycle
  transient: true
  with:
    todo:
      description: Todo item to be updated
      the: xyz.tonk.env/todo
      as: entity
    done:
      description: Done value to be set
      the: xyz.tonk.env/done


rule!:
	description: |
		Rule that updates `done` of the todo concept when `update-todo-status`
		is asserted. You can activate it by following assertion
		
		update-todo-status!:
			todo: did:key:zm9T0d0
			done: true
	# Rule says do todo!: { this: ?this, title: ?title, done: ?done }
	assert!: todo
	# when we have todo: { ?this, ?title }
	# and update-todo-staus: { todo: ?this, done: ?done }
	when:
		# when there is a todo
		- assert: todo
			where:
				this: ?this
				title: ?title
		# And a update for that todo
		- assert: update-todo-status
			where:
				todo: ?this
				done: ?done
```

It may feel backwards for a moment, but you'll get used to it if you give it a chance, I promise! There are few benefits to this over the script tags that I'd like to call out:

### Understanding system

Our rule now declares that it asserts `todo` concept, which means we can query for all the rules that affect specific concept and display them in the under the hood view. And we can have toggles that enable or disable them.

Not only we can identify effects, we can also identify all causes like `update-todo-status` because we can query all the (inductive) rules that assert concept & then query their premises identifying **transient** ones, which are the ones that would cause these effects to fire

> [!note]
>
> Transience is the evolved optimization trick from my previous entry about effects. Rule can only produce something when all of its premises hold. And if we have transient concepts that exist for single update cycle that means at every update we only need to trigger rules that have asserted transient in their premises, which would be just a handful ✨

This means not only we can visualize effects that affect the concept, but also (transient) concepts that in relation to those effects that will trigger them. In fact we could even have way to trigger them right from the UI, or have a way to suspend execution when (transient) concept is assessed and let you step through the process to see how effects fire and then how changes propagate. In fact we could also have way to go from (transient) concept to all the effects it will trigger and the concepts those effects will update.

### Naming is optional

One other interesting aspect is that we could have written up our rules as follows, without squatting names that would inevitably collide once past certain threshold

```yaml
concept!:
	this: ?update-todo-status
  description: Updates status of the todo
  transient: true
  with:
    todo:
      description: Todo item to be updated
      the: xyz.tonk.fx/todo
      as: entity
    done:
      description: Done value to be set
      the: xyz.tonk.fx/done


rule!:
	# Rule says do todo!: { this: ?this, title: ?title, done: ?done }
	assert!: todo
	# when we have todo: { ?this, ?title }
	# and update-todo-staus: { todo: ?this, done: ?done }
	when:
		# when there is a todo
		- assert: todo
			where:
				this: ?this
				title: ?title
		# And a update for that todo
		- assert: ?update-todo-status
			where:
				todo: ?this
				done: ?done
```

We don't need names everything is hash addressed entity already so we could just interlink things and be on our merry way. Instead of naming we can simply have a fuzzy search where you type things and get suggestions categorized by effects, causes, concepts etc…

### Discovery

Not only you can understand system if you are able to see relations between cause & effect, but those relations being in the database itself means you can discover various patterns. I think this can be a game changer for agentic systems, because agents could discover relations with fairly simple queries as opposed to having to digest large code base to gain understanding. As far as I can tell that takes up a lot of context space and uses up a lot of tokens. I also suspect that if environment allows you to see relations it can make local LLM models capable of aiding users in shaping environment into whatever they need.

### Prototypes

I had a niri like tiling layout working, a horizontal strip of columns where the strip scrolls sideways and each column is a vertical stack of tiles. It worked but it did not feel right. Several attempts to fix the feel, going in different directions, none of them landed. So I changed approach and started building standalone static HTML prototypes instead of keep changing the working system. The implementation gets touched again once the prototype is settled.

I tried a bentobox style layout and spent a while on different sizing ideas, how tiles should claim space and divide a column. Vjeux's [Google+ image layout algorithm](https://blog.vjeux.com/2012/image/image-layout-algorithm-google-plus.html) was a useful reference for spatial layouts and how to size things along a row. I also chased a few [browser trail](https://www.freecodecamp.org/news/lossless-web-navigation-with-trails-9cd48c0abb56) inspired ideas, treating the board more like a path you scroll through. None of that panned out.

In the end I circled back to niri, but with a twist. Tiles get their height from their content rather than from a fixed grid, and can then be resized from there.

Width still goes through preset sizes, XS, S, M, L, XL. These are the discrete steps a column can snap to, no awkward in between widths, so columns always stay on the grid and stay legible. XS is roughly one mobile screen width, the smallest sensible column, and S, M, L, XL step up progressively from there.

Anchoring XS to a mobile screen also handles mobile for free. On a narrow screen the board is just a stack of XS columns shown one at a time, on a wide screen the same columns lay out side by side.
