## Subviews

A todo list contains todo items. That's the simplest possible nesting and it's the one that breaks our current rendering model in interesting ways. Let's sketch the data first:

```yaml
concept!: &todo-list
  description: Todo list
  with:
    name:
      description: Name of the list
      the: xyz.tonk.list/name
      as: text
    item:
      description: Item in the list
      the: xyz.tonk.list/item
      as: entity
      cardinality: many

concept!: &todo-item
  description: Todo item
  with:
    title:
      description: Title of the todo
      the: xyz.tonk.todo/title
      as: text
    done:
      description: Completion status
      the: xyz.tonk.todo/done
      as: boolean
```

`item` is `cardinality: many` and points at `todo-item` entities. The list "has" items in the loose sense — each item is a separate entity with its own facts. A view of the list needs to display each item somehow.

### The obvious shape

```yaml
view!: &list-view
  model: todo-list
  name: "basic"
  display: |
    <article>
      <h2>{name}</h2>
      <ul>
        <li subject={item}>
          <tonk-display model=todo-item view=basic source={item} />
        </li>
      </ul>
    </article>

view!: &todo-view
  model: todo-item
  name: "basic"
  display: |
    <div>
      <input type=checkbox value={done} />
      <span>{title}</span>
    </div>
```

The outer list view iterates over `{item}`, each iteration mounts a `<tonk-display>` for one todo entity, and that inner display takes care of subscribing + rendering. Tidy. It works for the basic case.

It also opens **1 + 2N** subscriptions for N items: one for the outer list, and per item one for the todo's data plus one for the view template. The view-template subscriptions are wasteful — the template is identical for every row — but acceptable.

The real problem isn't subscription count. It's ordering.

### How do we order items?

Items come back from a `cardinality: many` query as a set, not a list. The worker doesn't promise any particular order across polls. If we want sorted-by-position display, the position has to come from somewhere — and it lives on the *item* entity, which the outer list view doesn't query.

This is the wall. The inner `<tonk-display>` knows the item's `position`; the outer view doesn't. CSS can sort children with `order: <integer>` but `order` can't read a string-valued attribute from a child, and `attr()` typed values still aren't shipped. So the outer can't sort by an attribute it can't see, and the inner can't influence its position in a list it doesn't know it's part of.

I considered a few escape routes:

- **Children publish their sort key upward.** Inner element resolves, sets `data-order=<position>` on itself, outer observes via `MutationObserver` and reorders. Layering inversion. Items visibly shuffle as they finish loading. No.
- **Move the sort into the query.** Outer query joins with the items' fields, brings the sort key back in the same fetch. Right answer architecturally — but dialog-query doesn't support nested projection yet. On the roadmap, not in our hands today.
- **Project the sort key separately at the outer scope.** Outer view subscribes to a *different* concept on each item — one that exposes only the fields the layout cares about — while the inner display keeps doing its own view-rendering subscription. Tractable now and decouples cleanly: outer asks for layout data, inner asks for display data, neither reaches into the other.

The third option leads here:



```yaml
concept!: &ordered-item
  description: Position of a todo within its list
  with:
    order:
      description: Order in which item is presented
      the: xyz.tonk.todo/order
      as: text

view!: &list-view
  model: todo-list
  name: "basic"
  display: |
    <article>
      <h2>{name}</h2>
      <ul>
        <template for={item} as=ordered-item>
          <li data-order={item.order}>
            <tonk-display model=todo-item view=basic source={item.this} />
          </li>
        </template>
      </ul>
    </article>
```

The `<template>` element does iteration + projection: for each `{item}` URI in the outer scope, subscribe to `ordered-item` and expose its fields (`{item.order}`) for the wrapper to use. The wrapper then carries `data-order` and the renderer sorts on that. The inner `<tonk-display>` does what it always did — subscribe to `todo-item`, render via `todo-view`.

> [!warning]
>
> 1 + 2N + N subscriptions for N items now (outer + per-item ordering + per-item display + per-item view-template). That's a regression on the count we already weren't loving. The principled fix is dialog-query nested projection that fuses the per-item subscriptions back into the outer query. Until then this is the price.

### Can we make the inner element less expensive?

If the outer template already brings back the data each row needs (`{item.order}`, plus `{title}` and `{done}` if we extended `ordered-item` to include them), then the inner element doesn't need to re-fetch. It just needs to *render* the view template — and the view template is the same for every row, so it can be fetched once for the whole iteration.

That suggests something like:

```yaml
concept!: &ordered-todo-item
  description: Todo item with its position in the list
  with:
    title:
      description: Title of the todo
      the: xyz.tonk.todo/title
      as: text
    done:
      description: Completion status
      the: xyz.tonk.todo/done
      as: boolean
    order:
      description: Order in which item is presented
      the: xyz.tonk.todo/order
      as: text

view!: &list-view
  model: todo-list
  name: "basic"
  display: |
    <article>
      <h2>{name}</h2>
      <ul>
        <template for={item} select=ordered-todo-item display=todo-view sort=order>
          <li><slot/></li>
        </template>
      </ul>
    </article>
```

`<template>` now owns four concerns:

- `for={item}` — iterate over the cardinality-many field.
- `select=ordered-todo-item` — per item, subscribe to this concept (one fetch per row, brings back everything the view needs).
- `display=todo-view` — fetch this view template *once*, share across all rows.
- `sort=order` — order the rendered rows by the projected `order` field.

`<slot/>` is where the view's rendered output lands. The wrapper (`<li>`) is the author's call; the view chooses what fills the wrapper.

The subscription count drops to N + 2 (one outer, one shared view template, one per item for the merged ordered-todo-item concept). The race goes away because the outer query brings back the sort key before any row mounts. The inner display vanishes — its job was redundant once the outer query carries everything.

> [!note]
>
> `<template>` is becoming a dual of `<tonk-display>`. Display = "given an entity, fetch and render." Template = "given a list of entities, fetch each (with optional projection), render each via a chosen view, place into a wrapper." Both do subscriptions; both render; they sit on opposite ends of "one vs many."

This shape feels like the right destination. It's a real redesign though — the iteration mechanism becomes a subscription orchestrator, `<slot/>` gets template-only semantics distinct from Shadow DOM slots, and `<tonk-display>` either deprecates or becomes sugar for the single-row case.

### The version I almost wrote

While sketching this I kept reaching for something cleaner:

```yaml
view!: &list-view
  model: todo-list
  name: "basic"
  display: |
    <article>
      <h2>{name}</h2>
      <ul>
        <template for={item} select=ordered-todo-item sort=order>
          <li><tonk-embed source={item} view=todo-view /></li>
        </template>
      </ul>
    </article>
```

Pull view selection off `<template>` and onto a `<tonk-embed>` element that fills the slot itself. Reads nicely — each concern in its own element. Problem: views are keyed by `(concept, name)`, not by name alone. `<tonk-embed view=todo-view>` is ambiguous. Is `todo-view` defined on `ordered-todo-item` (the concept the template projected) or on `todo-item` (the underlying entity's "real" concept)? The `<template>` knows about the former; the embed wants the latter; nothing connects them without smuggling context through DOM scope, which is exactly the inversion I was trying to avoid.

So the cleaner shape isn't actually expressible without dropping the `(concept, name)` view-identity convention or threading concept context through the markup. Both feel worse than putting `display=` on `<template>`. Filed under "I wanted this and couldn't make it work."

### What I'm landing on

For now the marker-attribute scheme (`<li subject={item}>` lifts iteration to the `<li>`) stays. It handles the no-sort case. The `<template for= select= display= sort=>` redesign is the right next step but it's a meaningful refactor, larger than the immediate incremental-update work:

1. Land keyed incremental updates on the current scheme so adding an item doesn't re-render the whole list. (Done today.)
2. Specify and implement the `<template>` redesign as a focused initiative.
3. Push on dialog-query nested projection so we can collapse the per-item subscriptions.

Steps 2 and 3 are independent — the redesign is worth doing even without nested projection, because shared view-template fetching alone saves a subscription per row. Nested projection then turns the per-item data fetches into a single outer fetch and we're done.
