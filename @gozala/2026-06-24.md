## Experience with Tonk CLI

As I worked through reviewing large PRs that add optionals to query engine I felt a need to create task list for my agent to address. I thought I'd use tonk cli for this, define couple of concepts and ask claude to use tonk to find tasks to do, update status etc… Basically something like [beads](https://gastownhall.github.io/) but with just handful of concepts. 

To be honest I found our CLI not very pleasant, it's just `eval` of the notation without a good input mode. I actually end up creating space in the browser and defining concepts there as I have autocomplete and diagnostics readily available. Then doing `tonk pull` to get it the cli

But as I was doing this I ran into the issue when evaluating 

> [!caution]
>
>  field "title" value expected a bare symbol (name lookup) or a URI (`xyz.tonk/foo`, `id:foo`, etc.) isn't supported here

```yaml
attribute!: &issue/title
  description: Issue title
  the: io.gozala.issue/title
  as: text

# ....

concept!: &issue
    description: |
      Work items with priorities, types, labels, and dependencies
    with:
      title: issue/title
      description: issue/description
      type: issue/type
      priority: issue/priority
      status: issue/status
```

It appears that when I introduced support for namespaces in names I taught the anchor grammar to accept `/` but forgot to teach the reference grammar the same thing. So I could declare `&issue/title` but never point back at it. The value classifier saw `issue/title`, decided it was neither a dotted-domain URI nor a slash-free symbol, and fell it through to a string literal which the analyzer then rejects.

The fix is to treat a `/`-joined bare identifier as a qualified symbol, just a name lookup like a bare symbol is. Now reference grammar is symmetric with the anchor charset, and multi-segment names like `space/route/view` work too. The analyzer needed no changes, it already resolves symbols to the attribute entity.

> [!note]
>
> One small cost: a MIME-shaped literal like `text/html` now reads as a symbol, so it has to be quoted as `"text/html"`. Turned out that only showed up unquoted in one test fixture and a couple of guide docs, everywhere else it was already a parsed string.

Fixed in [#533](https://github.com/tonk-labs/tonk/pull/533).

## CLI dry-run

While teaching Claude the skill it tried to "test" a bug create with `--no-sync`, which it assumed was a dry run. It isn't. `--no-sync` still commits locally, it just skips the pull/push, so it left the branch diverged and then a push propagated a throwaway attribute to the remote. The CLI had no real preview at all, even though I added exactly that to the web `/evaluate` route as `transact=false` so the notebook can render query results as you type without committing.

So we taught the CLI the same trick. `slide eval --dry-run` runs analyze then query then plan and drops the transaction: matches come back, zero claims, revision unchanged. The machinery was already sitting there, `matches_after` is computed against the txn overlay before the commit decision, so the only real change was gating the `commit()` call and zeroing claims to match the worker's contract. It implies `--no-sync` so a preview never touches the remote.

> [!note]
>
> The installed binary on PATH is the old release without the flag, so the skill mentioning `--dry-run` is slightly ahead of what's shipped until this lands and I reinstall.
