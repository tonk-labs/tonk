# Revocation, actually enforced

The revocation work landed ([#748](https://github.com/tonk-labs/tonk/pull/748)), and most of the day was finding out that the parts I thought were done were the parts that were not.

The starting point was that we had our own artifact shape, our own `target_cid`/`path_hex` pair, and a screen that ran after authorization and re-derived the chain's structure from a second parse of the same bytes. Each piece looked reasonable alone. Together they were a second implementation of something the UCAN spec and dialog both already describe, so all of it goes: minting and verification through `RevocationChain`, and the service only answers two questions of its own now, do we hold data this could protect and have we recorded it already.

## The screen was weaker than the walk

Moving enforcement inside the chain walk is not just relocation. A screen outside the walk sees one flat set of issuers and has to apply it to every hop. For `a → b → c → d` that lets d's issuer revoke c: a principal that merely *received* authority withdrawing the grant it depends on. Dialog scopes candidates per link, the issuers at or above it plus that link's own audience, who may always disclaim what it was given.

I pinned exactly that difference by patching dialog locally to compute the flat set and running our tests against it. One test failed and the rest passed, which is the right shape: the property is real and only one test is watching it.

> [!note]
> Mutation testing kept earning its keep today. Three separate times a test I had just written passed with the thing it tested disabled. Writing the test is not the same as knowing it works.

## Fixing dialog instead of working around it

Our `expiry.rs` re-parsed every container to compute a validity window, purely so an expired chain could answer `401 Expired` instead of the `400 Malformed` the boundary produced. The walk already computes that window and compares it to the clock. It just could not *say* so: every typed `CheckFailed` reason died in `ContainerError::Invocation(String)` before the authorize boundary saw it.

`AuthorizeError` was written to mirror `CheckFailed` variant for variant, its doc comments say so arm by arm, and nothing ever populated the mirror. `notes/error-audit.md` in the dialog tree had already worked this out and called it follow-up scope: the client-side matching (`Expired` means refresh, `Revoked` means stop) "cannot fire for real verification failures".

So the decision travels whole now ([dialog#461](https://github.com/dialog-db/dialog-db/pull/461)). `TimeBoundError` also grew the bound it failed against and the instant it was judged at, which `Expired { expiration, at }` needs and could not previously get. Then `expiry.rs` deleted outright, about a hundred lines of duplicated parsing, replaced by a test asserting the status and typed body a client actually sees.

> [!caution]
> The same flattening existed a second time on our side: the native server helper rendered every authorization failure into `format!("Authorization failed: {e}")`, which `read_rejection` cannot parse, so every denial through it degraded to `Unclassified`. The typed reason was being destroyed twice on the way out.

## The account panel was not revoking anything

This is the one I would not have found on my own. Revoking a device from `/account` verifies a real signed artifact and then writes the account service's device list, which is a projection. Nothing consults it when a presign is authorized.

The response even says `"published": true`. It is a hardcoded literal.

```
after account-panel revoke, storage still works = true
if forwarded to the index,  cut off            = true
```

The existing e2e passed because it only asserted the revoked device can no longer *list devices*, an account-service row check. Storage was never in the test. So a user could revoke a stolen laptop, watch the row go grey, and the laptop would keep reading and writing.

`revoke_invite.rs` already had the correct pattern sitting right there: mint, verify, post to the access service, check the receipt. `account_devices.rs` did the first two and stopped.

## And one service is not enough

Then the same question again one level up. A device grant is `Subject::Any`, a powerline, so it is not scoped to a space and not to one access service either. Publishing to the account's own left the device serving every space synced elsewhere.

The directory already records a remote per space, so one `Query::<Remote>` over the account branch gives the distinct endpoints, no per-space walk. Every endpoint has to accept it: a partial publication is the dangerous outcome, the user is told the device is gone while something still answers it. A directory we cannot read refuses rather than silently narrowing the revocation.

The test runs two genuinely independent access services, own S3 and own index each, and checks both serve the device, then both deny it. Publish to only one and it fails, which is the point.

## Revocations do not expire

I suggested using the revoked delegation's own expiry as a KV TTL, since a chain past its expiry is refused on time anyway. That was wrong twice over.

`target_expires_at` is `None` for unexpiring delegations, and device grants carry no `exp`, so there would be no bound for exactly the revocations that most need to be permanent. And a TTL is not a cost tradeoff here: the index answers "was this withdrawn", so expiring a key flips that from yes back to **no**. Permanence is what the fact means.

Written into the index docs and onto the field, because a computed-but-unused expiry is an open invitation to the idea.

## Sessions

Checked while I was in here, since a session hop is minted offline and registered nowhere. Both directions work: the issuing profile can withdraw one session without disturbing its others, and withdrawing the powerline severs every session under it. Built the test from the shape `session::open` actually mints rather than from the `tonk-identity` helpers, which the live path does not use.

## Still open

A remote added *after* a revocation never learns about it. That is inherent to fanning out at revoke time; the durable fix is the access service asking on first contact, which is a design change rather than a patch.
