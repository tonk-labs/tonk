## Autocompletion

Over night I left Claude agent running with an instructions to implement [completion][textDocument/completion] capabilities so that as you type expressions in the cell it would show available concepts, their attributes and locally defined variables. 

After reviewing some of what got cooked up it became apparent that tonk-schema crate got bloated, now it also an analyzer, evaluator and was about to become introspection engine for the autocomplete. Instructed Claude to break out competition related code into `tonk-introspection` crate that will have `SystemIntrospection`, `RepositoryIntrospection` and `BranchIntrospection` traits that corresponding structs in the reactor will implement.

### Where it landed

Plan moved into `plan/auto-completion.md` first, covering the trigger model (`\n` for head/field, `?` for variables, no `:` because value position is too varied to auto-fire usefully), the source families, and what we explicitly don't do.

A new `tonk-introspect` crate carries the contract: `BranchIntrospection` (lookup_* + list_*) plus stub `SystemIntrospection` and `RepositoryIntrospection` slots so future code has a place to land. The legacy `analyzer::Resolver` becomes a `#[deprecated]` blanket impl so analyzer call sites keep building.

The LSP picks up three completion sources and a hover handler. Built-in concepts in head, concept fields inside body, and document-local variables on `?` are branch-free; they walk the registry and the parsed buffer. Branch-published concepts (and hover details) go through an `IntrospectionFactory` the worker injects via `Server::with_introspection`; the worker's `ReactorIntrospectionFactory` parses the document URI back to `(repo, branch)` and acquires a reactor session on demand. Hover dispatches by indent the same way completion does. A head identifier renders the concept's description and field list, a body identifier renders the backing attribute's qualified name with type/cardinality/description.

`<tonk-code>` got two ergonomics fixes alongside: Tab accepts the active completion popup (`acceptCompletion`, falls through to `indentWithTab` when no popup is open), and pressing Enter at the end of a header line like `person:` now opens the body indented one unit deeper instead of dropping back to column zero. The latter is a small `indentService` that runs ahead of lezer-yaml's prop and reacts when the line up to the cursor ends with `:`.

Reference completion at value position (the bare-symbol `name: person-name` form) is the one source family from the plan that didn't ship, noted as deferred.

## Accounts

I think it makes sense to think of account as a key pair, aggregating access across all the repositories. It can also be viewed as just another repository that happens to store [UCAN delegation][]s so they can be synced across devices. If we leverage [Passkeys][] we get access to the public key credentials across user devices without building out complicated infrastructure.

### Customers

An account does not imply it is registered with tonk service. Later can be accomplished independently. Roughly that implies account holder requesting their account to be registered as a customer of the service, by issuing signed request with the completed registration form e.g. providing email address.

I think registration request should [create stripe customer](https://docs.stripe.com/api/customers/create?lang=curl) and record an account's [did:key][] to stripe [customer id](https://docs.stripe.com/api/customers/object?lang=curl#customer_object-id) mapping, so in the future we could resolve it. As result it should delegate `/customer/` capability with `id = customer.id` policy on the service did to an account key. This would allow us to define various capabilities like viewing or [editing customer information](https://docs.stripe.com/api/customers/update?lang=curl) using account key.

> ⚠️ We really should use [did:web][] method to announce service key and receive invocations on `did:web` subject, so we'd be able to rotate keys as needed, unfortunately that would imply bunch of work in UCAN implementation so we could probably punt on that and use [did:key][] initially.

I think initially we could expose `/customer/info` capability that simply returns result produces by stripe's [customer retrieval](https://docs.stripe.com/api/customers/retrieve?lang=curl) API. Similarly we could also add `/customer/update` capability that uses stipe's [customer update](https://docs.stripe.com/api/customers/create?lang=curl) API to update it. We could also expose `/customer/delete` capability that uses stripe's [customer delete](https://docs.stripe.com/api/customers/delete?lang=curl) API to permanently delete it from stripe and delete our own account → customer mapping.

#### Billing

Customer could be considered inactive until billing is active. I think we should use [usage based billing](https://docs.stripe.com/billing/subscriptions/usage-based) and allow customer to [setup billing](https://docs.stripe.com/billing/subscriptions/build-subscriptions?ui=stripe-hosted) _(which requires embedding stripe's iframe if I recall correctly, so they deal with credit card entry etc)_. When subscription is set up, stripe's web hook will notify tonk service creating an opportunity for the service to issue delegation from service DID to account DID e.g. delegating `/consumer/` capability.

> 🤔 Alternatively we could fold that capability under `/consumer/` but ensure at invocation that customer at hand has subscription when performing actions that require subscription.

### Consumer

Customer accounts with service subscription will have a capability to add consumers to the service, specifically this means initializing (remote) repository managed by the service. For example `/consumer/add` capability could pass repository [did:key][] setting it up in service operated R2/S3 bucket. UCAN access service will stop issuing [Presigned URLs][] for object read/write's when there is no payed consumer linked to a repository.

> 💡 Note that this means any service customer can add arbitrary repository as consumer of the service and as long they continue to be payed customer service will provide replication for that repository. This means customer may have limited to no access to a repository being replicated.

If customer terminates subscription, system will need to drop all consumers they have set up, which in turn may render some repositories without active replica. We'd probably need to build some UI that would allow other members to set it up as consumer under their own account as long as they are customer of the service with active subscription.

### User Experience

I think serious challenge is to communicate to a user in clear terms what the account is and why (not how) is it different from what they're used to. I do would like to think of it as opportunity however, because not having to be customer to participate is pretty unusual yet good illustration of our values. When we do ask users to become customers we also need to explain why do we need that and explain how this directly pays the operational costs and if they don't use the service they won't be charged.

I think if we offer some service for free, it should be clear that their tonk labs account is donating some resources, but just as well any other account could do the same. I think ideally it should be something like user asking discount for a trial. I think Apple has is pretty well dialed, by asking you to create subscription with 1 Month or 1 Year free at cancellation at any time, they likely know the psychology around feeling like you're getting something for free as opposed to contemplating if this is something you should pay for. I think we can probably be both honest and playful about this, saying we do this because we know you want cancel, because it's that good 😊

## It should work Offline!

I think this app should really work offline, there is no good reason it doesn't. The data layer already runs locally and syncs opportunistically, it's only the shell that's currently network-bound. We do have a service worker but it doesn't [cache](https://developer.mozilla.org/en-US/docs/Web/API/Cache) static assets or `/` URLs, so a flaky connection still kills the page. I don't think there is much to it, we just need to intercept fetches in the SW, stash responses in a [`Cache`](https://developer.mozilla.org/en-US/docs/Web/API/Cache), and serve them next time. The [Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache) is essentially a map: `caches.open(name)` gives you a named bucket and you `put` / `match` `Request` → `Response` pairs into it. Roughly:

```js
self.addEventListener("fetch", (event) => {
  if (new URL(event.request.url).origin !== location.origin) return;
  event.respondWith(
    caches.open("app").then(async (cache) => {
      const hit = await cache.match(event.request);
      if (hit) return hit;
      const res = await fetch(event.request);
      if (res.ok) cache.put(event.request, res.clone());
      return res;
    })
  );
});
```

The harder question is what to do when a new build ships. Today the user gets silently upgraded on the next reload and there is no way back if the new version turns out broken. I'd much rather make the upgrade explicit, detect a new version and let the user opt in. Years ago I worked on [graphene](https://gozala.io/graphene) and the bit I miss the most about it is exactly this: as soon as we pushed an update a small, unobtrusive notification would appear offering the new version. Just "there's a new version, want it?" It felt respectful in a way most software doesn't. And if you didn't like the new version you could go to `about:config` and put the previous version's hash in to switch back.

I think we can do something similar here. The trick is to keep each build's assets in its own named cache. A small build-time manifest at `/version.json` would list the version and its asset URLs:

```json
{ "version": "a3f9c2d1...", "assets": ["/index.html", "/index-a3f9c2d1.js", ...] }
```

The SW stores each version's assets under `app-<version>` and remembers which one is current in a separate `meta` cache:

```js
async function install(version, assets) {
  const cache = await caches.open(`app-${version}`);
  await cache.addAll(assets); // atomic, rolls back if any fetch fails
}

async function setCurrent(version) {
  const meta = await caches.open("meta");
  await meta.put("current", new Response(JSON.stringify({ version, at: Date.now() })));
}
```

The fetch handler reads `meta.match("current")`, opens the matching `app-<version>` bucket, and serves from there. A version switch is just a write to `meta`, no asset re-download because both versions are already cached. Same for rollback: keep the outgoing version's bucket around as `previous`, and rolling back is another `meta` swap. Anything older gets garbage-collected by listing `caches.keys()` and deleting the names that aren't `meta`, `app-<current>`, or `app-<previous>`.

## tonk-display web component

Started sketching a sibling custom element that renders **one** entity instead of many. Where `<tonk-concept>` reads its template from a child you author on the page, `<tonk-display>` pulls the template from a `view` concept stored on the branch:

```html
<tonk-display
    entity="did:key:zGreeting…"
    model="greeting"
    view="basic" />
```

So the author picks a view by name for a given concept, and the worker tells the element what HTML to render. Two live inputs feed one renderer: a subscription on the matching `view` row (so editing the template on the branch swaps the DOM) and a subscription on the entity (so field changes patch in place). The renderer caches the last entity frame so either input can change first without losing the other.

The thing being looked up is a plain concept on the branch, a `view` row that ties a `(model, name)` pair to a `display` template:

```yaml
concept!: &view
  description: HTML template used for displaying a concept
  with:
    name:
      description: Name of the view
      the: xyz.tonk.view/name
      as: text
    model:
      description: Concept being displayed
      the: xyz.tonk.view/model
      as: entity
    display:
      description: HTML template used for displaying source entity
      the: xyz.tonk.view/display
      as: text
```

A concrete view is just another assertion against that concept:

```yaml
view!:
  model: greeting
  name: "basic"
  display: !text/html |
    <p class="greeting">{message}</p>
```

A few decisions worth flagging:

- **`model` and `view` should both be optional.** Missing `view` → render the concept fields as a generic `<dl>` fallback. Missing both → "tonk-inspect" mode, query all attributes on the entity directly. Missing `model` while `view` is set is the only real error (view resolution needs the concept to scope on).
- **State reflected as `data-state="loading|ready|empty|error"` on the host.** Stylesheets can decide whether to hide a missing entity (`display: none`) or surface a styled placeholder. The element itself never injects fallback chrome.
- **Template engine wants to be its own crate.** The `{field}` parser, binding plan, and DOM walker currently live in `tonk-concept` but aren't specific to it. Plan is to extract them into a `tonk-template` crate as the first commit; both elements then depend on it.
- **Refactoring `<tonk-concept>` to delegate per-row rendering to `<tonk-display>`** is a tempting follow-up but explicitly out of scope for v1.

> Plan in more detail: https://github.com/tonk-labs/tonk/pull/455

## Passkeys as account signers

Picking up the thread from the [Accounts](#accounts) note above: the account is a keypair, and [Passkeys][] give us that keypair across the user's devices without asking anyone to manage key material. Passkeys are backed by platform biometrics; the hard part (cross-device sync of the secret) is solved for us by the platforms. If dialog can mint a `Signer`/`Principal` that wraps a passkey,  we'll be able to sign [UCAN delegation][]s, and invoke capabilities without ever surfacing a key to the user.

**Passkeys do not sign the payload you hand them.** They wrap it: the authenticator concatenates `authenticatorData || SHA-256(clientDataJSON)` and signs *that*, where `clientDataJSON` carries the relying-party origin, the type tag, and the challenge (which is the only place our payload gets pinned in). That means a passkey signature is not a drop-in for a `Signer<S>` that produces raw ECDSA over `S`. UCAN can't be signed naively this way.

The way through is to treat the WebAuthn assertion as a *decorated* signature: capture `clientDataJSON` and `authenticatorData` alongside the ECDSA bytes, encode all three as a single varsig signature, and let the verifier re-derive the signed message at check time. The [varsig WebAuthn extension][] already maps to this exactly. Verifying a UCAN signed by a passkey then means: parse out the decorators, redo the `authenticatorData || SHA-256(clientDataJSON)` concat, confirm the challenge in `clientDataJSON` matches the multihash of the canonicalized payload, then run the inner P-256 verify. The chain still works because the *encoded* signature is what travels and what the verifier inspects.
