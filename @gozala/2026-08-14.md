# August 14

## Register space

Yesterday I described how I think we can make account (space) registration, but we also need to somehow register individual spaces so they appear in KV / D2 as registered and access service will allow reads / writes. I think we could do it through `/consumer/add` capability that allows account to add a member space in order to activate replication on our service. 

```json
{
  "cmd": "/consumer/add",
  "sub": "did:key:zAlice",
  "args": {
 		  "consumer": "did:key:zAliceDb",
    	"consent": { "/": { "bytes": ... }}
  }
}
```

> [!warning]
>
> We should make sure that consumer being added consents, which can be expressed in terms of delegation that represents an approval as shown below

```json
{
	"cmd": "/provider/add",
	"sub": "did:key:zAliceDb",
  "args": {
    "provider": "did:key:zAlice"
  }
}
```

In practice account creates a space and adds it as a consumer so they can simply create above delegation as a consent in fact we almost always make power line delegation to the account which can be used as consent as is, access service just needs to validate above claim from the consent, which will succeed because power line include all capabilities and then effectively enroll space into their account.

---

Once consumer is added to the space we record in the D1, KV and account repo record tells us that subject space is in provisioned state, which in turn will enable space to be replaced through our service.

> [!note]
>
> We can choose to limit number of consumer spaces account can have based on their plan and enforce that on `/consumer/add` invocation. This is business decision and it can be changes as needed. We probably should set high limit either way.

## Accounts without passkey

It came up in the discussion today that it would be nice if we could have sync working as trial for accounts even before they register. More importantly we'd like to do it before we ask user to create a passkey. I think we could have "trial plan" for accounts before they register, however I felt that we can not do it until we generate a passkey. I have came around to the idea that maybe we could do this without much trouble by doing something that @jackddouglas already proposed and I have mildly opposed, now I am realizing I was wrong and this use case is proof.

What we could do is generate non extractable key pair to represent **account** credentials. Then we allow accounts to get a trial by invoking `/customer/preview` that will mark that customer to be enrolled in `trial`. This will allow account to register single space via `/consumer/add` capability described above. Under trial period we can limit account to a single space and small amount of usage credits. When they run out of credits we will deny service asking them to enroll into free tier by invoking `/customer/enroll` capability (previously  described as `/customer/register`) that would go through:

1. Typing email address
2. Setting up passkey
3. Clicking received email
4. Accepting terms of service

After completing this steps they will enroll to `free` tier with a higher usage credits and perhaps ability to create more spaces.

When passkey is created derived profile key will be delegated all the access from the account key and profile will delegate everything back to the account effectively forming a union. This also would enable adding more passkeys which in turn will entail delegating unconditionally between the two.

> [!warning]
>
> There is one unfortunate side effect of this design. Access to space created with passkey A could be revoked from device with passkey B and vise versa. That is because at the time of creation delegation is made to a passkey based profile and if delegation from A → B is revoked all the delegations flowing from A get revoked also.

Solution here is to have a principal with set of keys that can be mutated over time, this will allow us to have a principal all spaces delegate access to and passkeys could be registered under that principal.

> [!caution]
>
> One other issue is that on a device without access to same passkey we can not even know what the account identifier is.

## Accounts as did:plc

I'm starting to think that perhaps we should adopt [did:plc](https://web.plc.directory/spec/v0.1/did-plc) for accounts as it provides just enough functionality to handle account management. Specifically site could [create a new PLC identifier](https://web.plc.directory/api/redoc#operation/CreatePlcOp) that we can register with a [plc.directory](https://plc.directory/) and replicate it locally. When user adds passkey we can add derived profile key to `verificationMethods` and `rotationKeys` to that `did:plc` and if [plc.directory](https://plc.directory/) accepts an update copy that locally also.

> [!warning]
>
> Only `secp256k1` (“k256”) and NIST P-256 (“p256”) keys are currently supported for rotation keys, whereas `verificationMethods` keys can be any syntactically-valid `did:key`. 

Above is unfortunate limitation but we could derive key for supported algorithms from the same passkey even though lack of `ed25519` support is annoying.

## Accounts as did:web

Perhaps even simpler option would be to use [did:web](https://w3c-ccg.github.io/did-method-web/) identifiers e.g we could allow registered accounts to obtain a local name e.g. `did:web:network.tonk.gozala` and store a passkey derived key in the `verificationMethods`. 

> [!warning]
>
> In comparison to `did:plc` this allows us ability to add / remove `verificationMethods` which enables user to add passkey without access to already linked device, but there is a risk that we can abuse this do it without user permission.

## Delegations moved into the database

A user hit a wall with ~6K delegations: every remote effect (every block get and put during sync) re-listed and re-decoded the entire certificate store to prove a chain, about 300ms per effect on native. The store was a pile of files in a fifth provider field of `Space`, unreachable by any remote effect, so delegations also never synced between devices.

The root cause of the 6K turned out to be us: every operator build persisted a fresh profile-to-operator delegation (random nonce, so a new content address, no expiry, no dedupe), one immortal certificate per session. The operator key derives from the profile key, so persisting these bought nothing, identical authority re-mints on every build.

What landed, as a PR stack ending in [#440](https://github.com/dialog-db/dialog-db/pull/440):

- Delegations are ordinary synced data now: slim `dialog.ucan/*` facts (audience, subject, issuer, command, validity bounds) on the entity `blob:<hash>` of the signed envelope, with the envelope itself as a blob. Both land in one commit, replicate by push/pull, and answer datalog queries. 
- The prover walks those facts instead of decoding files: candidates filter on facts, only an admitted candidate's envelope is decoded, direct grants short-circuit. Measured against the same N certificates in the old stores: flat ~25us at N=6144 where the file store cost 210ms, and ~730ns once the resolved-chain cache (verify-on-hit, invalidated by any head movement) warms.
- Session grants live in memory. `build` mints them per allowed scope and proofs compose as `prove(profile, subject)` plus the in-memory link. Saving a delegation is now an explicit act reserved for cross-party authority.
- `profile.access().migrate().perform(&storage)` moves an existing store into the branch: skips self-issued certificates (regenerable residue, which for the 6K profile is nearly everything), compacts nonce-only duplicates to one representative, drains what migrated, leaves the rest. No operator needed, the profile attests for itself.

The crate graph had to invert for the operator to be born on its access branch: new `dialog-identity` crate holds `Profile` and `Authority` at the bottom, `dialog-operator` composes above `dialog-repository`. Public API unchanged.

> [!note]
> The authorization walk runs against an env whose remote-fork providers report content unavailable. Forking requires authorization, so an env that could fork mid-proof is circular, and the trait solver agrees: it literally overflows on the recursive bound. Sync hydrates access-branch state; authorization only reads it.

## Accounts, and how delegations get back to you

Follow up to the delegation work: we settled how accounts fit. The ==account repository is the durable home of delegations==, and login is data flow: retain the account to profile powerline on the device, add the account as the upstream of the profile's access branch, and pull. Access comes back because the delegations are just facts in a branch you can sync.

Spaces should delegate to the account, not to device profiles. That makes the topology a star rather than a chain:

```
Space → Account → Device A
Space → Account → Device B
```

Cutting off a lost device is one act at the account instead of a re-grant from every space, and revoking A does not sever B. Chaining through another device (A delegates to B) still works and is fine as a bootstrap, but B should get its own account edge once the account key can sign, otherwise A's revocation takes B down with it.

> [!note]
>
> Mechanically an account is just a profile whose repo other profiles sync from, there is no account type anywhere. The separate key earns its keep only if it is held differently than a device key: non extractable, passkey gated. The real fix for key rotation is a principal with a mutable key set (did:plc or did:web, above), so "the account key" stops living anywhere at all.

On the sync side we dropped the special hydration pass entirely. Proving now reads the access branch like any other read and replicates content on demand; the walk's remote reach is injected at operator build (naming the fork providers as bounds on Prove would close the Prove to Fork to Authorize to Prove cycle in the trait solver), and the proof that authorizes a fetch has no reach of its own, so it must resolve from what is already local: the retained powerline plus the in-memory session. That bounds the recursion and is also a nice statement of the model, local grants pay for fetching remote ones. Offline it degrades to skipping what it cannot read. Embedders that do not want proving to pay download latency call `pull().download()` and materialize the branch up front.

>
> [!note]
> Fetches are concurrent now as well (one task, bounded in flight futures, so it holds on wasm): traversal per level, spills and blobs fanned out. All of it is [#442](https://github.com/dialog-db/dialog-db/pull/450.
