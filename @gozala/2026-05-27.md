## Artifacts

Pondering on what artifacts are what should be an interface. It seems that we have two flavors of them that we're circling around them. I'll branch them as **declarative** and **imperative** so we can talk about them clearly.

### Declarative Artifacts

This are artifacts like shown in my latest journal entries, fully declarative they come in form of rules, commands and view templates. There is no imperative logic to say call this function or run this rule, non of that you simply describe data model, view for it and [state machine](https://en.wikipedia.org/wiki/Finite-state_machine) described as rules that transition things from one state to another in certain conditions.

> [!note]
>
> This are intentionally not [Turing complete](https://en.wikipedia.org/wiki/Turing_completeness)

### Imperative Artifacts

This are your bundles of JS + HTML + CSS bundles that imperatively query and update state. Can express arbitrary computation  including runaway loops. You get full fidelity of web platform, well part that can be [sandboxed in an iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

---

I am biased towards declarative artifacts, I do think in long run they offer more benefits & I don't buy argument that LLMs are better with imperative artifacts for a second. This are flawed arguments IMO, LLMs evolving and getting increasingly more capable and that is to argue that they can do better with well designed system than with more familiar one that is full of pitfalls.

> [!note]
>
> This reminds me of a good talk Richard Feldman gave about [Making Impossible States Impossible](https://www.youtube.com/watch?v=IcgmSRJHu_8). Gist of it is if it's impossible to express invalid state, your programs won't be able to create it and it's true regardless of whether author is human or LLM.

I think there is another pitfall with imperative artifacts that seems to be often overlooked. While full fidelity of motion does offer a lot of flexibility, it comes with a cost of no uniformity or consistency that can feel chaotic. It is also worth calling out that LLMs are highly susceptible to this (at least frontier models of today). No matter how many rules and skills I create for Claude it seems to still choose to use different test harness, or recreate existing functionality for just one feature or just insist on different code style. Put it differently if you don't set clear expectations you'll get very little reuse or coherence in the system and lot of duplication. Hardware today a web platform seems to handle this amazingly well, but people not so well. Our capacity of consuming novelty is far outpaced by LLMs capacity to produce it. What that means for interactive artifacts is that it is unlikely to get some coherence between them, unless you introduce constraints like conform to my data model or to my visual language etc… At that point why not also constraint se of our means of abstraction.

I think only valid reason is that sometimes means of abstraction may not offer range of expressivity needed to address problem at hand.

> [!note]
>
> This is I think primary use case for imperative artifacts, you need something novel that can't be expressed with available components.

### Escape Hatch

I think we can have our cake and eat too! I think web-components are a silver bullet here. Instead of going all the way into the imperative artifacts, why not offer a way to break out of constraints where you actually need it. Better yet it's become reusable component that you can reuse across artifacts. Game changes instead of building cheap plastic artifacts to building durable and reusable components that can be used across many artifacts. And if defects are discovered they are fixed and all artifacts improve as opposed to having to fix the same issue in number of places

> [!warning]
>
> This is why copy  & pasting code is frowned upon, if have same piece of code in 10 different places any change to it needs to be replicated across all those places. If you refactor that code in a function you just have to change it in one place.

## Portals to Imperative Artifacts

> I clearly digressed from my objective, truth is there is no perfect solution, everything is compromise and best thing to do is to describe tradeoffs so that authors of artifacts can make well informed decisions

I think we can make imperative artifacts relatively convenient to use, I had this rough sketch before but now with effects it stating to take more shape. I think this is how imperative artifact could look like this

```yaml 
<html>
  <script language="application/dialog+yaml">
    concept!: &todo
      description: Todo item
      with:
        title:
        the: xyz.tonk.todo/title
        as: text
      done:
        the: xyz.tonk.todo/done
        as: boolean
    
    concept!: &todo-list
      description: Todo List
      with:
        name:
          descirption: Name of the todo list
          the: xyz.tonk.list/name
          as: text
        item:
          description: Item on this list
          the: xyz.tonk.list/item
          as: entity
    
    command!: &update-todo-status
      description: Toggle todo completion
      with:
        todo:
          descirption: Todo item to update
          the: xyz.tonk.command/todo
          as: entity
        done:
          description: Done status to be set
          the: xyz.tonk.command/done
          as: boolean
    
    command!: &add-todo-item
      description: Create new todo item
      with:
        title:
          description: Title of the item to be added
          the: xyz.tonk.command/title
          as: text
        list:
          description: List todo should be added to
          the: xyz.tonk.command/list
          as: entity

    rule!:
      assert!: todo
      when:
        - assert: todo
          where:
            this: ?this
            title: ?title
        - assert: toggle-todo-item
          where:
            todo: ?this

    rule!:
      assert: todo
      when:
        - assert: add-todo-item
          where:
            this: ?this
            title: ?title
        - assert: ==
          where:
            of: ?done
            is: false

    rule!:
      assert: todo-list
      when:
      - assert: add-todo-item
        where:
          this: ?item
          list: ?this
      - assert: todo-list
        where:
          this: ?this
          name: ?name
  </script>
  <script type=module language="text/javascript">
  	const list = parent.tonk[todo-list].subscribe()
  	list.onreset = (state) => {
  		// render my todo list here
  		for (let list of state) {
  			for (let item of list.item) {
  				let todo = parent.tonk['todo-list'].subscribe()
  				// handle updates for each list item
  			}
  		}
  	}
  	list.onupdate = (delta) => {
  		// incrementally update list
  		
  	})

   window.addEventListener("click", event => {
     if (event.target.dataset.todo) {
     		parent.tonk['update-todo-status'].assert({
     			todo: event.target.dataset.todo,
     			done: !event.target.parentElement.querySelector("input").value
     		})
     }
   })
  </script>
  <body>
    <main>
    </main>
  </body>
</html>
```

Although that starts to feel like author needs to define so much ahead of time. Having commands is cool if we care about having  command pallet that can be used, but if we don't that seems like a unnecessary ceremony in which case you could simply go and do following instead


>

## Name Scarcity

Reading following note from @jackddouglas deeply resonated with me as I have contemplated similar ideas also

> I'm thinking of adding a `key` field where the author can specify what elements of the concept are used to derive the entity ID. For a view, we know `model` and `name` won't change so long as the view remains the same, though other aspects of a view like its display don't fundamentally change the view, and therefore don't change the ID. Same with tiles: position doesn't fundamentally change the tile while the model it's rendering does, so we key on `model` but not `order`.
>
> ```yaml
> concept!: &view
>   with: { name: view-name, model: view-model, display: view-display }
>   key: [model, name]          # editing `display` upserts; no duplicate (model,name)
> 
> concept!: &tile
>   with: { board: .., view: .., model: .., entity: .., order: .. }
>   key: [board, model, view, entity]   # order/focus are NOT in the key → mutable
> ```

On my it felt natural to use `this` as a way to describe how to derive it from data

```yaml
concept!: &view
  this:
    model:
    name:
  with:
    name: view-name
    model: view-model
    display: view-display
```

> [!caution] 
>
> However `this` is already used to capture produced entity in the variable itself so we'd either hav to revisit that or use a different  name indeed.

Relatedly I was thinking that what I actually need isn't necessarily how to derive entity and more about how to derive it during assertions, so more like this

```yaml
view!:
  this:
    model: tile
    name: Top
  display: |
    <div class=tile></div>
```

Idea here is that I don't need to know what the `did:key` will come out as I just need a way to specify it clearly at construction time. It would imply some repetition on creation though

```yaml
view!:
	this:
		model: counter
		name: Basic
	mode: counter
	name: Basic
	display: |
		<p>{count}</p>
```

However we could do punning to imply deriving it from listed fields

```yaml
view!:
	this:
		model:
		name:
	mode: counter
	name: Basic
	display: |
		<p>{count}</p>
```

This would also mean you can bring other things into the mix like constants or references to concepts itself e.g.

```yaml
view!:
	this:
		model:
		name:
		concept: view # now this is part of identifier
	mode: counter
	name: Basic
	display: |
		<p>{count}</p>
```

But what if I do not want to specify all these fields every time I create, seems like listing them on definition is both concise and avoids that. I think that is sensible, but then I'm also tempted to suggest that we're basically defining constructors here and in practice you'd want more than one of those. However with commands and rules we kind of can express those things

```yaml
command!: &new-view
	description: Creates a new view for the model
  with:
    name: view-name
    model: view-model
    display: view-display

rule!:
	description: Asserts view new-view on new-view command
  assert!: view
  when:
  	- assert: new-view
  		where:
  			name: ?name
	  		model: ?model
  			display: ?display
  	- assert: ==
  		of: ?this
  		is:
  		  name: ?name
        model: ?model
      
```

It is definitely more verbose, but then it is also a lot more flexible and allows you to have many different constructors

> I got sidetracked again though I was going to point out the problem with naming

Bigger issue I observe however is that `name!` concept now became special and I find myself contemplating if I should give some concept a name or not, because if I do that name is now occupied. I also ran into issues when I was careless and defined another concept with the same name, overriding what it meant which is even worse. If I define a view for the same model and name but different display now I have two views with the same name & currently system picks on at random.

> [!note]
>
> I would argue that problem with defining view with same name, model and different display is not that it makes up new identifier, but the fact that now we have two views with the same name. I think proper solution would have being to keep a view but bind new one to name.
>
> If I had time to hack more on the dialog side of things I would have finished up PR that allows us to have dictionary like concepts so that view concept would have looked like
>
> ```yaml
> concept!: &view
>   description: Named view for this concept
>   with:
>     ?name:
>       description: Named view template for this concept
>       the: xyz.toxn.view/?name
>       as: text
> 
> view!:
> 	this: counter
>   basic: |
> 	  <span>{count}</span>
> ```
>
> This would have produced following facts under the hood
>
> ```yaml
> fact!:
> 	the: xyz.tonk.view/basic
> 	of: counter
> 	is: <span>{count}</span>
> ```
>
> This way you could simply update view for the concept without extra indirection and better capture intent of one named view per concept. Current approach was kind of workaround for lack of this feature.

## Artifacts

Have being mulling over what the artifact is and how do we model them. I am realizing that my thinking have being misaligned with the new conceptual model we're building. In my mental model there were many views and each view composed out of bunch of other views in fact event simple todo list was manifested as such, list was a view and items were views. But view is probably not an artifact, it would make no sense to have a tab for every single single todo item, counter etc.. nor it would make sense to have tabs for each view because there might be many things that match that view which I think gets at the crux of the issue - artifact as seems to imply cardinality one where's views imply cardinality many (you can have many todo lists, many journal entries, many issues etc…)

> [!warning]
>
> I think it is naive to assume that tab bar will scale to number of artifacts, even iPhone added some nesting even though they really resisted it for a while. Tab bankruptcy in browsers is what I spend years trying to address. If tab bar can handle number of artifacts people create we probably have failed to create something people care to use.

Perhaps artifact is more like board or a directory that can have many things in it ? So more like view over the whole database as opposed to view over a specific entity ? That framing seems more promising to me, in some sense that is what I thought workspaces (boards) with tiles represented. So I think perhaps artifact is something along the following lines:

```yaml
concept!: &artifact
  description: View over all the data in this repository
  with:
  	name:
  		description: Name of this artifact
  		the: xyz.tonk.artifact/name
  		as: text
  	icon:
  		description: Icon displayed in next to tile of this artifact
  		the: xyz.tonk.artifact/icon
  		as: entity
  	view:
  		description: HTML view for this artifact
  		the: xyz.tonk.artifact/view
  		as: text
```

I think this raises questions about what concepts does this artifact query and where are they defined are they defined inside the HTML or outside of it ? Also when are they defined.
