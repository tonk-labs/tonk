# July 7th

## The row that rendered into the void

Space switching updated the URL and nothing else. The chain was healthy end to end: claim landed, worker stamped the new route, frames crossed the relay, the display called render. The break was one line in the renderer: a whole-fragment repeat (a multi-root template with no `{this}`, exactly the space chrome's shape) recorded the template fragment as its row root, and `append_child` empties a fragment. Every later binding update navigated an empty fragment, found no target, and silently no-oped, so `with="main@{id}"` on the nested site never restamped. The identical bug had been found and fixed for chrome bindings before, one line up, with a comment explaining it. Row roots now re-point at the host after mount, with regression tests for attribute and text bindings in that shape. With that fixed the in-place navigation could come back: a same-reach path change reuses the live iframe and just re-claims, no guest reboot.

## dom.host is a live input now

The FAB stayed on the old space after a switch because `{dom.host/data-space}` was read once at render time and nothing reacted when the diff restamped it. The plan now reports which host attributes a template consumes, the view advertises them as `data-host-bindings`, and the display watches exactly those with a filtered MutationObserver (`observedAttributes` is fixed at define time, so it cannot express a per-instance set). A genuine value change replays the cached frame through the binding diff, which touches only what changed. Clicking a spot-menu item also closes the menu now.

## The crash was stream transfers

Tab crashes had haunted the whole branch and kept getting attributed to whatever was rebuilt last. The reproducible trigger was navigating from a space to the hub, and the killer was `ReadableStream` transfers: tearing down a guest whose relayed response bodies were transferred into it, or reconnecting a burst of them after a worker restart, took the whole renderer down. Same repro, transfers on: dead tab, twice. Transfers off: survived everything we threw at it. The credit-based chunked MessagePort relay, originally the Safari fallback, is now the transport everywhere, and portal teardown aborts every relayed fetch so nothing streams into a destroyed realm.

## The worker owns its sync cadence, the page keeps it breathing

Replaced the page heartbeat with a worker-owned loop per the design Irakli specced: while any branch has a live subscriber, drain every ten seconds; stop when the page goes quiet, when offline (after stamping `sync:offline`), or when every open space is paused; any fetch restarts it, so a resume transact is its own wake-up. The catch his spec also predicted: nothing extends a worker's lifetime from the inside. SSE bodies do not count, timers do not count, so the worker died thirty seconds after every wake and the churn outran the healing. The page now sends a keepalive poke every ten seconds, but only while it holds live subscriptions, which is the difference between this and the old heartbeat: an idle page lets the worker die, a subscribed page keeps it alive. Per-space pause turned out to already be correct at the data level; the earlier all-spaces-paused impression was the stale FAB targeting the same space on every alt-click.

## Restarts you cannot see

Stopping the worker used to replace every view with an error callout, then crash, then on the rebuilt attempt show a spinner that never ended. Three fixes, one per layer. A transport interruption no longer clears content: the display stamps `data-state=offline`, keeps the DOM, and the reconnect heals it. The `tonk:site` stamp lives in the worker's in-memory overlay and dies with it, so each site now watches its own stamp through a hidden probe and re-asserts `tonk:load` when a frame comes back empty. And the first frame after a reconnect is marked, because it can reflect state the worker lost and is about to get back: the display holds rendered content through a marked empty frame under a five-second grace, so the heal lands invisibly and a genuine deletion still applies, just unhurriedly. Final state, verified with the service worker killed from serviceworker-internals: no callout, no crash, no spinner, same content before, during, and after.

## The update that could never take over

With two tabs open, refreshing one wedged the worker update forever: the new version sat in waiting and skipWaiting never completed. The mechanics are unforgiving once you see them. skipWaiting waits for the active worker's in-flight fetch events to settle, an SSE response is a fetch event that never settles, and the updatefound release clears streams exactly once, after which every tab's reconnect machinery reopens streams against the outgoing worker within seconds. The keepalive fed its lifetime too. One tab raced, several tabs wedged permanently, and the stuck transition is where the remaining tab crashes lived.

Broke it at every link. The worker refuses to open a long-lived stream while a newer one is waiting: it serves the current snapshot plus a `{"control":"update-pending"}` frame and closes, so no event can pin it and correctness stops depending on client timing. Irakli's suggestion became the protocol: a consumer that saw the control frame holds its reconnect on a long fallback instead of the short timer, and the top page re-issues every subscription the instant controllerchange fires, so recovery is one pass. Guests cannot observe controllerchange, so the long fallback covers them, and a premature retry now costs a cheap snapshot-and-close rather than a wedge. The keepalive pauses while an update is installing or waiting. And the FAB's sync disc paints the hollow offline ring on a stream error now, so a worker disconnect is something you can see instead of something you deduce.

Verified with two tabs, a pending update, and a refresh: old versions went REDUNDANT, one ACTIVATED worker running, both tabs fine. tonk PR #567.

## Correction: the transfers were innocent

Irakli wanted the zero-copy stream transfers back rather than dropped, and re-testing proved him right. The all spots crash returned even on the chunked transport, and the crash report showed the BROWSER process segfaulting, not the renderer, which pointed at browser-brokered lifetime bugs rather than the transfer mechanism. The real trigger was destroying a live nested guest synchronously from inside a render pass: running wasm, brokered ports, its own nested frame, all torn down in one DOM call. Teardown is two-phase now: abort every relayed fetch, close every chunk port and the bridge port, point the frame at about:blank so the realm unloads on its own schedule, remove the element a tick later. With that fixed, transfers went back on and both historical repros pass: five space to hub cycles and a worker stop, no crash. The earlier A/B that convicted transfers was confounded by the timing change the chunked path introduced. Lesson kept: when the fix is "disable the fast path", keep interrogating until the actual trigger confesses.

## The profile branch that was always meant to be main

The profile repository kept everything on a `meta` branch while every other repo defaults to `main`, for no reason other than history. Before renaming I had to prove `meta` was not load-bearing, because it is overloaded: the profile uses it as its one branch, but each space repo has both `main` and `meta`, and the space `meta` is device-local bookkeeping that must never replicate. Irakli's question was the right one to check, whether the roster is on `meta`, since we show who is a member. It is not. Membership, MemberName, and Invitation all write to and read from the space's `main` content branch, on purpose, so they sync across replicas. The space `meta` holds only the local Replica record, remotes, and branch enumeration. So the split stays for spaces and only the profile moves. The worker's single `META_BRANCH` constant, which was quietly serving both roles, split into `PROFILE_BRANCH = "main"` for profile paths and `META_BRANCH = "meta"` for space paths. Rename-forward only, no data migration, dev reseed. Verified on a fresh profile: every profile op hits `/api/profile/branch/main`, zero `meta`.

## Inspecting the profile you are standing on

Added `/inspector` and `/diagnose` as profile routes so the query notebook and the search-tree view can point at the profile DB, not just a space. Two small gaps stood between the elements and the profile. The tree's Loader only built `/api/repository/{repo}/…` and the inspector's context resolver returned nothing for a profile location, because a profile has no repo segment. Both now take a `Location` and route to the parallel `/api/profile/branch/{branch}/…` surface when the space is absent. The elements themselves need no wiring beyond that: they mount inside the profile's own sealed guest, which pins every unrouted operation to the site's own context, so an inspector cell evaluates against the profile without carrying any route of its own. Verified: diagnose renders the real profile search-tree, inspector mounts with a live LSP over the guest fetch relay. tonk PR #570.
