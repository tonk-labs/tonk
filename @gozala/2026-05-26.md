## Events

The `<tonk-display>` element gained event handlers. Authors bind a DOM event to a transient concept by writing `on<event>=<concept>` in the view template; the runtime walks the concept's `with:` map at click time and projects field values out of the JS event. A `the:` identifier under the `dom.event` namespace tells the runtime to read that field from the event rather than from dialog storage. 

> [!note] 
>
> Some interactions like drag and drop stuff require advance event handling, like calls to [`event.preventDefault()`](https://developer.mozilla.org/en-US/docs/Web/API/Event/preventDefault) / [`event.stopPropagation()`](https://developer.mozilla.org/en-US/docs/Web/API/Event/stopPropagation) which currently can be caused by having fields like
>
> ```yaml
> concept!: &increment
>   transient:
>   with:
>     counter:
>       description: "the counter to bump"
>       the: dom.event.target.dataset/counter
>       as: entity
>       cardinality: one
>     stop:
>       description: "stops event propagation if set to true"
>  	 the: dom.event.do/stop-propagation
> ```
>

The assertion crosses the SW boundary as an ordinary `TransactRequest`: one transient `Claim::Assert` with the field values the event projection produced. The worker handles it like any other transient — induces, sweeps, broadcasts the resulting subscription deltas to subscribers.

Entity context (which counter is being clicked, which item is being selected) reaches the handler via a regular `data-*` attribute the template author writes on the element using existing `{field}` interpolation: `data-counter={this}` on the button, `dom.event.target.dataset/counter` on the concept reading it back. No new variable-injection plumbing; the chain `template → data-* → event.target.dataset → concept field` is visible at every step.

Implementation lives entirely in `tonk-display`. `Renderer::from_snapshot` runs a preprocess pass that rewrites `onclick=increment` to `data-onclick="increment"` so the browser doesn't try to evaluate it as inline JS. `<tonk-view>` publishes the discovered bindings to a `data-event-bindings` attribute. `<tonk-display>`'s view-frame handler resolves each binding's concept descriptor and installs a single delegation listener per event type on its own host. The listener walks up from `event.target` to find the closest `[data-on<event>]` ancestor, looks up the cached descriptor, and POSTs to `/transact`.

One delegation listener per event type, on the host, means re-renders don't disturb the binding: the renderer's incremental patch can replace a button's text node without touching the listener, and the next click still routes the same way.

## Counter end-to-end

This is the integration test on `feat/events` — it bootstraps a counter via `/evaluate`, navigates to the display route, clicks the rendered `+` button twice, and verifies the rendered count goes from 0 to 1 to 2.

```yaml
concept!: &view
  description: A rendered view of an entity
  with:
    name:
      description: view name
      the: xyz.tonk.view/name
      as: text
      cardinality: one
    model:
      description: view model
      the: xyz.tonk.view/model
      as: entity
      cardinality: one
    display:
      description: view display template
      the: xyz.tonk.view/display
      as: text
      cardinality: one

concept!: &counter
  with:
    count:
      the: xyz.tonk.counter/count
      as: unsigned-integer
      cardinality: one
      description: current count
      
view!: &counter-view
  name: "basic"
  model: counter
  display: |
    <div>
      <span class="value">{count}</span>
    </div>


concept!: &increment
  transient:
  with:
    counter:
      the: dom.event.target.dataset/counter
      as: entity
      cardinality: one
      description: The counter to bump

rule!:
  assert!: counter
  when:
    - assert: increment
      where: { counter: ?this }
    - assert: counter
      where: { this: ?this, count: ?m }
    - assert: math/sum
      where: { of: 1, with: ?m, is: ?count }
      
view!: &counter-view
  name: "basic"
  model: counter
  display: |
    <div>
      <button onclick=increment data-counter={this}>+</button>
      <span class="value">{count}</span>
    </div>

counter!: &my-counter
  count: 0
```

A click on the `+` button asserts `increment` transient with `counter` set to the rendered counter's URI (pulled out of `event.target.dataset.counter`, which the template populated from `{this}`). The rule fires once: it joins `increment` with the durable `counter`, runs `math/sum` to produce `count + 1`, and asserts the new `counter` row. The entity subscription that `<tonk-display>` already maintains re-fires, the `.value` span's text node patches in place, the screen shows the new number. Transient sweep removes the `increment` fact before the durable commit lands.

## Detangling views from subscriptions

Started to look into tonk-layout that has landed in attempt to rebuild one of the tiling manager prototypes with it. It seems that tonk-layout morphed from managing layout to managing state of tiles _(if I understand it correctly)_, either way my instinct was lets revive todo list first as tile manager will need to manage collection of tiles also. As I [evaluated code](./2026-05-14.md#the-obvious-shape) from the previous sketch I discovered it was not working because `tonk-display` needs to know `repository` and `branch` to query / claim. It was easy to fix by adding `space=home branch=main`, but obviously it's not right if you're on different branch.

> [!warning]
>
> This is actually something bugged me from the day one of tonk-display, tonk-concept and other web components, views should not know or care what repo or branch they're on.

This got me thinking that I had similar issue with `tonk-code` until I refactored logic that talks to service worker in a `tonk-language-service-provider` web component. After that all `tonk-code`'s simply dispatch events and enclosing `tonk-language-service-provider` component takes care of sending requests to SW, decoding readable stream which is shared across all the code blocks as opposed to creating LSP client per each block.

After some pondering I settled on the redesign illustrated by the example below

```html
<tonk-host>
  <tonk-repository name="home">
    <tonk-branch name="main">
			<tonk-display
        entity="did:key:zT0d0l1st"
        model=todo-list
        view=basic />
    </tonk-branch>
  </tonk-repository>
</tonk-host>
```

General idea is similar as with `tonk-code` - `tonk-display` simply dispatches `query`, `claim`, `subscribe`, `evaluate` events on itself. Event bubbles up and `tonk-branch` sets a branch name, `tonk-repository` sets the repository name and `tonk-host` stops propagation and performs `query` or more interestingly establishes `subscription` for the query with SW and when there is an update it calls `event.target.update(delta)` allowing `tonk-display` to reflect changes in the view.

Another interesting aspect is that nested `tonk-display` elements also just dispatch events that bubble up to the `tonk-host` which does the same thing.

> [!note]
>
> `tonk-host` manages subscriptions and can deduplicate if there are multiple subscribers inside it. More importantly if you change say branch name it can tear down subscriptions and establish new ones.

There is additional piece of machinery in place to improve behavior of nested `tonk-display` - each `tonk-display` also listens to those events and when they happen it captures nesting something like `++event.detail.depth` which will allow `tonk-host` to be more intelligent when switching branches or repositories. Specifically it can do teared re-subscription, first update nearest `tonk-display` elements allowing them to prune obsolete children and consequently drop subscriptions from host, then do the same for subscriptions one level deeper and so on until all are covered. Idea here is to avoid issuing queries that will yield nothing & to avoid temporary inconsistencies while things are reloading.

### Portals

I like this model because it also makes `tonk-portal` somewhat coherent, idea being that iframe host simply bridges same events from within guest and forwards subscription updates back in. It also would mean doing all the subscription management in `tonk-host` and sharing it across `tonk-display`, `tonk-portal` and other web components like `tonk-concept` and such could share same `tonk-host`.

## Attributes vs. properties in the template engine

Reviving the todo list also surfaced an older bug: `<input type=checkbox checked={done} />` never unchecked when `done` flipped to `false`. The template engine treated everything between `=` and the next whitespace as an HTML *attribute* and called `setAttribute("checked", "false")`. But `checked` is a boolean attribute — the browser only looks at its *presence*, so the rendered string `"false"` left the box checked. The same wrongness applies to `value`, `disabled`, `selected`, and every other reflected property where HTML attribute semantics diverge from DOM property semantics. The renderer simply had no way to express "set the property."

The fix dispatches at apply time based on what the value actually is. A non-string JSON value (bool, number, array, object) is assigned as a JS property via `Reflect.set` with a typed `JsValue`. A string value falls through to a `name in element` check: if the name exists as a property on the target element, assign as property; otherwise `setAttribute`. Multi-segment bindings like `href="/x/{id}"` always stringify and then take the same name-in-element check. That's enough to cover every common case without per-attribute special-casing — `checked={done}` and `value={text}` go through property assignment, `aria-hidden={x}` and `data-id={x}` go through `setAttribute`, all automatically.

For the cases where author intent diverges from the heuristic, `html:foo={x}` is the explicit escape hatch. Reads as "this name lives in the HTML attribute namespace," visually distinct because the colon stands out, doesn't collide with any real HTML attribute (the spec's only colon-prefixed attribute namespaces are `xml:`, `xmlns:`, `xlink:` inside SVG/MathML). On the forced-attribute path, boolean values follow HTML's presence/absence convention — `true` writes an empty attribute, `false` removes it.

## Got My Todo List working

```yaml
concept!: &todo-item
  description: Todo item
  with:
    done:
      the: xyz.tonk.todo/done
      description: Completion status
      cardinality: one
      as: boolean
    title:
      the: xyz.tonk.todo/title
      description: Title of the todo
      cardinality: one
      as: text
      
concept!: &todo-list
  description: Todo list
  with:
    name:
      the: xyz.tonk.list/name
      description: Name of the list
      cardinality: one
      as: text
    item:
      the: xyz.tonk.list/item
      description: Item in the list
      cardinality: many
      as: entity

view!:
  model: todo-list
  name: "basic"
  display: |
    <article>
     <h2>{name}</h2>
     <ul>
     <li subject={item}>
     <tonk-display model=todo-item view=basic entity={item} />
     </li>
     </ul>
    </article>
    
view!:
  model: todo-item
  name: "basic"
  display: |
    <div onclick=toggle-todo data-todo={this}>
     <wa-checkbox checked={done}></wa-checkbox>
     <span>{title}</span>
    </div>
```

With above setup you can then create a list like this one

```yaml
todo-item!:
  this: ?todo
  done: false
  title: Make a list

todo-list!: &demo-list
	name: Todo List
	item: ?todo
```

And you can wire it up with effects as follows

```yaml
concept!: &toggle-todo
  transient:
  with:
    todo:
    	# not we capture todo from current target because actual
    	# dispatch target may be e.g. span in the diff
      the: dom.event.current-target.dataset/todo
      description: Todo item to toggle
      cardinality: one
      as: entity
      
rule!:
  assert!: todo-item
  when:
    # if there is a toggle-todo command active on this todo
    - assert: toggle-todo
      where:
        todo: ?this
    # and todo has done with value ?v
    - assert: todo-item
      where:
        this: ?this
        done: ?v
        title: ?title
    # and ?done is !v
    - assert: boolean/not
      where:
        value: ?v
        is: ?done
```
