# June 8th

## Tonk is broken on Firefox 

Other day I was demoing our system to a Firefox user & was embarrassed to discover nothing worked there. This is especially touchy for me as I worked at Mozilla for 10 years and had enough share of frustration with people not even bothering to test on Firefox as it felt like betrayal of the open web. Now I felt guilty of betraying myself.

Feelings aside turns there is a [well known issues](https://bugzilla.mozilla.org/show_bug.cgi?id=1594633) with a support of streams in service worker. Quite a memory lane for me, because I spend last year prior to layoff implementing and [reimplementing support for streaming](https://gozala.io/libdweb) in Firefox extensions context, so we could have implementations of P2P protocols as web extensions.

The actual failure was narrower than "streams don't work". Our service worker hosts an axum router and converts the intercepted browser request into an axum one. On Firefox `Request.body` of an intercepted request is `undefined` rather than a `ReadableStream`, so web-sys hands us `None` and we silently fell back to an empty body. Every POST reached the router with nothing to parse, hence the `invalid ConceptQuery body: EOF` symptom. Chrome gives us a live stream so it just worked there, which is how this slipped through.

A tiny service worker harness confirmed `request.body === undefined` on Firefox 151 while `request.blob()` returns the full bytes. So the body is right there, only the stream view is missing. To keep streaming instead of buffering into a `Vec`, `blob().stream()` gives a `ReadableStream` that reads back the exact bytes. The blob is materialized eagerly, so it is the streaming interface without true end to end streaming, but our query bodies are tiny and it keeps the existing `Body::from_stream` path with a minimal diff.

So the fix is a fallback, not a replacement: prefer `body()` (Chrome), fall back to `blob().stream()` when it is `None` (Firefox). A bodyless GET yields an empty blob hence an empty stream, matching the old `Body::empty()`, so no special casing. Verified on Firefox: the `/query` POSTs that were 400 now come back 200.

## Empty artifacts and the sheet tab strip

I picked up the viewer's bottom tab strip, which until now was display only. You could see sheets but not add or remove them, which made the whole thing feel like a static mockup. I wanted the strip to actually behave: close a tab, create a tab, and have a freshly created tab show something real instead of a broken load.

The first thing I hit was that `assert: ==` in core.yaml was being rejected even though `==` is a perfectly good dialog equality constraint. Turned out notation parses it fine and dialog supports it fine, but the analyzer sat in the middle knowing only about *formulas* (`math/sum` and friends) and *concepts*. The `==` constraint lives in a separate dialog enum that the analyzer never enumerated, so it fell through to concept resolution and came back "unknown concept". I gave the analyzer a constraint registry parallel to the formula one, deriving the operand names from dialog's own `Equality::schema()` so they can't drift from the wire format, and routed premises through `Proposition::Constraint`. `==` now also shows up in the LSP autocomplete next to the formulas.

The close button was straightforward to draw but the focus behavior was a rabbit hole. The model side is two rules: retract the workspace -> sheet membership so the tab disappears, and move the `active` pointer to a neighbour if you closed the active tab. Closing a background tab should leave focus exactly where it is.

It kept stealing focus anyway, and I refused to keep guessing, so I drove the real app over the Chrome DevTools protocol and watched the actual events. Closing a background tab flipped `active` to the *closed* tab. The cause was a command collision that I want to flag because it is a genuinely subtle footgun in how our commands are matched.

> [!warning]
> Commands are matched by their *attribute facts*, not by the event type or the command's name. The close command and the activate command both read their sheet off the same attribute, `dom.event.detail/sheet`. So the fact a close emits also satisfies the activate command's premise, and closing a background tab silently re-selected the tab I was trying to remove. Nothing about the event name `close` versus `activate` enters into it. Two commands that happen to read the same attribute will fire on each other's events, and there is no error, just wrong behavior. The fix was to give close its own attribute (`dom.event.detail/closed`), but the lesson is that distinct commands must use distinct attributes or they alias.

I also taught the binder to fall back to showing the first sheet when `active` points at nothing, purely for display, never writing it back, so a stale pointer can never collapse the layout.

Then creating a sheet. The "+" button opens an inline name input that dispatches a `create` event the view maps to `workspace/create-sheet`, and the binder owns the order key so the new tab lands at the end. A created sheet is self-describing now: its entity is the sheet itself and its model is a new `empty-artifact` concept, so it renders a real empty-artifact canvas (name, an agent link, instructions) instead of failing to load. Wiring it up exposed a genuinely old bug: the event-to-command coercion knew `unsigned-integer` and `UnsignedInt` but not `UnsignedInteger`, which is the form the descriptor actually serializes, so *any* integer command field silently dropped and the whole command fell through. That one had been lurking for anyone who put an integer on a command.

## Artifact-scoped agent links

The empty-artifact canvas wants to hand a sheet to an agent. The link I want is `/space/<name>/<artifact-entity>@artifact?access=...#...`, where the entity is the sheet's `this` and `@artifact` names the concept, so the link drops the agent straight onto that artifact's view to edit the model or entity behind it. These are a CLI target, not a browser claim flow.

One thing to be clear about: in dialog the **repository is the unit of sharing**. A delegation grants access to a whole repo DID, by design, and that is not going to change. So the artifact targeting in the link is navigation, dropping the agent on the right view, layered over a repo-wide grant. The link points at one artifact; the access it carries is the whole repo's.

I went around the design a few times. My instinct was to model this through the command and Provider subsystem we shipped earlier, where a command is a transient concept and a Provider runs post-commit and can assert results back as facts. That is a clean pattern and I reached for it first.

> [!caution]
> The command/Provider pattern communicates results through DB facts, and the invite's URL fragment is a 32-byte Ed25519 private-key seed. Writing the generated link into the synced prolly-tree DB would replicate that credential to every peer, forever. A leaked seed is not a bug you patch, it is a key you can never un-share. So nothing about the invite, not the seed and not the full URL, may ever touch durable, synced storage.

That constraint is what killed every storage-shaped design in turn: command-asserts-a-fact, an in-memory secret map with an opaque id, even Cache Storage keyed by the entity. Each one was more machinery in service of persisting a thing we must not persist. The realization that ended it is that a link is cheap to mint and meant to be used once, so we do not need to store anything at all. The endpoint mints an invite and returns it in the HTTP response, the web component shows it, and the secret lives only in that response and in the element's DOM for the session. Reload regenerates. If we ever want stable links we derive the seed deterministically from the artifact rather than storing it.

That collapsed the whole feature down to almost nothing. Our existing repo invite endpoint already mints a URL from a caller-supplied base URL and returns it without storing anything, which is exactly how the top-bar share button works. An artifact link is just that same endpoint called with `base_url = {origin}/space/{repo}/{entity}@artifact`. I checked that the `url` crate preserves the literal `@` and `:` in the path through `Invite::to_url`, so the display route can still split on `@`. So all that was left was a small `<tonk-invite>` element that resolves the repo from its ancestor, builds the artifact base URL, posts to the existing endpoint, and renders the link. No new route, no command, no Provider, no fact, no cache.
