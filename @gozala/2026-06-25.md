## Narrowing branch fixes the optional-query bug

Dialog's `feat/narrowing-diagnostics` is the top of a four-PR stack (operator IR, type-checker, refinement predicates, narrowing diagnostics) that reworks the query engine. I swapped our deps over to it to check whether it fixes the bug I hit before, where a `this`-unbound query like `person:` over a concept with optional `age` dropped everyone who had no `age`. The planner led the unbound scan with whatever field sorted first alphabetically, and `age` < `name`, so the optional premise led and its Absent fallback got suppressed.

It's fixed. Both regression guards pass now, the minimal dialog-level one and the end-to-end `person:` repro, so I un-ignored them. The optionals surface is green against the new branch (evaluator, schema, analyzer, notation).

The dep swap itself only needed three adaptations: `ConceptDescriptor::operands()` became `required_operands()` (now excludes optionals, so for head-fact emission I append the optional keys back and let the Absent guard skip the missing ones), the derive dropped `From<Query> for ConceptDescriptor` so `dialog-reactor`'s `Decode` blanket impl reads the descriptor through `Descriptor<ConceptDescriptor>` instead, and an empty-`with` test fixture had to gain a field since empty concepts are now rejected at deserialize.

## `_:_` is the gotcha

> [!caution]
>
> The strict Entity/Text typing on the new branch breaks the default-model view. `view!: model: _:_` is stored as a Text `"_:_"`, but the view query asks for `model` `as: entity`. The old engine matched Text against an Entity-typed term loosely; the new one does not, so the `_:_` fallback view is invisible and `slide`'s default-view test fails.

I tried teaching the notation parser to classify `_:_` as a URI so it lowers to an Entity, but dialog rejects `_:_` as an entity URI ("relative URL without a base"). So `_:_` genuinely isn't an Entity, and the sentinel needs a real decision: either a valid blank-node URI dialog accepts, or the view-model attribute becomes Text. Reverted the parser poke since it just traded one failure for another. This is independent of optionals, a separate consequence of the dialog upgrade, so filing it on its own.

The optionals branch is otherwise clean on the new deps.

## The age:3 disappearing act

Reported bug: assert `person!: name=Alice, age=3`, it commits, then `person:` returns nothing. The domain query `xyz.tonk.person:` over the same attributes did find it, so the write was fine and the concept query was dropping a row that had all its required fields.

The concept was `age` `as: text` but I asserted a bare `3`. `scalar_to_value` only ever coerced `Integer -> UnsignedInt` for unsigned fields; every other literal kept its lexical type regardless of the field's declared `as:`. So `age: 3` landed as a `SignedInt` under a Text attribute. The untyped domain query matched it; the strictly-typed concept query types `age` as Text and never matched the `SignedInt`. The entity vanished from its own concept with no signal. Loose matching had hidden this all along, the narrowing rework just stopped tolerating it.

> [!note]
> The data model was actually wrong (`age` should be a number, not text). But "wrong type commits, then silently disappears from its concept" is the worse failure. Parse, don't validate: reject the mismatch at assert time and point at the field.

So `scalar_to_value` now rejects a literal whose type contradicts the field's declared type (`TypeMismatch`, with the field name and a range), and a field with no declared type still accepts anything. The message reads in the `as:` vocabulary: `field "age" expects Text but got a SignedInteger literal`.

## `_:_` resolved as a side effect

The new check immediately caught the bigger instance of the same bug: the stdlib seed itself. `view/directory!: model: _:_` writes a Text `"_:_"` into the `as: entity` model field, so `slide init` started failing to seed.

`_:_` was always meant to be a URI, it just was not one and worked by accident. The render and display consumers only ever compare `model` against the `"_:_"` string (a `DEFAULT_MODEL` constant in each), so it is purely a lookup key, no `_:_`-specific parsing anywhere. Swapped it for `tonk:_`, a real entity URI in the existing `tonk:` scheme: three functional edits (core.yaml plus the two constants), and the previously-ignored default-view test goes green. Picked `tonk:_` over `tonk:concept` so it survives a later `model` -> `concept` rename untouched.

> [!note]
> We define concepts then refer to them as `model` everywhere (the view/artifact field, `{dom.host/model}`). A view's `model` IS a concept. Filed BUG-19 to standardize on `concept`, kept separate since the attribute-URI change is a data migration touching ~20 files.

## 🤔 Notation ergonomics

I have being finding notation ergonomics to be not ideal and I feel like it nudges you into a wrong direction, specifically I find myself defining concepts and wanting to use just attributes which requires defining them separately. Also optional namespaces does introduce dilemma whether to namespace a concept or not. I feel like we'd be better off that dilemma did not arise and if we could avoid having to think about attribute vs concept and more of thought of concept as convenient set to refer to it by name. Here is reimagining of this

```yaml
concept!: &person
	description: A person
	with:
    name:
      description: Name of the person
      the: xyz.tonk.person/name
      as: text
    age:
      description: Age of the person
      the: xyz.tonk.person/age
      as: unsigned-integer

# assert just one attribute
person/age!:
	of: alice
	is: Alice
	
# query just one attribute
person/name:
	of: ?person
	is: ?name
```

## Renamed the slide CLI to tonk

Eileen wanted `slide` to take the `tonk` name it's already invoked by, so I made the crate match: `rust/slide` is now `rust/tonk-cli`, package `tonk-cli`, binary `tonk`. Dropped the `slide` alias. The one holdout is the `OPERATOR_CONTEXT` salt, which stays `b"slide"`: it derives the operator key, so changing it would re-key every DID and lock existing repos out. Left a comment saying so.

While in the release workflow I made the download usable without a rename dance. Binaries ship as `tonk-<platform>.tar.gz` with the binary named `tonk` inside and the exec bit kept, plus an `install.sh` that detects the platform, clears the macOS quarantine, and drops `tonk` on PATH. chmod alone wasn't enough on mac, Gatekeeper quarantines the unsigned binary, so the script runs `xattr -d com.apple.quarantine` too. Stable is the canonical latest now so `releases/latest/download/...` resolves; staging stays a pre-release. Channel is env-only: `TONK_CHANNEL=staging` for the pre-release, `TONK_RELEASE` to pin an exact tag, otherwise stable.

## Adopting optionals, and the fallout

Rebased the adopt-optionals branch onto staging (which now has the tonk-cli rename) and opened [#538](https://github.com/tonk-labs/tonk/pull/538). It converts the binder's active sheet to an optional field (retiring the `tonk/active-sheet` carrier concept) and carries a dialog-reported fix.

The dialog bug: a concept's `maybe:` field would not resolve an attribute that lives on the branch, by name or by URI, even though the same reference resolves fine in `with:`. Inline defs worked, which masked it. The analyzer's prefetch (`collect_concept_with_needs`) only gathered references from the `with:` block, so a branch attribute referenced solely from `maybe:` never got fetched into scope and read back as an unknown name. Widened the gather to both blocks; the resolution logic was already shared. Added a guard that fails before the fix and passes after.

> [!note]
> The guard had to publish a real branch attribute by name and reference it through the resolver, since in-doc anchors register during push and never exercise the prefetch. That is the only path that actually reproduces it.
