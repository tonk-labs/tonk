## Tonk Offline
Version control, local only, and no account are magical moments
Inspectability: can I open a file with my data and is it human readable?

Bringing users through a setup ceremony where they select a name and place for their repo on disk is an elegant way to gesture at the local first nature of [[Tonk]]. It gives us an opportunity to say you can work offline, keep and protect your data, and sync whenever possible. Perhaps this is also where we can explore generating [[PWA]]s.

That manual ceremony might be preferable to [[WebRTC]] if it can effectively demystify how data is stored, synced, and develop a productive mental model for users to reason about how the tech fits into their lives and how it's different than everything else.

There're a couple problems baked into the above. For one, the repo is currently stored as `.tonk/` wherever you initialize `slide`. Making it more identifiable is easy enough, but it's just a thin wrapper around the [[Dialog DB]] storage format, which is binary encoded. Either we require users to introspect it via [[Tonk Hub]] or [[Slide]], or we mirror YAML snapshots to a place the user knows. The former is the easy path for now because if we choose to put human-readable data somewhere on disk, users might think they can edit it manually and get the same affordances they would via the UI or slide.

## Directory Picker
Chromium-only is worth it to experiment for now though we may want a Tauri wrapper later, especially if the tiling views/canvas get built out further. It would feel like using Figma in the browser.

The repo directory in UI will be per-browser-profile for now, not synced through Dialog, especially because users may want different repos on different devices, different locations, different sync states, etc.

We also need to account for when users inevitably move or rename the directory locally. This will require the UI to re-prompt the user to point to it ("We can't find `MyVault.tonk` where you left it, point us at it again?").

We'll need a boot-time check with `handle.queryPermission({ mode: 'readwrite' })` which tells us whether the previously specified directory still has permissions or not, then we can layer an access probe on top that will tell us if the directory still exists at that path. Based on those two, we can either re-prompt for permissions or notify that the path has changed.

Perhaps there's a vault dashboard UI with green for ready, yellow for re-connect, read for re-locate. Yellow will arise pretty frequently so if we keep this approach, the UX needs to feel like unlocking a phone or some other behavior that occurs frequently, not like a burden and a hack. It should feel lightweight.

IDB will be the constant storage layer, but can fan out to R2 (if paying) and/or FS. Putting FS API at the R2 layer instead of replacing IDB resolves issues around needing to re-prompt for FS access any time you want to open a repo. It might also improve the mental model around working state and saved state, so the UI doesn't impact slide or vice versa in unexpected ways.

Need a new `dialog-remote-fs` crate. Choosing to create a new private trait `FsHandle` that covers the I/O surface and two structs, `NativeHandle` and `WebHandle`, cfg-gated to their respective platforms. This is opposed to dynamic dispatch, fully cfg-gated implementations, or making providers and registry generic over `H: FsHandle`. I think this is the cleanest tradeoff that avoids dynamic dispatch, lots of redundant surface area, and propagated generics.

Found a bug in `dialog-storage` while mirroring for `dialog-remote-fs`. There's a TOCTOU bug where the existence of a value is checked before acquiring a lock, so in the time between checking and actioning there could be unexpected behavior.

Also upgraded `pidlock` to `v0.2` which addresses potential panics.
