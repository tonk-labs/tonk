## Portals
`<tonk-view>` and `<tonk-display>` provide a declarative pipeline that works well for structural rendering but cannot express arbitrary DOM manipulation, external library integration, external content, or any imperative logic. Portals aim to provide an escape hatch when users need this type of behavior.

`<tonk-portal>` is a custom web element that renders content inside an iframe. It can appear anywhere inside a `<tonk-view>` alongside declarative bindings and other custom elements. This way any imperative logic is scoped only to portals, while views stay declarative.

A core principle is that portals are painters, not fetchers. `<tonk-display>` and `<tonk-concept>` are fetchers; they open a live subscription to the worker, receive an entity's field values, and bundle them into a `Conclusion`.

`<tonk-view>` is a painter that can either receive a `Conclusion` and paint it, or use a transport internally that communicates with a fetcher. The `{placeholder}` template says where each field value lands. `<tonk-portal>` is a painter like `<tonk-view>` and `<tonk-portal>` is a child of `<tonk-view>`, not a replacement:

```
<tonk-display>
  subscribes to entity + view
    |
    v
<tonk-view>
  renders template (declarative bindings + child elements)
    |
    v
<tonk-portal>
  renders iframe with imperative content
```

`<tonk-display>`, future artifacts, or any other top level renderer doesn't need to know about portals. Fully imperative logic can be rendered by wrapping a portal in a light `<tonk-view>` and then passed on.

`<tonk-portal>` receives an already-fetched HTML string through normal attribute interpolation and simply writes that string into an iframe instead of patching it into the page DOM.

### The `portal` concept
Portal content is asserted directly into [[Dialog DB]] independently so it can be referenced from anywhere. This mirrors how `view` is itself a concept whose `display` field holds a declarative template.

```yaml
concept!: &portal
  description: Imperative HTML rendered in an isolated iframe
  with:
    content:
      description: HTML document written into the portal iframe
      the: xyz.tonk.portal/content
      cardinality: one
      as: text
    height:
      description: Iframe height in pixels
      the: xyz.tonk.portal/height
      cardinality: one
      as: unsigned-integer
```

### Canonical view
A single built-in view bridges the concept to the element. It's asserted once in the boostrap.

```yaml
view!:
  model: portal
  name: basic
  display: |
    <tonk-portal content={content} height={height} />
```

### Referencing portal content
Something must subscribe to the portal content entity to project its `content` field. A nested `<tonk-display>` plays this role. The portal element stays a pure painter and the reference is resolved one level up by a display:

```yaml
portal!: &locations
  content: |
    <canvas id="m"></canvas><script>/* draw locations on #m */</script>
  height: 400

concept!: &map
  with:
    portal:
      the: xyz.tonk.map/portal
      as: entity

view!:
  model: map
  name: basic
  display: |
    <tonk-display entity={portal} model=portal view=basic />
```

Note that this specifically covers the case where the content is unlikely to change, as the entire DOM is rewritten and doesn't preserve state. A robust transport will be implemented as a follow up.

### Rendering
The portal renders with `iframe.srcdoc` so `allow-same-origin` isn't needed, whereas reaching `iframe.contentDocument` to call `document.write` would require same-origin.

The browser conveniently manages the document lifecycle and re-parses on every `srcdoc` change.

On mount and on every `content` change, the portal assigns `srcdoc`. This reloads the iframe wholesale, discarding DOM/JS state. The content field is authoritative. Authors who need incremental, state-preserving updates should handle that inside the iframe's own JS for now.

### Sandboxing
The iframe is created with `sandbox="allow-scripts"` and no `allow-same-origin`. The content cannot read or modify the parent page.

A `portal/content` value is dialog data that any principal with write access to the branch can assert; a viewer then renders it. Granting that content same-origin access would allow the framed content to remove its own sandbox so same-origin isn't available for now. In the future we can provide an opt-in for trsuted content that would remove this sandbox.

### Navigation
Links will default to navigating the iframe. In the future we could enable `allow-top-navigation` with `target="_top"` to navigate the parent. This exploration should probably be coupled with a larger project to intelligently handle opening corresponding views for entities clicked within a given view (i.e., opening a new issues view for issues clicked inside a project view).
