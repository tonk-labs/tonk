## Identify `<tonk-display>` views by anchor name
`<tonk-display>` renders a single entity through a view. A view is a small record describing how to render a concept, which concept (`model`) and what HTML template (`display`). There are two modes:
- single mode: `view` attribute set, render one named view
- carousel mode: only `model` set, render every view published for that concept, one slide each

A view itself is just data in the store asserted like so:
```yaml
view!: &book-dashboard
  model: book
  display: |
    <h1>{title}</h1>
```

Here, `@book-dashboard` is an anchor name, which assigns a stable handle to content-addressed data. `id:book-dashboard` points at the entity DID derived from the hash of the body. This name -> entity mapping is stored as a claim, `dialog.name/referent` on the name DID.

This makes re-asserting views much simpler than before, because while the underlying entity DID changes, the anchor stays the same and is dynamically resolved at usage-time. This eliminates the class of error where there were multiple conflicting claims on a view and no deterministic way to resolve the correct one in a given context.

Before this change, the `view` concept had three fields, `{model, name, display}`, and `<tonk-display>` found its view by matching `model == <model entity>` AND `name == <view attr>`. Each edit minted a new row that carried the same `name: "basic"` so the store accumulated multiple rows matching the same `(model, name)` pair.

`<tonk-display>` would nondeterministically pick one of the multiple entries from the `(model, name)` query.

The fix removes the `name` field from the `view` concept and leans entirely on the anchor name for identity.

Carousel mode also becomes more stable by avoiding potential name conflicts between views. Rather than keying on user-defined view names, slides are keyed by the view entity DID.

## Guide for dynamic, declarative views
The old `slide` CLI guide instructed agents to use `<script>` tags and `globalThis.tonk` bridge API for interactivity. Now that we're building out effects, I'm phasing that out and updating the guide for a fully declarative event model with no JS. This is obviously more limiting than arbitrary HTML/CSS/JS in an iframe, so I discussed options with [[Irakli Gozalishvili]] this morning about the minimal escape hatch for bridging the flexibility of JS with an otherwise declarative model. Therefore, the guide and model around authoring views in general will stay in flux, especially as I'm building out the portals.
