Yesterday I mapped out `<tonk-portal>` for relatively fixed imperative content (think external content, static maps, 3D elements, or arbitrary JS). However, there's another class of usage where authors will want to actively transact with a [[Dialog DB]] repo from within the sandboxed iframe and dynamically update the DOM.

The [[Tonk DSL]] notation is still in flux and transports are likely to change so I want to commit on a stable API now and keep the transport as swappable as possible:

```ts
window.tonk = {
    context,              // { this, model }
    query(query?),        // Promise<Conclusion[]>
    subscribe(query?),    // ReadableStream<Conclusion[]>
    transact(request),    // Promise<receipt>  — structured TransactRequest → /transact
    ready,                // Promise<void>
  }
```

Today I focused on the bridge injected into the portal's iframe and the `<tonk-display>` hook that routes a `text/html` view to a portal.

The `text/html` routing hook is built and tested but isn't reachable in normal use because there's no bootstrapped `view` concept that declares `xyz.tonk.view/type` yet, so no live view frame carries a `type` and the route never fires outside tests. We can wire this in progressively as views are migrated to declaring `type`s.

The main goals were to:
- Get an iframe that reads and writes live data through a stable `tonk` object
- Have `<tonk-display>` automatically mount a portal instead of rendering inline when a `text/html` view is present
- No hand-authored wrapping view
- Author-facing `tonk` bridge API is transport-agnostic and well-suited to experimenting with shape going forward

Notably, there's no `postMessage` implemented yet but will be a fast follow. Iframes are currently same-origin so there's effectively no sandboxing.

`<tonk-host>`, `<tonk-repository>`, and `<tonk-branch>` are parents of `<tonk-portal>`. When the iframe asks for data, the portal dispatches the existing `tonk-query`/`tonk-subscribe`/`tonk-claim` events on itself, which bubble through the parents to `<tonk-host>` which performs the IO.
