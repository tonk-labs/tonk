## Window Manager
Created a new route in [[Tonk Hub]] at `/space/{repo}/branch/main/layout/default` for testing the `<tonk-layout>` component.

You can add a new tile to the workspace either manually, by entering an entity DID, model, and view, or automatically by choosing an already asserted `view` which will render in `<tonk-display>` component, or a concept, which will render as a table in `<tonk-concept>` component.

Per the spec, `<tonk-layout>` manages [[Dialog DB]] subscriptions, state, interpreting input into notation writes, and patching DOM into the niri-strip shape. This makes it opinionated about everything from state and logic to the UI. I'm going to try another approach on top of this where `<tonk-layout>` remains in control of state and logic as fundamental primitives that benefit from imperative style, while remaining fully open-ended about the DOM, gestures, etc.

The shape will be entirely up to the view rendering `<tonk-layout>` from within a `<tonk-display>`. The view may not even need to communicate directly with `<tonk-layout>`, it could just read the same data in Dialog. Niri-specific concepts like columns and widths should be asserted at runtime, whereas fundamentals like the tile registry and universal ordering which the view can interpret per use case.

View template could use `<tonk-concept source="tile">` to bind directly to rows `<tonk-layout>` would have rendered. Reads are fine through Dialog directly, but writes have some complications:
- Midpoint for tile ordering is complex
- ULID minting
- First tile-open needs to mint workspace + tile if workspace doesn't exist yet

For the complicated bits `<tonk-layout>` can expose effects but avoid an API. Maybe one `layout` JS property that returns something like the following, useful for complex niri-like layouts:

```js
{
  workspace: string,           // workspace entity URI
  focus: string | null,        // focused tile entity URI
  tiles: Array<{
    entity: string,
    order: string,             // lex key
    content_entity?: string,
    content_view?: string,
    content_model?: string,
  }>                           // sorted by `order`
}
```

Though a solid effects system might take care of most of the use cases, like directional moves to different tiles (e.g., left arrow moves to left adjacent tile).

Effects would look like this:
- focus-tile (by entity)
- focus-prev / focus-next (walk linear order)
- open-tile (atomic bootstrap-aware; takes content fields)
- close-tile (retracts the tile; advances focus if needed)
- reorder-tile (place between two tiles, or at end — element computes midpoint)
- update-tile-content (set entity / view / model)

View template body would look like this:
```html
<tonk-layout workspace="{workspace}" space="{space}" branch="{branch}"></tonk-layout>
<!-- niri-strip's own rendering, reading column / placement overlay via <tonk-concept>: -->
<div class="strip">
  <tonk-concept source="niri-column" filter="workspace = id:...">
    <template>
      <div class="column" style="flex: {width} 1 0" data-entity="{this}">
        <!-- inner tonk-concept for tiles in this column ... -->
      </div>
    </template>
  </tonk-concept>
</div>
<script>
  // keyboard handlers, drag-resize, scroll-to-focused all live here;
  // they emit effects via DOM events that bubble up to <tonk-layout>.
</script>
```

Universal `tonk-layout`:
```yaml
concept!: &workspace
  description: A workspace of tiles
  with:
    name:    { the: xyz.tonk.layout/workspace-name,  as: text }
    focus:   { the: xyz.tonk.layout/workspace-focus, as: entity, cardinality: one }

concept!: &tile
  description: One tile in a workspace; renders an entity via <tonk-display>
  with:
    workspace: { the: xyz.tonk.layout/tile-workspace, as: entity }
    order:     { the: xyz.tonk.layout/tile-order,     as: text }   # universal linear lex key
    entity:    { the: xyz.tonk.layout/tile-entity,    as: entity }
    view:      { the: xyz.tonk.layout/tile-view,      as: text }
    model:     { the: xyz.tonk.layout/tile-model,     as: text }
```

Niri overlay:
```yaml
concept!: &niri-column
  description: A column in a niri-strip
  with:
    workspace: { the: xyz.tonk.niri/column-workspace, as: entity }
    order:     { the: xyz.tonk.niri/column-order,     as: text }
    width:     { the: xyz.tonk.niri/column-width,     as: float }

concept!: &niri-placement
  description: A tile's placement in a niri column
  with:
    tile:   { the: xyz.tonk.niri/placement-tile,   as: entity }
    column: { the: xyz.tonk.niri/placement-column, as: entity }
    order:  { the: xyz.tonk.niri/placement-order,  as: text }
    height: { the: xyz.tonk.niri/placement-height, as: float }
```

As for the effect transport, I'm starting with DOM `CustomEvent`s which bubble up to `<tonk-layout>`, but they'll be designed for easy refactoring into Dialog effects when that lands ([feat: effects by Gozala · Pull Request #461 · tonk-labs/tonk · GitHub](https://github.com/tonk-labs/tonk/pull/461)).
```ts
tonkLayout.emit('focus-next');
tonkLayout.emit('open-tile', { entity, view, model });
```

When effects land we can emit transient `focus-tile`/`open-tile`/etc concepts that `<tonk-layout>` can subscribe to or describe rules that fire on them.

`tonk-ui` will assert the default niri view doc into a fresh workspace on first run.
