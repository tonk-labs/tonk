## Dialog Cardinality PR
Reviewing [feat: cardinality one assertions by Gozala · Pull Request #333 · dialog-db/dialog-db · GitHub](https://github.com/dialog-db/dialog-db/pull/333). The core issue is that asserting a new value for a cardinality-one attribute on the same entity didn't retract the old one, so subsequent queries would return both the stale value and new one. This PR introduces `Instruction::Replace` and `Change::Replace` to signal supersession alongside existing `Assert` and `Retract`.

Asserting a new value on cardinality-one was supposed to use `Assert` via the `cause` field (a reference to the ancestor version that was to be replaced), delete the previous entries, and insert the new ones. However, `cause` was never populated. `Artifact::update` did set `cause` but it was never called in the lowering.

`associate_unique`'s default delegated to `associate` and `Change::Assert` lowered to `Instruction::Assert` with `cause: None`, so the cause-gated supersession branch was never invoked on the cardinality-one path.

`Replace` is now the default instruction for cardinality-one, while `Assert` is still used for cardinality-many.

> [!NOTE]
> `cause`-based supersession was removed, not fixed, so there is no causal chaining. `Artifact::cause` is never called. Code comments claim the new artifact's `cause` is populated from the first prior found but this isn't true. Noted on PR review.

My first observations are that `claim` is vestigial now and silently dropped in various places which could lead consumers to think causal chains are built when there are none. Misleading docstrings don't help.

Also makes me think `cardinality` could be strongly enforced by typing because there a number of ways `cardinality-one` in particular could degrade if implementers aren't careful to override or respect the specific semantics.

The schema should be the source of truth in both the type system and storage. I think it'd be cleaner if `Instruction::Assert(artifact)` looked up cardinality and routed itself or if `Replace` became a parameter in `Assert` (though first feels purer to me).

The exception where asserting the same value is identical implies that two entities with the same value and different causal histories are identical which further implies causality doesn't matter at all. Either this is a mistake or better to drop `cause` entirely.

The first pass with new notation properly generated a kanban view of some tasks it asserted. Everything is queryable as it should but you'll notice there's no data populating the view. This is due to iframe sandboxing. The script that activates the template lives in the root, while the template lives in the iframe, so they can't talk.

I explored possible options such as injecting the script into the agent's template at either write- or serve- time, giving the agent a starter template that includes the script, or going with an SSG-inspired template structure and simply telling the agent it's writing a template à la Jekyll/Astro.

I'm choosing the SSG approach for now as it minimizes the surface area for mistakes the agent can make, it's the most forgiving, and it closely matches how SSG would actually work so the agent won't need much nudging to do it properly. I'll inject at serve-time, not write-time, which allows us to update `<tonk-concept>` for all views without re-asserting anyone's data.

One potential benefit of only letting agents write the `<body>` fragment is that they can't set titles, custom fonts, or top-level `<meta>`, which keeps us in control for where we want [[Tonk]] brand identity to come through.

I'll try just telling the agent "you're writing the body of a page; chrome and the live-query runtime are provided" which is more accurate and to-the-point than SSG. It's more like a server-rendered layout with hydration.

The wrapper needs to inject `<tonk-concept>` into the iframe's `customElements` registry and `<tonk-concept>` is WASM, so we can either build and link it with `trunk` or reimplement a minimal version in vanilla JS and inline it in the worker.

I'm going with the second for proof of concept though I think the former is better long term to prevent drift.

Hit three bumps along the road. First is that `home` was hardcoded as the repo name so if I joined a repo and gave it a local nickname of `test`, the worker would still query `home` and the template would show up blank. The second snag was `snapshotTemplate` needed to be deferred to `DOMContentLoaded` so the parser-created `<tonk-concept>` elements see their `<template>` children. Lastly, the iframe sandbox didn't allow forms so I added that permission, which makes it easier for users to enter data back into Dialog from the view.
