## `postMessage` transport for `<tonk-portal>`
I want to enforce actual sandboxing on the portal iframes, which means we need to drop `allow-same-origin`. This means it can no longer reach `parent.document` which was previously giving it synchronous calls to the parent. These calls will now require a handshake over `MessagePort`.

We already have prior art for `postMessage` in `tonk-worker/src/router/bridge.rs` so the handshake will roughly mirror that:
- Define `window.tonk` sync with a pending `ready` promise the top-level `tonk.query()` still works. We'll have each method internally await `ready`
- The iframe will open a `MessageChannel` and post "hello" to start the connection, keeping port 1 and handing the parent port 2
- The parent side will attach a handler to the `message` event, check `event.source` from the iframe against ones we've registered, save the channel, and post "ready" back to the iframe along with the parent context, including the dialog `model`

## Background Sync
`tonk-worker` exposes `/sync/{pull,push,sync}` routes and `TonkServiceWorker::sync()` is wired to the browser's background sync API, but nothing drives `sync` on a schedule. [[Dialog DB]]'s `Branch::fetch()` lets us read the upstream without mutating local state and reading `Revision` gives us enough info the classify synced/ahead/behind/diverged for sync statuses.

For [[Slide]], I'm thinking background sync means we'll wrap each mutating command with a pull before and a push after. We can add a `--no-sync` flag to prevent this, or an env var to disable for the term session.

For browsers, the background sync API looked promising but is only supported in Chrome and is intended for PWAs. While it technically works in service workers, idle ones could get killed anyway so it doesn't seem worth it to explore. For now, I'm thinking an interval plus trigger on events.

### Sync State
I'll add a simple `SyncState` enum into `tonk-schema` with `NoUpstream`/`Synced`/`Ahead`/`Behind`/`Diverged`, and a `classify(local: Option<&Revision>, remote: Option<&Revision>) -> Sync State` method.

Not going for precision now, just a general indication of where local stands in relation to remote. We do a single fetch and no history walk. No upstream is self-explanatory, if `local.tree == remote.tree` then we're synced, if `remote.tree ∈ local.cause` we're ahead, if `local.tree ∈ remote.cause` we're behind, and if it's ambiguous we're diverged. If this turns out to be confusing I'll refine further.

Not going to touch the existing push/pull buttons, background sync will remain in the background and push/pull will be usable if a toggle is flipped.

Worker status route is: `/api/repository/{repo}/branch/{branch}/sync/status`.

Since we don't walk history, any more than one commit ahead or behind remote will show as diverged instead. This will be improved in a follow up, keeping the cheap fetch and compare for now.
