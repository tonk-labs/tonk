## `tonk-concept`
Reviewing my work on views in [[Tonk Hub]] yesterday. The vanilla JS subset of the `<tonk-concept>` WASM module is a hack that I'll need to revisit soon before they start drifting, maybe a focus for today as Gavin wants to bring in the tiles.

While exploring `tonk-concept`, I found a bug when the `source` changes from one concept to another. The `Renderer` is dropped but the underlying DOM nodes are never explicitly removed, so they stay attached to their parent container. When the new `Renderer` attaches for the new concept, it appends to the same container but only diffs against rows it knows about. This lumps the old rows from the original concept together with the new ones.

Did a drive-by fix to address the above by clearing the DOM nodes before dropping the renderer.

Also choosing to drop the vanilla JS port now that I know views work and set up a proper `trunk` build that links in the WASM module. Added a new `wasm-bindgen-main` bin shim that calls `tonk_concept::register()` after instantiation. This is how `<tonk-concept>` is added into the `customElements` of the iframe. Instead of embedding the vanilla JS directly into the `<script>`, there's a small `<script type="module">` that imports `init` from the `/tonk-concept.js` wrapper around the WASM module.

## View Manager
Thinking about how we could bring more of Gavin's view manager into the UI.

`<tonk-concept>` owns the set of "tiles" and would update live when tiles are added or removed, driven by a query over views. `<tonk-display>` owns what renders in each tile, picks the right view template for the entity, and mounts a `<tonk-view>` or carousel.

Very rough sketch of tile shape:
```yaml
concept!: &tile
  description: Entity in the set of repo tiles
  with:
    model:
      description: The concept of which this entity is an instance
      the: xyz.tonk.tile/model
      as: entity
      cardinality: one
    position:
      description: Sort key for the strip
      the: xyz.tonk.tile/position
      as: signed-integer
      cardinality: one
	width:
	  description: Width of tile
	  the: xyz.tonk.tile/width
	  as: unsigned-integer
	height:
	  description: Height of tile
	  the xyz.tonk.tile/height
	  as: unsigned-integer
    hidden:
      description: Excluded from the strip without deleting the entity
      the: xyz.tonk.tile/hidden
      as: boolean
      cardinality: one
    pinned:
      description: Held to top of strip
      the: xyz.tonk.tile/pinned
      as: boolean
      cardinality: one
```

- `model` might not be necessary if `<tonk-display>` can resolve the model from `dialog.meta/concept` on the entity. Preferable so `tile` could be pure WM state.
- `position` would hopefully have two axes for the grid, and maybe size/fullscreen, but keeping things simple with a strip for sake of example
- `hidden`/`minimize` would move the tile to the dock in Gavin's example or just hide altogether
- `pinned` would keep the tile to the top of the strip

I'm thinking `tile` would only care about WM state while `<tonk-display>` and the views themselves would handle titles, icons, descriptions, colors, timestamps, authors, and any other artifact-specific data.

```yaml
view!:
  model: tile
  name: default
  display: |
    <article class="tile" style="width: {width}px; height: {height}px">
      <header>{name}</header>
    </article>
	
view!:
  model: board
  name: default
  display: |
    <section class="board">
      <tonk-concept source="tile?board={this}">
        <template>
          <tonk-display entity="{this}" model="tile"></tonk-display>
        </template>
      </tonk-concept>
    </section>
```

Possible effects:
```yaml
# Minimize
effect!:
  assert: { tile: { this: ?this, hidden: true } }
  when:
    - command: { this: ?this, name: Close }

# Reorder
effect!:
  assert: { tile: { this: ?this, position: ?p } }
  when:
    - command: { this: ?this, name: SetPosition, position: ?p }

# Pin
effect!:
  assert: { tile: { this: ?this, pinned: true } }
  when:
    - command: { this: ?this, name: Pin }
```
