## Migrate to Effects
Since my work on the [[Tonk Hub]] layout manager, multiple relevant workstreams have landed:
- proper effects bring declarative `effect!:` rules and `transient:` concepts
- DOM events and transient concept assertions with structured `/transact` means no more YAML-injection bugs
- `<tonk-host>` dissolves problem requiring `space`/`branch` to be passed down to nested concepts

Many of the outstanding bugs in the current hacks/workarounds in `<tonk-layout>` are avoided by simply migrating to effects, so that's the focus focus of the day.

With `<tonk-concept>` and `<tonk-display>` hardened, we almost get the layout manager for free. The increments I'm focusing on today are:
1. Declare a `tiles` concept and a couple `rule!:`s (add/remove) along with a `<tonk-display>` that iterates and renders tiles
2. Order-key correctness with fractional indexing
3. Stable entity IDs

I'm testing where things are now by reimplementing a little reading list demo I made with effects replacing the JS that was previously required to modify and add books.

One quirk I noticed with effects is that they fire structurally, so if I have a `set-status` with `{target,status}` schema and `delete-book` with `{target}` and both `.target`s are declared on `dom.event.target.dataset/id`, a `set-status` could trigger `delete-book` if the effects are declared together.

### Create Issue
**How I understand the event path is supposed to work:**
A button/form in the view names a command concept to fire and the runtime turns the DOM event into a transient claim which a rule turns into a durable change.

DOM event (click) -> transient command claim (add-book, set-status, etc) -> rule fires -> durable `book` change

Every durable claim in [[Dialog DB]] is an EAV triple, so a book is an entity with four claims on it (title, author, status, rating). It's important to determine which entity a write lands on. This is chosen when a concept is asserted:
- Explicit `this:` -> that entity
- Omitted `this:` -> content-addressed, entity ID derived by hashing the body

```yaml
rule!:
  assert!: book
  when:
    - assert: add-book
      where: { this: ?this, title: ?title, ... }   # ?this == "dom:event"
```

If an attribute is cardinality-one, the second add overwrites the first. So instead of adding two books, only the latter one survives: `{"this":"dom:event","title":"The Brothers Karamazov"}`.

Possibly, if `this:` is excluded from transients, the entity's ID would be content-addressed instead.
