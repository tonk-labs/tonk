## Dialog Version Control
### Notes
The driving force behind rethink of divergence clock is that two repositories with no shared history are irreconcilable because the `since` counter in `{ since, at, drift }` have different meanings in the different histories. One history would need to be rewritten with respect to the other, losing provenance.

The new version control proposes replacing the logical counter with the revision DAG when deriving causality. The `Edition` of a revision represents the number of revisions that come before it in the causal chain so a higher revision means more causal history.

Along with an `Origin`, which uniquely identifies a repository by `issuer` and `subject`, `Edition` can be used to point to a specific revision scoped to a specific repository—a `Version`.

Each claim has a `cause` that's empty on first write and contains one entry in the normal sequential case. It contains multiple when resolving concurrent claims from different authors, indicating that this claim intentionally superseded them. This means conflicts can be found by following a single attribute history rather than traversing the entire DAG.

Conflict resolution between claims A and B:
- Check `cause`:
	- If B's version in A's `cause`, A supersedes B, or vice versa
	- If neither, proceed to traversal
- Cause chain traversal
	- Follow higher edition claim's `cause` chain backward looking for lower claim's version
		- Found other claim's version in chain -> supersede
		- Found claim whose edition is less than other claim -> concurrent
		- Chain exhausted -> concurrent

To fork: take `max(forked repo) + 1` as the new edition. Same when creating a fresh repo and pulling pre-existing history.

When pulling history into a repo with separate history of its own: `max(repo A, repo B) + 1` is the new edition. Prior claims are preserved in revision DAG and cause chain re-anchors from merge point.

Concurrent claims are resolved deterministically by claim hash, though the user can view conflicts by querying all concurrent values.

### Comments
While I understand how `Edition` is analogous to Lamport timestamps, I don't understand the claim that a larger edition guarantees seeing at least as much causal history. In the isolated sense, yes, but if two repos evolve from genesis separately then try to merge, if A has edition 100 and B has edition 5, A has seen more causal history but none of B's causal history. The inverse is trivially true: B has seen less causal history than A so it can't be a descendant, but I'm not sure how comparing separate causal histories in this way is useful.

I think this is just a language point, not sure it actually impacts the spec, but it's better to say that editions are useful because they indicate whether one repo might be a descendant/subset of another.

Where it does seem to matter is in cause chain traversal. If causes could potentially hold multiple merge nodes, then you might stop prematurely when finding a lower edition on one branch, while the actual target was on another branch further down. So the only way to definitively know the target doesn't exist in the DAG is to traverse it completely.

For `Origin`, what happens after key rotation? The origin would change and wouldn't be a stable identifier of repo membership.

`Version` should include content hash itself to be more specific, because if Alice has the same repo on two devices and makes concurrent edits locally then tries to sync, the versions will be the same. There's currently no path for surfacing conflict resolution between identical versions. Not sure this is possible if revisions are stored in the tree they describe, so they might need to be separate like Git, or this is an acceptable tradeoff.

As I understand it, `Version` is a workaround to a circularity problem when inserting a new revision: `T = hash(tree_containing(claim(is: hash(Revision(tree: T)))))`. To insert the revision you need the root hash of the tree, which you can't find until inserting the revision. `Version` gives you the ability to compare editions trivially, provenance baked in, and a workaround to the above problem, but it doesn't resolve conflicts around the content itself.

I'm assuming Dialog doesn't want to give up the ability to query revisions the same way as everything else. Claude told me Datomic has an interesting approach where transactions are still queryable as data, but transaction IDs are "assigned monotonically by a single transactor" rather than content-hashed. This avoids circularity because IDs are independent of tree state and a single transactor never reuses an ID. Obviously this won't work for Dialog because it's hardly local first.

Another interesting option is having claim `is:` point backward. A revision claim records "the parent of edition N is the content-hashed revision X" instead of "I am edition N." Essentially the same thing as `cause` but recursively applied to revisions. One tradeoff is that finding the current revision is more complex because you need to find the revision claim with an `is:` that no other claim's parent references. The first claim's `is:` would point to a genesis node or the repo DID.

I guess the challenge here though is that you still need to put the revision metadata somewhere, and that still affects the tree hash. So you could track two tree hashes, one before the current claim was added, and another that resolves after the revision was added, which means there's no single tree hash to look up.

Lastly, any ideas about how to optimize storage when causality is attached to every single transaction?
