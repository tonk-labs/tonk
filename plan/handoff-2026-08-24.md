## What landed

### Onboarding account (`rust/tonk-worker/src/onboarding.rs`)

A device mints a real account at first boot, custodied locally rather
than by a passkey — same secret shape, same envelope, same delegations.
Enrolling a passkey is therefore an account key *rotation*, not a bespoke
migration.

The custodian is a **non-extractable keypair** stored via `.key()`. Its
KEK is never stored: it is re-derived from a signature over
`CUSTODIAN_KEK_CONTEXT` on every boot (Ed25519 signatures are
deterministic, RFC 8032). That is the local stand-in for a passkey's PRF
output.

### Clearance (`rust/tonk-identity/src/clearance.rs`)

Two levels, `Recovery` (custodies the account secret) and `Account`
(`HKDF(account secret)`, wraps space and invite seeds). `Kek<C>` and
`Envelope<C>` are generic over the level, so a mis-tiered wrap is a
compile error; the level is *also* a header byte bound in as AEAD
associated data, so a blob arriving over the wire without a type is
refused rather than failing as an opaque bad key.

There is deliberately **no** third device-scoped level. Session state is
a KDF context and a local root is a delegation; neither is a secret.

### Facts (`rust/tonk-schema/`)

- `SpaceFounded` — `xyz.tonk.space/{foundedAt,foundedBy}`, stamped on the
  space's directory entity at creation only. A directory row *without* it
  is a space this account joined rather than founded.
- `DeviceLink` — `xyz.tonk.device/{createdAt,title,reason}` on the
  `account -> profile` delegation's own entity. The one concept with no
  identifying fields of its own: dialog already made the entity.

`from_navigator` moved to `tonk-common` so the page and the worker label
a device identically.

### Devices through delegations (`router/account_devices.rs`)

Revoking another device no longer demands a passkey-signed artifact. A
device link is a powerline, so any authorized device can prove for the
account subject — which is exactly the authority revoking an
account-issued grant requires. `delegated_revocation` mints it, rebuilding
the target's path from retained `dialog.ucan/*` facts.

Access-service registration also verified chains with
`UnverifiedRevocations`, whose `query` answers "not revoked" to
everything. It now consults `IndexedRevocations`, bound per request.

## The three known gaps in this PR

1. **`DeviceLink` facts are write-only.** The list reverted to the account
   service (see below). The facts land but nothing reads them.
2. **`meta` on the delegation is not written.** `mint_account_union` does
   not expose `DelegationBuilder`'s `meta` field, so only the queryable
   `reason` fact exists, not the signed copy that would survive leaving
   our DB.
3. **`delegated_revocation` needs the target's grant retained locally.**
   A device linked on another machine may not have replicated its grant
   here. The caller-supplied artifact path still takes precedence, so the
   existing flow is unaffected.

## Next: retire account-service

**Read this before starting — it corrects an earlier conclusion.**

The device list was moved to local `DeviceLink` facts and then reverted,
because E2E showed it listed only a subset: a CLI device links on another
machine and registers its name with the service, so this profile never
asserts a fact for it.

**That reasoning is probably wrong, and the retirement hinges on it.**
`describe_device_link` writes to
`profile_repository().branch(MAIN_BRANCH)` — the *same* branch
`retain_space_delegation` uses, which `dialog-identity` calls "the durable
home of delegations" and which pulls bring down to every device. So the
facts are already on a branch that replicates. What is missing is likely
`sync_queue.mark_dirty(...)` to schedule the push, which
`retain_space_delegation`'s caller does and `describe_device_link` does
not.

> [!note]
> This is an **unverified hypothesis**. Confirm it with the E2E test
> before rebuilding the local list —
> `it_revokes_the_cli_device_from_the_browser`
> (`rust/tonk-ui/src/account_flow.rs:1609`) is the one that caught the
> regression.

Order, once replication is confirmed:

1. Add the missing `mark_dirty` after `describe_device_link` commits.
2. Restore the local list (`git show 07dd61c8` has `local_devices` and
   `delegation_audience`, removed in `2e6d4e00`).
3. Verify with E2E that a CLI device appears in the browser's list.
4. Drop the `/devices/list` and `/devices/revoke` calls, keeping
   `publish_revocation` — that is what actually enforces.
5. Delete the `devices` table, its handlers, and the `delegation_cid` pin.

> [!caution]
> `authorize_device_ceremony` (`tonk-account-service/src/auth.rs:129`)
> also requires `proofs[0] == device.delegation_cid`, pinning an
> invocation to one exact delegation. That is stricter than revocation and
> no index can express it. Decide whether it was deliberate or a
> workaround for revocations that did not work; the user's read is the
> latter.

Note account-service's ceremony path still passes `UnverifiedRevocations`.
Wiring it is wasted work if the service is being retired — stop routing
through it instead.

Email is **not** a blocker: access-service already emails a UCAN
delegation of `/customer/activate` audience-bound to the customer, which
is strictly better than account-service's 6-digit code (the link is not a
bearer credential).

## Next: profile secrets

Dialog tag **`tonk-2026-08-24`** was cut for this and points at main's
head, `247ea478` (dialog PR #463).

```rust
use dialog_credentials::secret::Context;
const VAULT: Context = Context::new("dialog/vault/v1");

let sealed = profile.ed25519_did().secret(VAULT).conceal(&vault_key).await?;
let revealed = profile.secret(VAULT).reveal(&sealed).await?;
```

Three properties that matter:

- **No prior interaction.** The recipient's X25519 agreement key derives
  from the Ed25519 key its DID already carries, so you can seal for a
  profile you have only ever seen as a DID — including one that has never
  been online.
- **Forward secrecy per seal.** Each `conceal` uses a fresh ephemeral
  X25519 pair and discards the secret.
- **Compile-time domain separation.** `Context` takes a `&'static str`.

The plan: generate a profile-level secret at account creation and conceal
it for that profile; conceal again for every profile added, at
`persist_link` (`router/account.rs:315`). That is the moment a profile
gains an account.

> [!caution]
> On the web, `SigningKey::generate` now generates an *extractable*
> Ed25519 key, reads its seed once, imports both the signing and X25519
> keys as non-extractable, and drops the original. Because the seed is
> then unrecoverable, the X25519 pair is **archived alongside the signing
> key**. A key restored from an older archive still signs but reports
> `AgreementKeyUnavailable` rather than deriving a wrong key. Check what
> that means for keys already in users' IndexedDB.

## Next: CustodiedSeed and accreditation

Designed, not started. See `plan/onboarding-accreditation.md`.

Space keys are currently generated **non-extractable**, so their seeds
cannot be custodied and a space can only be re-issued by a device holding
its live credential. The user's decision: generate them **extractable**,
seal the seed under the account KEK, and unseal only when rotating.

Space creation then becomes, in this order:

1. `generate_extractable()` — signer + seed (the helper exists as
   `generate_ephemeral` in `router/create_invite.rs:52`; move and rename
   it, "ephemeral" describes an invite key and a space key is the
   opposite).
2. **Mint `space -> account` and save it** — must happen while the signer
   lives; it is the only thing that can sign as this space.
3. Seal the seed under `Kek<Account>`, assert `CustodiedSeed`.
4. Create the local space from the **verifier only** — the
   `join.rs:2137` pattern. `.create()` persists whatever credential it is
   given, so passing the signer would write raw seed bytes to storage.
5. Drop signer and seed.

Accreditation is then account rotation: new secret + passkey KEK, mint
`new_account -> profile`, re-wrap every `CustodiedSeed` under the new
account KEK (bumping `generation`), re-issue each space and invite,
revoke `standin -> profile`, and destroy the onboarding custodian last.
`generation` is what makes an interrupted rotation resumable.

`onboarding::destroy()` was written and then removed (clippy rejects dead
code, and `#[allow]` is against house rules). `git show 07dd61c8^` has it;
it demotes the custodian to its own public half rather than deleting,
since the credential API has no retract for keys.

## House rules that bit during this work

- `cargo fmt --all` and
  `cargo clippy --all --all-targets --all-features -- -D warnings` are the
  gate.
- No `#[allow(...)]` lint silencers — fix the cause or delete the code.
- No `Co-Authored-By` trailers, no "Generated with Claude Code".
- Never bare `git stash` / `git stash pop`: the stack is shared across
  worktrees.
- Tests in `tonk-*` crates use `#[dialog_common::test]` and `it_` names.
- A wasm test module needs `wasm_bindgen_test_configure!(run_in_browser)`,
  and the directive is crate-global — deleting a module can drop it.
